# OpenSpec IDE

Среда для работы по методологии [OpenSpec](https://github.com/Fission-AI/OpenSpec) —
десктопное приложение для Windows, macOS и Linux или локальный сервер с
интерфейсом в браузере:
обозреватель и редактор артефактов, дельты спеков, доска процесса, метрики по
каждому пункту плана, конструктор собственного процесса с проверкой
спек-ориентированности (SDD) и запуск агента через **GigaCode CLI**.

Источник истины — файлы `openspec/` на диске и CLI `@fission-ai/openspec`. Своей
базы состояния у IDE нет: всё, что она создаёт или меняет, остаётся обычным
OpenSpec-проектом, с которым можно работать и из терминала.

Сама IDE тоже разрабатывается по OpenSpec: требования, решения и план лежат в
[`openspec/changes/add-openspec-ide/`](openspec/changes/add-openspec-ide/), макеты
экранов — в [`docs/mockups/openspec-ide.html`](docs/mockups/openspec-ide.html).

## Требования

| Что | Версия | Зачем |
| --- | --- | --- |
| Node.js | 22 и новее | сборка и режим браузера; установленному приложению не нужен |
| `@fission-ai/openspec` | 1.13.x | все операции над проектом идут через этот CLI; приложение везёт свой |
| Браузер | любой современный | только для режима браузера |
| GigaCode CLI | необязательно | раздел «Агент»; без него недоступен только он |

CLI OpenSpec IDE ищет так: `node_modules/.bin/openspec` в каталоге проекта и выше
по дереву, затем `PATH`. Удобнее всего держать его в зависимостях проекта:

```bash
npm install -D @fission-ai/openspec@1.13.1
```

## Установка

```bash
git clone https://github.com/LordOfTheSber/openspec_idle.git
cd openspec_idle
npm ci
npm run build

# команда openspec-ide в PATH
cd packages/cli && npm link && cd -
```

Без `npm link` IDE запускается по полному пути:
`node <путь к openspec_idle>/packages/cli/bin/openspec-ide.js`.

Сборка обязательна при любом способе получения исходников — в том числе из
ZIP-архива ветки: в репозитории нет собранных файлов `dist/`. Без неё
`openspec-ide` сообщит, что IDE не собрана, и напомнит команды.

### Windows

Работает в PowerShell, cmd и Git Bash — те же команды `npm ci`, `npm run build`,
`npm link`. Обёртки `.cmd`, которые npm ставит для `openspec` и `gigacode`, IDE
разбирает сама и запускает их скрипт напрямую через Node: через `cmd.exe`
многострочный промпт агента не передаётся. Команды проверки приёмки в метриках
выполняются оболочкой платформы — на Windows это `cmd.exe`, а не `sh`.

## Запуск

```bash
cd ~/work/my-project        # каталог с openspec/ или любой вложенный
openspec-ide
```

IDE находит ближайший вверх по дереву каталог с `openspec/`, поднимает сервер и
открывает браузер. Адрес печатается в консоль:

```
Рабочее пространство: /home/me/work/my-project
OpenSpec IDE: http://127.0.0.1:41523
```

| Опция | Что делает |
| --- | --- |
| `[путь]` | каталог проекта; по умолчанию текущий |
| `--port <номер>` | фиксированный порт; по умолчанию берётся свободный |
| `--no-open` | не открывать браузер |
| `--dev` | режим разработки IDE: страницу отдаёт Vite |
| `-h`, `--help` / `-v`, `--version` | справка и версия |

Если OpenSpec в проекте ещё не заведён, IDE подскажет выполнить `openspec init`.
Без интерактивного выбора инструментов: `npx openspec init --tools none`.

**Безопасность.** Сервер слушает только `127.0.0.1`. Каждый запрос к API
проверяется по токену сессии, который сервер встраивает в отданную страницу, —
другие программы на машине и чужие вкладки браузера к API не достучатся. Пути к
файлам канонизируются: чтение и запись за пределами рабочего пространства
отклоняются, в том числе через символические ссылки.

## Десктопное приложение

Обычное приложение в своём окне: стартовый экран с недавними репозиториями,
открытие папки системным диалогом, отдельное окно на каждый репозиторий. Ни
Node.js, ни CLI OpenSpec ставить не нужно: CLI входит в поставку и
используется, когда в репозитории нет своей версии (своя версия важнее — в
строке состояния видно, какой CLI работает).

### Установка на Windows

1. Взять установщик `OpenSpec IDE-<версия>-setup.exe`: собрать самому (см.
   «Сборка установщика») или скачать из артефакта `OpenSpec-IDE-windows`
   запуска workflow **desktop** в GitHub Actions.
2. Запустить. Установка идёт в профиль пользователя
   (`%LOCALAPPDATA%\Programs\OpenSpec IDE`) без прав администратора, ярлыки
   появляются в «Пуске» и на рабочем столе. Удаление — через «Приложения».
3. Установщик не подписан, поэтому SmartScreen при первом запуске
   предупредит: «Подробнее» → «Выполнить в любом случае».

Без установки: `OpenSpec IDE-<версия>-portable.exe` запускается откуда угодно,
в систему пишет только каталог настроек.

### Работа

- **Открыть репозиторий** — `Ctrl+O` или кнопка на стартовом экране. Можно
  выбрать любую папку внутри репозитория: корень с `openspec/` ищется вверх по
  дереву. Если `openspec/` нет, приложение предложит выполнить
  `openspec init`.
- **Недавние** — на стартовом экране и в меню «Файл → Недавние». Удалённые
  папки помечаются, их можно убрать из списка.
- Повторное открытие того же репозитория переводит фокус на его окно; повторный
  запуск ярлыком не создаёт второй экземпляр, а путь из командной строки
  (`"OpenSpec IDE.exe" C:\Work\platform`) открывается в уже запущенном.
- Размер и положение окна запоминаются для каждого репозитория.
- Внешние ссылки открываются в системном браузере.
- Закрытие окна, в котором работает агент, спрашивает подтверждение: запуск
  останавливается и помечается прерванным.

| Сочетание | Действие |
| --- | --- |
| `Ctrl+O` | открыть репозиторий |
| `Ctrl+1` … `Ctrl+8` | Обозреватель, Дельты, Доска, Метрики, Агент, Настройки, Процессы, Поиск |
| `Ctrl+W` | закрыть окно |
| `Ctrl+R` | перечитать окно |
| `Ctrl+=` / `Ctrl+-` / `Ctrl+0` | масштаб |

На macOS вместо `Ctrl` — `Cmd`.

Недавние репозитории и положение окон хранятся в профиле пользователя
(`%APPDATA%\OpenSpec IDE` на Windows, `~/.config/OpenSpec IDE` на Linux,
`~/Library/Application Support/OpenSpec IDE` на macOS). В репозиторий
приложение пишет только то же, что и режим браузера, — `.openspec-ide/`.

### Запуск из исходников

```bash
npm ci
npm run desktop:dev          # сборка и запуск приложения
npm run desktop:dev -- C:\Work\platform   # сразу с репозиторием
```

Двоичный Electron (~100 МБ) скачивается не при `npm ci`, а при первом запуске
`electron`, — установка зависимостей для режима браузера его не требует.

### Закрытая сеть: зеркало Electron

Electron и инструменты сборки установщика по умолчанию качаются с GitHub. В
корпоративной сети укажите внутреннее зеркало (Nexus, Artifactory — прокси на
`https://github.com/electron/electron/releases/download/`):

```powershell
# PowerShell
$env:ELECTRON_MIRROR = "https://nexus.example.ru/repository/electron/"
# для сборки установщика ещё и NSIS/7-Zip
$env:ELECTRON_BUILDER_BINARIES_MIRROR = "https://nexus.example.ru/repository/electron-builder-binaries/"
npm run desktop:dev
```

```bash
# Git Bash / Linux / macOS
ELECTRON_MIRROR=https://nexus.example.ru/repository/electron/ npm run desktop:dev
```

Путь зеркала должен заканчиваться `/`; внутри ожидается та же раскладка, что у
релизов Electron: `v44.4.5/electron-v44.4.5-win32-x64.zip`. Скачанное
кэшируется в `%LOCALAPPDATA%\electron\Cache` (`~/.cache/electron`), так что
архив можно и просто положить туда вручную.

### Сборка установщика

```bash
npm ci
npm run desktop:dist
```

Результат — в `packages/desktop/release/`: на Windows установщик NSIS и
переносимый `.exe`, на macOS — `dmg`, на Linux — `AppImage`. Собирать под
Windows надёжнее всего на Windows: на Linux для NSIS нужен Wine с 32-битной
частью. В поставку попадают собранный интерфейс и CLI OpenSpec со всеми
зависимостями (`packages/desktop/staging/openspec`).

## Разделы

Разделы переключаются кнопками на левой панели.

| Кнопка | Раздел | Что в нём |
| --- | --- | --- |
| Об | Обозреватель | Дерево changes, спеков, процессов и архива. Выбор артефакта открывает редактор с подсветкой формата OpenSpec, структурой документа и живой валидацией. Правка на диске, сделанная в обход IDE, подхватывается сразу |
| Дл | Дельты | Требования и сценарии change по операциям ADDED / MODIFIED / REMOVED / RENAMED, сравнение с основным спеком, карта связей capability и changes |
| Дс | Доска | Колонки выводятся из схемы change: сначала артефакты процесса, затем «Готово к работе», «В работе», «Готово к архивации». Создание change по выбранной схеме, отметка пунктов плана, архивация |
| Мт | Метрики | По каждому пункту плана: состояние, время в работе, запуски агента, токены, затронутые файлы, критерий приёмки и его проверка командой. Сводка по change |
| Аг | Агент | Запуск GigaCode CLI по артефакту или пункту плана: сборка промпта, режим и бюджет, ход работы в реальном времени, история запусков |
| Нс | Настройки | Подключение к GigaCode CLI и проверка подключения |
| Пр | Процессы | Реестр схем и конструктор собственного процесса |
| По | Поиск | Полнотекстовый поиск по артефактам и спекам |

Метрики и журнал запусков IDE держит в `.openspec-ide/` в корне проекта. Каталог
исключён из git собственным `.gitignore`: это локальные данные разработчика, и их
потеря не меняет ни одного артефакта OpenSpec. Выгрузка метрик в JSON с версией
формата: `GET /api/metrics/export` (с параметром `?change=<имя>` — по одному change).

## Подключение GigaCode CLI

Единственный канал к модели — процесс GigaCode CLI (форк Qwen Code). Сама IDE в
сеть не ходит.

1. Установите GigaCode CLI и убедитесь, что `gigacode --version` работает.
2. Задайте учётные данные **переменной окружения** в той среде, из которой
   запускается IDE, и перезапустите IDE:

   ```bash
   export GIGACODE_API_KEY=…          # bash, Git Bash
   $env:GIGACODE_API_KEY = "…"        # PowerShell
   set GIGACODE_API_KEY=…             # cmd
   openspec-ide
   ```

   Значение ключа IDE не хранит, не показывает и вырезает из сохраняемых
   промптов и журналов — в настройках указывается только **имя** переменной.
   Если вставить в это поле сам ключ, сохранение будет отклонено.
3. Откройте «Настройки» → «Проверить подключение». Проверка находит исполняемый
   файл (при неудаче перечисляет просмотренные пути), определяет версию и
   поддержку потокового вывода `stream-json`. Если сборка его не принимает, IDE
   переходит на одноразовый вывод `json` и предупреждает, что ход работы будет
   виден только по завершении.

Настройки хранятся в `.openspec-ide/config.json`:

```json
{
  "version": 1,
  "agent": {
    "command": "gigacode",
    "model": "GigaChat-2-Max",
    "credentialsEnv": "GIGACODE_API_KEY",
    "approvalMode": "default",
    "maxWallTime": "15m",
    "maxToolCalls": 120,
    "extraArgs": []
  }
}
```

| Поле | Значение |
| --- | --- |
| `command` | имя в `PATH` или путь к исполняемому файлу |
| `model` | модель; `null` — по умолчанию CLI |
| `credentialsEnv` | имя переменной с ключом; `null`, если CLI авторизован сам |
| `secretEnvs` | другие переменные, значения которых вырезаются из журнала |
| `approvalMode` | режим подтверждения по умолчанию (см. ниже) |
| `maxWallTime` | предел времени запуска: `90`, `30s`, `15m`, `1.5h` → `--max-wall-time` |
| `maxToolCalls` | предел вызовов инструментов → `--max-tool-calls` |
| `extraArgs` | несекретные аргументы CLI, например адрес шлюза. Флаги вида `--api-key` отклоняются |
| `launch.args` | шаблон командной строки — править, только если сборка разошлась с интерфейсом Qwen Code |

**Режимы подтверждения.**

| Режим | Что может агент |
| --- | --- |
| `plan` | только анализ: файлы не меняются, команды не запускаются |
| `default` | правки и команды требуют подтверждения; в неинтерактивном запуске они отклоняются. Значение по умолчанию |
| `auto-edit` | правит файлы без вопросов, команды подтверждаются |
| `auto` | безопасные действия подтверждаются автоматически, рискованные блокируются |
| `yolo` | всё без остановки; каждый такой запуск требует явного согласия |

**Как идёт запуск.** Промпт собирается из вывода `openspec instructions
<артефакт>` или, для пункта плана, `openspec instructions apply` с текстом
пункта и его критерием приёмки. Перед запуском его можно поправить. Команда
запуска видна целиком. По одному change одновременно идёт не больше одного
запуска. Превышение бюджета — отдельный исход, не зависшая вкладка. Остановка
посылает мягкий сигнал, затем принудительный. Показатели запуска попадают в
метрики пункта; запуск по артефакту учитывается только в сводке change.

**Сверка с установленной сборкой.** Шаблон аргументов по умолчанию сверен с
интерфейсом Qwen Code 0.24.4, записанным в [`tests/agent/`](tests/agent/). Чтобы
сверить со своей сборкой GigaCode, запишите её интерфейс и прогоните тесты:

```bash
node tests/agent/record.mjs gigacode tests/agent/gigacode-<версия>
npx vitest run packages/server/src/agent packages/core/src/agentStream.test.ts
```

Если какой-то флаг разошёлся, тест назовёт его. Расхождение правится в
`agent.launch.args`, код IDE менять не нужно.

## Собственный процесс

Встроенная схема OpenSpec — `spec-driven`: proposal → specs → design → tasks. В
разделе «Процессы» команда собирает свою, например с исследованием перед
предложением и обязательным ревью спека перед дизайном.

1. **Создайте схему** с нуля (`openspec schema init`) или форком существующей
   (`openspec schema fork`). Схема появится в `openspec/schemas/<имя>/` —
   `schema.yaml` и каталог шаблонов. Это формат самого OpenSpec: процесс работает
   и без IDE.
2. **Соберите процесс.** Граф артефактов, форма свойств и YAML синхронны: правка в
   любом из них сразу видна в остальных. Пока YAML не разбирается, граф и форма
   показывают последнее корректное состояние, а сохранение заблокировано. У
   артефакта задаются порождаемый путь, описание, шаблон, инструкция для агента и
   зависимости. Для начала работ — какие артефакты нужны и какой файл
   отслеживается (по нему считается прогресс).
3. **Проверьте.** Проверка идёт в два слоя. Структура — `openspec schema validate`:
   цикл зависимостей, отсутствующий шаблон. Спек-ориентированность — правила IDE:

   | Правило | Уровень | Суть |
   | --- | --- | --- |
   | `sdd/behaviour-contract` | ошибка | есть артефакт, порождающий дельты спеков (`generates: specs/**/*.md`) |
   | `sdd/code-after-contract` | ошибка | работа по коду (`apply.requires`) зависит от контракта |
   | `sdd/tracked-artifact` | ошибка | отслеживаемый артефакт объявлен и существует |
   | `sdd/reachable` | ошибка | все артефакты достижимы по зависимостям |
   | `sdd/motivation-first` | предупреждение | спекам предшествует артефакт с мотивацией |
   | `sdd/artifact-instruction` | предупреждение | у каждого артефакта есть инструкция |

   Выбор нарушения в отчёте выделяет артефакт на графе и ставит курсор в нужное
   поле формы.
4. **Назначьте.** «Назначить проекту» меняет в `openspec/config.yaml` только
   строку `schema:`. Назначение, как и создание change по схеме, блокируется, пока
   есть нарушения уровня «ошибка»; предупреждения показываются, но не мешают.
   Сохранить несоответствующую схему как черновик можно всегда. Начатые changes
   остаются на своей схеме.

От правила можно отказаться адресно, с причиной, записанной в самой схеме, —
тогда отказ попадёт в код-ревью вместе с процессом:

```yaml
sdd_waivers:
  - rule: sdd/behaviour-contract
    reason: Процесс для хотфиксов, поведение системы не меняется
```

Отказ без причины не действует. Действующий отказ виден в реестре схем и на
карточках доски.

## Разработка

```bash
npm ci
npm run dev        # IDE на этом же репозитории: сервер и Vite с горячей перезагрузкой
npm run verify     # typecheck + lint + модульные тесты (Vitest)
npm run test:e2e   # сборка и сквозные тесты (Playwright)
npm run test:desktop  # сборка приложения и его сквозные тесты (Playwright + Electron)
```

На Linux без дисплея e2e приложения запускаются под `xvfb-run -a npm run test:desktop`.

Для e2e нужен Chromium. Если браузеры Playwright не скачаны, укажите свой:
`CHROMIUM_PATH=/path/to/chrome npm run test:e2e`.

```
packages/
  core/      чистая логика без Node API: разбор артефактов, доска, метрики,
             правила SDD, разбор потока агента (проверяется тестом purity)
  server/    Fastify, обёртка над CLI OpenSpec, наблюдение за файлами,
             метрики, реестр схем, мост к агенту
  web/       React-приложение
  cli/       бинарь openspec-ide
  desktop/   приложение на Electron: окна, стартовый экран, меню, поставка
tests/
  fixtures/  фикстурные OpenSpec-проекты для тестов
  agent/     записанный интерфейс CLI агента и заглушка для тестов
  e2e/       сквозные тесты
  desktop/   сквозные тесты приложения
openspec/    требования и план самой IDE
docs/        макеты
```

Работа ведётся по OpenSpec: у каждой задачи в
[`tasks.md`](openspec/changes/add-openspec-ide/tasks.md) есть критерий приёмки,
после каждой группы прогоняется `npm run verify`.

```bash
npx openspec status --change add-openspec-ide
npx openspec validate add-openspec-ide --strict
```
