# OpenSpec IDE для VS Code

Расширение VS Code для работы по методологии
[OpenSpec](https://github.com/Fission-AI/OpenSpec): дерево changes и спеков,
замечания валидации в панели «Проблемы», доска процесса, дельты спеков, метрики
по каждому пункту плана, конструктор собственного процесса с проверкой
спек-ориентированности (SDD), проверка структуры папок и **карта контекста**:
модули, их домены (спеки), зависимости и ADR — графом и матрицей. В редакторе —
**помощь при написании** спеков, дельт и плана; на доске и в «Проблемах» —
**пересечения changes и устаревшие дельты**; в разделе «Контекст» —
**контроль контекста**: объём в токенах, лишнее и связь с кодом; для CI —
команда **`openspec-ide-check`** с теми же проверками.

Источник истины — файлы `openspec/` на диске и CLI `@fission-ai/openspec`. Своей
базы состояния у расширения нет: всё, что оно создаёт или меняет, остаётся
обычным OpenSpec-проектом, с которым можно работать и из терминала.

Раньше IDE была отдельной web-средой с бинарём `openspec-ide` и вкладкой
браузера. Теперь это расширение: артефакты правятся в редакторе VS Code, а
бэкенд работает внутри процесса расширения, без сетевого порта. Решение и план
переезда — в архивном change
[`add-vscode-extension`](openspec/changes/archive/2026-09-24-add-vscode-extension/),
исходные требования IDE — в
[`add-openspec-ide`](openspec/changes/archive/2026-09-24-add-openspec-ide/). Действующие
требования — основные спеки в [`openspec/specs/`](openspec/specs/).

## Требования

| Что | Версия | Зачем |
| --- | --- | --- |
| VS Code | 1.90 и новее | среда, в которой работает расширение |
| `@fission-ai/openspec` | 1.13.x | все операции над проектом идут через этот CLI |
| Node.js | 22 и новее | только для сборки расширения из исходников |

CLI OpenSpec расширение ищет так: путь из настройки `openspec.cliPath` (или
переменной `OPENSPEC_CLI`), если он задан; иначе `node_modules/.bin/openspec` в
каталоге проекта и выше по дереву, затем `PATH`, затем каталоги глобальной
установки npm (`%APPDATA%\npm`, префикс npm, nvm-windows, Volta, fnm;
`~/.npm-global/bin`, `/usr/local/bin` и т. п.). Удобнее всего держать CLI в
зависимостях проекта:

```bash
npm install -D @fission-ai/openspec@1.13.1
```

**`openspec` работает в терминале, а расширение пишет «Не найден CLI».** VS Code
берёт `PATH` при запуске: CLI, поставленный после, или путь, который добавляет
`.bashrc` Git Bash, процессу редактора не видны. Закройте все окна VS Code и
откройте заново; если не помогло — узнайте путь и впишите его в настройку
`openspec.cliPath` (подойдёт и каталог, и вывод Git Bash вида `/c/Users/…`):

```bash
which openspec      # Git Bash
where openspec      # cmd
```

После изменения настройки расширение перезапускает бэкенд само; кнопка
«Обновить» в дереве тоже ищет CLI заново.

## Установка

Расширение пока не опубликовано в Marketplace — оно собирается в файл `.vsix`:

```bash
git clone https://github.com/LordOfTheSber/openspec_idle.git
cd openspec_idle
npm ci
npm run package        # → packages/vscode/dist/openspec-ide.vsix

code --install-extension packages/vscode/dist/openspec-ide.vsix
```

Вместо последней команды можно в VS Code открыть «Расширения» → «…» →
«Установить из VSIX…» и выбрать тот же файл. Собранных файлов в репозитории нет:
сборка обязательна при любом способе получения исходников, в том числе из
ZIP-архива ветки.

**После установки новой сборки поверх прежней перезагрузите окно VS Code**
(палитра → «Developer: Reload Window» или кнопка «Перезагрузить» у расширения).
Панель подхватывает новый интерфейс сразу, а бэкенд расширения — только после
перезагрузки окна; до неё новые разделы отвечают, что бэкенд не знает маршрута.

Команды одинаковы в bash, PowerShell, cmd и Git Bash. На Windows обёртку `.cmd`
для `openspec`, которую ставит npm, расширение разбирает само и запускает скрипт
CLI через Node напрямую; нераспознанная обёртка запускается через `cmd.exe`.
Команды проверки приёмки в метриках выполняются оболочкой платформы — на Windows
это `cmd.exe`, а не `sh`.

## Запуск

Откройте в VS Code папку проекта («Файл» → «Открыть папку…» или `code .`).
Расширение активируется само, если в рабочей области есть
`openspec/config.yaml`, и берёт корнем первую папку рабочей области, в которой
или выше которой по дереву есть `openspec/` — так же, как CLI. На панели действий
появится значок **OpenSpec**.

Если OpenSpec в проекте ещё не заведён, дерево подскажет выполнить
`openspec init` (без интерактивного выбора инструментов:
`npx openspec init --tools none`) и нажать «Обновить». Если не найден CLI
OpenSpec, дерево назовёт команду установки.

**Безопасность.** Расширение не открывает ни одного порта: панель разделов
общается с бэкендом сообщениями webview. Панель загружает скрипты только из
файлов расширения, по политике Content-Security-Policy с одноразовым nonce и без
доступа к сети. Пути к файлам канонизируются: чтение, запись и открытие за
пределами рабочего пространства отклоняются, в том числе через символические
ссылки.

## Что где в VS Code

**Дерево «Рабочее пространство»** на панели OpenSpec — разделы «Изменения»,
«Спеки», «Процессы» и «Архив». У change видны схема, прогресс по отслеживаемому
артефакту (`4/11`) или число ошибок валидации, у артефакта — состояние. Выбор
артефакта, спека или проектной схемы открывает файл в редакторе; отсутствующий
артефакт расширение предложит создать по шаблону схемы. Правки на диске в обход
редактора — git, терминалом, внешним агентом — подхватываются сразу.

**Панель «Проблемы».** Замечания `openspec validate <change> --strict` ложатся на
файл и строку. Если CLI строки не сообщает, но называет требование
(`MODIFIED "Выгрузка данных" omits scenario(s)…`), замечание ложится на строку
заголовка этого требования в дельте. Проверка идёт при активации для всех
активных changes, при каждом изменении файлов change и по команде. **Основные
спеки** проверяются так же — `openspec validate --specs --strict`: при
активации, при изменении `openspec/specs/` (в том числе после архивации) и
командой «Проверить основные спеки»; путь замечания вида `requirements[2]`
переводится в строку третьего требования. Там же — нарушения структуры папок,
замечания карты контекста (неизвестный домен, неописанный модуль в
`depends_on`, цикл зависимостей) на строке поля `index.md`, ссылки дельт и плана
(см. «Помощь в редакторе») и пересечения changes (см. «Пересечения и
устаревание»).

**Контекстное меню change:** «Проверить change», «Предпросмотр архивации»,
«Архивировать change», «Метрики», «Дельты», «Доска». У спека — «Дельты».

**Панель разделов** — одна вкладка редактора с интерфейсом IDE. Повторный вызов
переключает раздел в той же вкладке. Оформление берётся из темы VS Code: цвета
акцента, успеха, предупреждения и ошибки — из переменных темы, статус всегда
показан иконкой, цветом и текстом.

Разделы — вкладки в шапке панели (в узкой панели у неактивных остаются иконки).
Там же поле **«Поиск и команды»** (Ctrl+K, ⌘K на macOS): палитра ищет по
требованиям, сценариям, changes, спекам и схемам, фильтруется чипами, а команды
вроде «Создать change…», «Проверить», «Архивировать change…» и «Трассировка»
выполняются из того же поля. Команда VS Code «Поиск и команды» открывает ту же
палитру. «Дельты» и «Метрики» выбирают change переключателем в шапке раздела —
дерево слева больше не нужно.

**Нить change** — путь change одной линией: узлы артефактов схемы и завершающий
«Архив». Созданный артефакт — зелёный узел, следующий шаг — обведённый,
пропущенный — пунктирный; отрезок перед «Архивом» заполняется по прогрессу
плана. Щелчок по узлу открывает файл артефакта. Нить стоит на карточке доски и
в панели деталей.

| Раздел | Что в нём |
| --- | --- |
| Доска | Фазы выводятся из схемы change: сначала артефакты процесса, затем «Готово к работе», «В работе», «Готово к архивации». Над колонками — полоса всех фаз со счётчиками; колонки показаны только для фаз с карточками, щелчок по пустой фазе в полосе показывает её колонку, кнопка «Пустые фазы» — все сразу. В узкой панели (уже 640 px) режим «Авто» показывает фазы списком; режим и показ пустых фаз запоминаются. Фильтр по имени. Карточка: схема, возраст, нить change, статус проверки и одно следующее действие — создать недостающий артефакт по шаблону или архивировать. Панель деталей change: готовность к архивации из пяти условий (артефакты, план, валидация, покрытие сценариев, предпросмотр), артефакты и затронутые спеки, вкладки «План» (пункты по группам с отметкой), «Проверка» (валидация с переходом к строке, предпросмотр архивации) и «Трассировка». Правки файлов в редакторе двигают карточки сразу |
| Дельты | Сводка по операциям, требования change по ADDED / MODIFIED / REMOVED / RENAMED со сценариями «когда / тогда», сравнение с основным спеком, предупреждение, если спек меняет ещё один активный change. Вкладка «Трассировка» — сценарии → пункты плана → приёмка (см. ниже), «После архивации» — предпросмотр того, что станет с основными спеками. Без выбранного change — карта связей capability и changes |
| Метрики | Сводка: выполнено, приёмка проверена, без критерия, расхождения; показатели без данных — одной строкой, пустые столбцы скрыты. Строка пункта раскрывается: критерий и команда проверки приёмки, время, затронутые файлы (открываются в редакторе) |
| Процессы | Реестр схем и конструктор собственного процесса |
| Структура | Проверка папок контекста и спецификаций по `openspec/structure.yaml`: сводка, дерево описания со статусами, нарушения с переходом к файлу или правилу, создание описания |
| Контекст | Карта модулей, доменов и ADR из `openspec/context/`: граф и матрица связей модуль ↔ домен, зависимости модулей, замечания, набор файлов контекста для модуля или для нескольких выбранных щелчками модулей, доменов и ADR. Пока модулей нет — формат с примером и «Создать модуль…» |

**Команды палитры** (префикс «OpenSpec:»): «Обновить», «Создать change» (с выбором
схемы), «Проверить change», «Предпросмотр архивации», «Архивировать change»,
«Архивировать готовые changes…», «Проверить основные спеки», «Проверить
структуру папок», «Карта контекста» и открытие каждого раздела. Команды, которым
нужен change, при вызове из палитры предлагают выбрать его.

**Предпросмотр архивации.** У `openspec archive` нет «сухого» режима, поэтому IDE
прогоняет настоящий `openspec archive <name> --yes --json` на временной копии
каталога `openspec/` и сравнивает получившиеся основные спеки с текущими. Файлы
проекта не меняются, копия удаляется. Видно, пройдёт ли архивация (а если нет —
сообщение CLI и подсказка), какие capability появятся или изменятся, какие
требования добавятся, изменятся, переименуются и удалятся, какие сценарии
появятся и пропадут, и построчное сравнение файла. Команда «Предпросмотр
архивации» и кнопка «Открыть сравнение» открывают это во встроенном редакторе
сравнения VS Code (справа — документ только для чтения). «Архивировать change»
сначала показывает сводку изменений спеков и не предлагает архивацию, которую
CLI отклонит.

**Строка состояния** — число активных changes и спеков; щелчок открывает доску.

Метрики расширение держит в `.openspec-ide/` в корне проекта.
Каталог исключён из git собственным `.gitignore`: это локальные данные
разработчика, и их потеря не меняет ни одного артефакта OpenSpec.

## Как IDE работает с CLI OpenSpec

Любое чтение и изменение OpenSpec-проекта идёт через CLI `openspec` — своей
реализации этих операций у IDE нет. LLM IDE не вызывает: агентов вы запускаете
сами, а IDE готовит для них контекст (раздел «Контекст») и подхватывает
изменения файлов, которые они сделали.

| Когда | Команда |
| --- | --- |
| Дерево, доска, метрики — состояние changes, спеков, схем | `openspec list`, `status --change`, `schemas`, `schema which`, `templates` |
| Проверка change (панель «Проблемы», доска) | `openspec validate <change> --strict` |
| Проверка основных спеков | `openspec validate --specs --strict` |
| Проверка архива (только `openspec-ide-check`) | `openspec validate --archived` |
| Создание change | `openspec new change <name> --schema <schema>` |
| Архивация | `openspec archive <name> --yes` |
| Предпросмотр архивации | `openspec archive <name> --yes --json` на временной копии `openspec/` |
| Создание и проверка собственной схемы | `openspec schema init` / `schema fork` / `schema validate` |

Создание артефакта «Создать по шаблону» берёт шаблон схемы из
`openspec templates` — файл получается с заголовками и заглушками.

Структура папок и карта контекста строятся по файлам, без CLI. Для
устаревших дельт и забытых changes IDE читает историю `git` (только чтение:
`log`, `show`, `status`); без git эти проверки работают по архиву и датам.

## Помощь в редакторе

Для основных спеков, дельт активных changes и их планов (отслеживаемого
артефакта схемы) расширение даёт языковые функции VS Code. Всё работает по
несохранённому тексту редактора.

| Где | Что |
| --- | --- |
| Дельта: строка `##` | Заголовки `## ADDED/MODIFIED/REMOVED/RENAMED Requirements` |
| Дельта: `### Requirement: ` в MODIFIED и REMOVED, `FROM: ` в RENAMED | Имена требований основного спека этой capability, ещё не упомянутые в секции |
| Спек и дельта: пустая строка | Шаблоны «Требование со сценарием» (с ДОЛЖНА (SHALL) и WHEN/THEN) и «Сценарий» |
| План: после `↳ ` | Ссылки `capability / сценарий` и `capability / требование` на ADDED и MODIFIED дельт change |
| Наведение | На ссылке плана — требование и шаги сценария; на MODIFIED/REMOVED — текущий текст требования в основном спеке |
| F12 | Со ссылки плана — к сценарию в дельте; с MODIFIED/REMOVED — к требованию основного спека |
| Над требованием дельты | «Пунктов плана: N» (к первому пункту) или «Не покрыт планом — добавить пункт» (дописывает пункт со ссылкой на требование целиком); «Основной спек» |
| Над пунктом плана | «Покрывает сценариев: N» |
| Outline плана | Группы и пункты с отметкой выполнения (заголовки спеков и дельт в Outline уже показывает Markdown VS Code) |
| Ctrl+T | Требования и сценарии основных спеков и дельт — с capability, операцией и change |

**Проверка ссылок** (панель «Проблемы», источник `openspec-authoring`, сразу при
наборе):

| Замечание | Уровень |
| --- | --- |
| MODIFIED, REMOVED или RENAMED `FROM:` — требования нет в основном спеке (с похожими именами) | ошибка |
| ADDED или RENAMED `TO:` — требование уже есть в основном спеке | ошибка |
| MODIFIED/REMOVED для capability без основного спека | ошибка |
| Ссылка `↳` в плане не находит ни сценария, ни требования | предупреждение |

Имена сравниваются так же, как при архивации CLI: точно, после обрезки
пробелов по краям, — поэтому «кодировка файла» и «Кодировка файла» разные
требования, и второе будет предложено в исправлении.

**Быстрые исправления** (Ctrl+.): «Заменить на „…“» — похожее имя основного
спека; «Скопировать требование из основного спека» для MODIFIED — тело блока
заменяется описанием и всеми сценариями требования основного спека, заголовок и
остальной файл не меняются. Это и есть правка ошибки CLI «MODIFIED … omits
scenario(s)»: MODIFIED заменяет требование целиком.

## Пересечения и устаревание

- **Пересечение** — одно требование capability затрагивают два и более
  активных change (MODIFIED, REMOVED, RENAMED по прежнему имени или одинаковое
  ADDED). Видно отметкой «пересечение» на карточках, строкой в панели деталей
  (««Выгрузка данных» — также rework-export (MODIFIED)», с переходом к строке) и
  предупреждением в «Проблемах» на заголовке в каждой дельте. Change,
  архивированный вторым, должен учесть правки первого.
- **Устаревшая дельта** — для MODIFIED, REMOVED и RENAMED IDE берёт основной
  спек в том коммите, где файл дельты появился в git, и сравнивает требование
  тогда и сейчас. Изменилось — отметка «дельта устарела», в панели деталей —
  изменённые сценарии и архивированные после этого changes, в «Проблемах» —
  предупреждение с действием «Что изменилось в основном спеке» (сравнение
  «тогда ↔ сейчас» в редакторе VS Code). Незакоммиченная дельта написана по
  текущему спеку и устаревшей не считается. Без git — «возможно устарела», если
  после даты создания change (`created` в `.openspec.yaml`) архивирован change,
  менявший то же требование.
- **Забытый change** — в фазе «Готово к архивации» без активности 3 дня и
  дольше: отметка «ждёт архивации N дн.». Активность — последний коммит каталога
  change (незакоммиченные правки — «сейчас»), без git — время изменения файлов.
- **«Архивировать готовые changes…»** — выбор из фазы «Готово к архивации»,
  одно подтверждение, архивация по одному в порядке создания (без даты —
  последними), каждой предшествует предпросмотр. Change, который CLI отклонит,
  пропускается с причиной; итог — одним сообщением.

## Проверка в CI

`openspec-ide-check` прогоняет те же проверки, что показывает расширение, и
годится для CI и pre-commit. Это один файл без зависимостей: нужен Node 22 и
CLI OpenSpec проекта.

```bash
npm run build -w openspec-ide-check     # → packages/check/dist/openspec-ide-check.mjs
node openspec-ide-check.mjs             # в каталоге проекта или --root <каталог>
```

| Проверка | Что | Пропускается, если |
| --- | --- | --- |
| `validate` | `openspec validate --strict` всех активных changes и основных спеков, со строками | — |
| `archived` | `openspec validate --archived`: у архивных changes выполнены все пункты | архив пуст |
| `structure` | `openspec/structure.yaml` | нет описания |
| `context` | карта контекста `openspec/context/` | нет модулей и ADR |
| `schemas` | структура и правила SDD собственных схем `openspec/schemas/` | нет собственных схем |
| `authoring` | ссылки дельт на основной спек и ссылки `↳` плана | — |
| `coverage` | сценарии ADDED/MODIFIED без пунктов плана (предупреждение) | в планах нет пунктов |
| `drift` | пересечения и устаревшие дельты (предупреждение) | нет активных changes |

Параметры: `--only a,b`, `--skip a,b`, `--format text|json|github`,
`--fail-on error|warning|info` (по умолчанию `error`), `--cli <путь к openspec>`,
`--root <каталог>`. Код завершения: 0 — замечаний на уровне `--fail-on` и выше
нет, 1 — есть, 2 — ошибка запуска (неизвестная проверка, нет корня OpenSpec,
нет CLI для проверок, которым он нужен). Проверка ничего не пишет в проект.

Проще всего положить собранный файл в репозиторий проекта, например в
`tools/openspec-ide-check.mjs`. GitHub Actions — замечания появляются
аннотациями на строках PR:

```yaml
- uses: actions/checkout@v4
  with:
    fetch-depth: 0          # история нужна проверке drift
- uses: actions/setup-node@v4
  with:
    node-version: 22
- run: npm ci               # ставит @fission-ai/openspec из devDependencies
- run: node tools/openspec-ide-check.mjs --format github
```

pre-commit (`.git/hooks/pre-commit` или husky) — только быстрые проверки по файлам:

```bash
node tools/openspec-ide-check.mjs --only structure,context,authoring
```

В этом репозитории — `npm run check:openspec`.

## Собственный процесс

Встроенная схема OpenSpec — `spec-driven`: proposal → specs → design → tasks. В
разделе «Процессы» команда собирает свою, например с исследованием перед
предложением и обязательным ревью спека перед дизайном.

1. **Создайте схему** с нуля (`openspec schema init`) или форком существующей
   (`openspec schema fork`). Схема появится в `openspec/schemas/<имя>/` —
   `schema.yaml` и каталог шаблонов. Это формат самого OpenSpec: процесс работает
   и без IDE.
2. **Соберите процесс.** Граф артефактов, форма свойств и YAML синхронны: правка в
   любом из них сразу видна в остальных. Пока YAML не разбирается, граф и форма
   показывают последнее корректное состояние, а сохранение заблокировано. У
   артефакта задаются порождаемый путь, описание, шаблон, инструкция и
   зависимости. Для начала работ — какие артефакты нужны и какой файл
   отслеживается (по нему считается прогресс).
3. **Проверьте.** Проверка идёт в два слоя. Структура — `openspec schema validate`:
   цикл зависимостей, отсутствующий шаблон. Спек-ориентированность — правила IDE:

   | Правило | Уровень | Суть |
   | --- | --- | --- |
   | `sdd/behaviour-contract` | ошибка | есть артефакт, порождающий дельты спеков (`generates: specs/**/*.md`) |
   | `sdd/code-after-contract` | ошибка | работа по коду (`apply.requires`) зависит от контракта |
   | `sdd/tracked-artifact` | ошибка | отслеживаемый артефакт объявлен и существует |
   | `sdd/reachable` | ошибка | все артефакты достижимы по зависимостям |
   | `sdd/motivation-first` | предупреждение | спекам предшествует артефакт с мотивацией |
   | `sdd/artifact-instruction` | предупреждение | у каждого артефакта есть инструкция |

   Выбор нарушения в отчёте выделяет артефакт на графе и ставит курсор в нужное
   поле формы.
4. **Назначьте.** «Назначить проекту» меняет в `openspec/config.yaml` только
   строку `schema:`. Назначение, как и создание change по схеме, блокируется, пока
   есть нарушения уровня «ошибка»; предупреждения показываются, но не мешают.
   Сохранить несоответствующую схему как черновик можно всегда. Начатые changes
   остаются на своей схеме.

От правила можно отказаться адресно, с причиной, записанной в самой схеме, —
тогда отказ попадёт в код-ревью вместе с процессом:

```yaml
sdd_waivers:
  - rule: sdd/behaviour-contract
    reason: Процесс для хотфиксов, поведение системы не меняется
```

Отказ без причины не действует. Действующий отказ виден в реестре схем и на
карточках доски.

## Трассировка сценариев

Спеки change задают сценарии, план — пункты, метрики — проверки приёмки.
Вкладка «Трассировка» раздела «Дельты» связывает их: сценарии добавленных и
изменённых требований → пункты плана → проверка приёмки и затронутые файлы, с
процентом покрытия. Сценарий, на который не ссылается ни один пункт, — пробел:
его может не оказаться в коде, хотя он есть в контракте.

Пункт плана ссылается на сценарий строкой под ним — `↳` (или `->`), затем
`<capability> / <сценарий>`:

```markdown
- [ ] 2.2 Предупреждение при команде без CLI
  ↳ vscode-extension / Команда без CLI
```

Ссылка на требование (`↳ ide-runtime / Поиск CLI OpenSpec`) покрывает все его
сценарии, несколько ссылок — несколько строк. Без явной ссылки IDE находит связь
по названию сценария или требования (от 12 символов) в тексте пункта и рисует её
пунктиром как предполагаемую. Для CLI OpenSpec строка ссылки — обычный текст
списка: прогресс и валидация от неё не меняются.

Для пробела есть два действия: **«Добавить пункт в план»** дописывает в конец
последней группы отслеживаемого артефакта пункт с названием сценария и строкой
ссылки (остальные строки файла не меняются), **«Копировать задачу для агента»**
кладёт в буфер сценарий с шагами и пути `@файл` спека и плана.

## Структура папок

Структура папок для контекста и спецификаций описывается в
`openspec/structure.yaml` и лежит в репозитории, как `config.yaml`: это
договорённость команды. IDE проверяет, что проект ей соответствует, в разделе
«Структура», а в VS Code — ещё и в панели «Проблемы». Без этого файла проверка
не выполняется; раздел «Структура» предложит создать его по текущей раскладке
`openspec/`.

Описание — дерево от корня проекта: ключ — имя, значение — правило.

| Запись | Что значит |
| --- | --- |
| `имя: file` | обязательный файл |
| `имя:` и вложенный перечень | папка строго с перечисленным содержимым — всё остальное в ней лишнее |
| `имя: "*"` | папка, внутри которой допустима любая структура |
| `имя: any` | файл или папка с любым содержимым |
| `имя?: …` | необязательный элемент |
| `"*.md": file`, `"ADR-*": file`, `"*": "*"` | шаблон имени: сколько угодно подходящих элементов, каждый проверяется по правилу |

Жёстко, с точностью до папки и файла:

```yaml
version: 1
structure:
  docs:
    context:
      README.md: file
      glossary.md: file
      architecture.md: file
```

В `docs/context` должны быть ровно эти три файла: любой другой — нарушение.

Мягко — жёстко до нужной папки, а внутри неё что угодно:

```yaml
version: 1
structure:
  openspec:
    structure.yaml: file
    config.yaml: file
    specs: "*"          # путь до specs/ фиксирован, внутри — любая структура
    changes: "*"
    schemas?: "*"
  docs:
    context:
      README.md: file
      "*.md": file      # сколько угодно .md, и ничего кроме них
      adr: "*"
```

Правила проверки:

- Корень проекта не строгий: проверяются только перечисленные на первом уровне
  элементы, `src/`, `package.json` и прочее не трогаются.
- Точное имя важнее шаблона; из нескольких шаблонов действует первый
  подходящий. Шаблон всегда необязателен, `?` к нему — ошибка описания.
- Служебные `.DS_Store`, `Thumbs.db`, `.gitkeep` не считаются лишними; список
  меняется полем `ignore`.
- Имена сравниваются с учётом регистра, как в git.
- Нарушения трёх видов: нет обязательного элемента, лишний элемент в строгой
  папке, не тот тип (файл вместо папки и наоборот). У каждого — строка правила в
  `structure.yaml`. В VS Code лишний файл подсвечивается на самом файле, всё
  остальное — на строке правила.
- Ошибки в самом описании (неизвестное правило, `/` в имени, необязательный
  шаблон) показываются с номером строки, и пока они есть, проверка не
  выполняется.

Структура этого репозитория описана в [`openspec/structure.yaml`](openspec/structure.yaml).

## Контекст модулей

Контекст для людей и агентов лежит в `openspec/context/`:

```
openspec/context/
  1.md, 2.md, …              общий контекст проекта
  modules/
    master/
      index.md               метаданные модуля (frontmatter)
      context.md             сам контекст модуля
    sds-impl/
      index.md
      context.md
  adr/
    ADR-001-….md             решения со ссылками на модули и домены
openspec/specs/
  session-lifecycle/spec.md  домены — это спеки OpenSpec
  replication/spec.md
  …
```

`index.md` модуля:

```yaml
---
module: sds-master        # идентификатор; без поля — имя папки
description: Хранение данных сессии in-memory, жизненный цикл сессии, репликация
domains: [session-lifecycle, session-data, replication]   # папки из openspec/specs/
code_paths: [sds-master/src/main/java, sds-master-api]
depends_on: [sds-router]  # модули, чей контекст нужен вместе с этим
max_tokens: 20000         # необязательно: бюджет набора контекста модуля
---
```

Связь модуль ↔ домен — **многие-ко-многим**: модуль перечисляет свои домены,
а у домена видны все модули, которые его перечислили. Домен — путь спеки
относительно `openspec/specs/` (вложенный тоже: `identity/auth`). ADR ссылается
на модули и домены полями `modules` и `domains`, заголовок берётся из поля
`title` или из `# …`:

```yaml
---
status: accepted
modules: [sds-master, sds-impl]
domains: [replication]
---
# ADR-001: Синхронная репликация данных сессии
```

**Раздел «Контекст»** (команда «OpenSpec: Карта контекста»):

- **граф** — колонки ADR → модули → домены, дуги `depends_on` слева от
  модулей. Наведение или выбор узла подсвечивает его связи; ненайденные
  домены и модули — красным пунктиром, рёбра цикла зависимостей — красным;
- **матрица** модули × домены с числом модулей у каждого домена — домен без
  модулей виден сразу;
- **карточка узла** — описание, файлы, домены, зависимости и зависимые модули,
  ADR, пути кода. Для модуля — **набор контекста**: общий контекст, `context.md`
  модуля и транзитивно его зависимостей, спеки их доменов и ADR. «Копировать
  пути» кладёт его в буфер строками `@путь` — в таком виде его принимает агент в
  терминале;
- **набор контекста из нескольких узлов** — кнопка «Набор контекста» включает
  режим, в котором щелчок по модулю, домену или ADR на графе (по строке или
  столбцу матрицы) добавляет узел в набор, повторный щелчок убирает. Без режима
  то же делает Ctrl+щелчок (⌘ на macOS), а в карточке узла — кнопка «В набор».
  Панель набора собирает общий контекст, `context.md` выбранных модулей, спеки
  их доменов и выбранных доменов, ADR этих модулей и доменов и выбранные ADR —
  каждый файл один раз. Флажки отключают зависимости модулей по `depends_on` и
  спеки доменов модулей — тогда в набор идут только явно выбранные домены. Узлы
  вне набора на графе приглушены; набор запоминается в окне.

**Замечания** — в разделе и в панели «Проблемы» VS Code, на строке поля:

| Замечание | Уровень |
| --- | --- |
| домен из `domains` не найден в `openspec/specs/` | ошибка |
| модуль из `depends_on` или из ADR не описан | ошибка |
| зависимость от себя, цикл зависимостей | ошибка |
| два модуля с одним `module` | ошибка |
| нет `index.md`, frontmatter не разбирается или поле не того типа | ошибка |
| нет `context.md` | предупреждение |
| путь из `code_paths` не найден (шаблон проверяется до первого `*` или `...`) | предупреждение |
| домен не относится ни к одному модулю | предупреждение |

Раскладку папок можно закрепить в `openspec/structure.yaml`:

```yaml
structure:
  openspec:
    context:
      "*.md": file
      modules:
        "*":
          index.md: file
          context.md: file
      adr?:
        "*.md": file
```

## Контроль контекста

Связи между модулями, доменами и ADR — только половина дела: агенту вредит и
контекст, который слишком велик, повторяется или описывает код, которого уже
нет. Вид **«Контроль»** раздела «Контекст» (кнопка рядом с «Граф» и
«Матрица») собирает это в три блока.

**Объём.** Каждый файл контекста — общий контекст, `context.md` модулей,
спеки доменов, ADR — с числом строк и оценкой токенов, от самого тяжёлого;
ниже — наборы модулей с суммой и бюджетом. Оценка — эвристика без токенизатора
модели: 4 символа латиницы или 2,5 символа кириллицы на токен, точность
около ±25 %, поэтому везде со знаком ≈. Та же оценка — в сводке раздела, в
карточке модуля и у каждого файла набора контекста. Бюджет набора модуля
задаётся полем `max_tokens` в `index.md`.

**Лишнее.**

- Повторы — абзацы от 80 символов, которые дословно (с точностью до пробелов
  и регистра) встречаются в общем контексте, `context.md` и ADR больше одного
  раза. Замечание ставится на каждый повтор со ссылкой на первое вхождение в
  порядке набора. Заголовки и блоки кода не сравниваются, спеки — тоже:
  повторяющиеся формулировки сценариев в них — норма.
- Пустой `context.md` — только заголовки и комментарии.
- Файлы вне наборов — всё в `openspec/context/`, что не общий `*.md`, не
  `index.md`/`context.md` модуля и не ADR: например, `notes.md` рядом с
  `index.md`. Агент их не увидит.
- Недействующие ADR — со статусом `superseded`, `deprecated`, `rejected`,
  `obsolete`, `withdrawn` или «заменён», «отменён», «отклонён», «устарел»
  (смотрится первое слово: `superseded by ADR-007` тоже). Такие ADR **не
  входят в набор** модулей и доменов: панель набора называет их, а флажок
  «недействующие ADR» возвращает. Явно выбранный ADR входит всегда.

**Связь с реальностью.**

- Пути в тексте общего контекста, `context.md` и ADR: цели ссылок
  `[текст](путь)` и пути в `` `коде` `` со слешем, оканчивающиеся расширением
  или `/` (`src/Session.java`, `packages/core/`, `` `a/b.ts:42` `` — номер строки
  отбрасывается). Путь ищется от файла, от корня проекта и от каждого пути
  `code_paths` модуля — так в `context.md` можно писать `main/App.java`
  вместо полного пути. Внешние адреса, якоря, абсолютные пути
  (`/api/...`), шаблоны (`<папка>`, `*`) и блоки кода не проверяются.
- Отставание от кода — по git: сколько коммитов в путях кода модуля сделано
  после последнего коммита его `context.md`. Незакоммиченная правка
  `context.md` считается свежей. Это сведение, а не предупреждение: решать,
  устарело ли описание, человеку. Без git проверка молчит.
- Модуль без `code_paths` — сведение: ни пути, ни отставание проверить не от
  чего.

Новые замечания — в списке раздела, в панели «Проблемы» VS Code (сведения —
уровнем Information) и в проверке `context` команды `openspec-ide-check`;
сведения не роняют проверку при пороге по умолчанию `--fail-on error`.

| Замечание | Уровень |
| --- | --- |
| файл контекста больше 8000 токенов | предупреждение |
| набор модуля больше `max_tokens` (на строке поля) | предупреждение |
| `max_tokens` — не положительное целое | ошибка |
| абзац повторяет другой (на строке повтора) | предупреждение |
| `context.md` пуст | предупреждение |
| файл в `openspec/context/` не входит ни в один набор | предупреждение |
| путь из текста не найден (на строке ссылки) | предупреждение |
| контекст модуля отстаёт от кода на N коммитов | сведение |
| у модуля нет `code_paths` | сведение |

## Разработка

```bash
npm ci
npm run build      # core, server, интерфейс и бандл расширения
npm run verify     # typecheck + lint + модульные и дымовые тесты (Vitest)
npm run package    # .vsix в packages/vscode/dist/
npm run check:openspec   # проверка самого репозитория, как в CI
```

**Отладка расширения.** Откройте репозиторий в VS Code и запустите конфигурацию
«Расширение OpenSpec IDE» (F5): соберётся расширение и откроется окно Extension
Development Host на фикстуре `tests/fixtures/full-change`.

**Интерфейс в браузере.** Разделы панели — это React-приложение, которое можно
разрабатывать в браузере с горячей перезагрузкой. Бэкенд для этого поднимается в
HTTP-режиме на loopback с токеном сессии — это средство разработки, а не способ
пользоваться IDE:

```bash
npm run build && npm run dev   # бэкенд на этом репозитории + Vite
npm run test:e2e               # сквозные тесты интерфейса в Chromium (Playwright)
```

Для e2e нужен Chromium. Если браузеры Playwright не скачаны, укажите свой:
`CHROMIUM_PATH=/path/to/chrome npm run test:e2e`.

**Как проверяется расширение.** Модульные тесты покрывают модель дерева,
раскладку замечаний по файлам, разметку панели с CSP, мост сообщений и выбор
корня. Дымовой тест `packages/vscode/src/smoke.test.ts` собирает тот же бандл,
что уходит в `.vsix`, загружает его с подменённым модулем `vscode` и проходит
активацию, дерево, создание артефакта, панель, валидацию, создание и архивацию
change на фикстурах. Поведение в настоящем окне VS Code (раскладка, фокус, меню)
проверяется вручную.

```
packages/
  core/      чистая логика без Node API: разбор артефактов, доска, метрики,
             правила SDD, структура папок, карта контекста, протокол панели
             (проверяется тестом purity)
  server/    Fastify, обёртка над CLI OpenSpec, наблюдение за файлами,
             метрики, реестр схем, карта контекста; встраиваемый бэкенд без
             сокета для расширения
  web/       React-интерфейс разделов: панель VS Code и HTTP-режим разработки
  vscode/    расширение: дерево, диагностика, языковые функции, команды,
             панель, сборка .vsix
  check/     команда openspec-ide-check для CI: сборка одним файлом
scripts/     HTTP-режим бэкенда и dev-сервер для разработки интерфейса
tests/
  fixtures/  фикстурные OpenSpec-проекты для тестов
  e2e/       сквозные тесты интерфейса
openspec/    требования и план самой IDE
docs/        макеты
```

Работа ведётся по OpenSpec: у каждой задачи в `tasks.md` есть критерий приёмки,
после каждой группы прогоняется `npm run verify`.

```bash
npx openspec status --change add-vscode-extension
npx openspec validate add-vscode-extension --strict
```

## Состояние

Первые три change реализованы и заархивированы, их требования перенесены в
основные спеки [`openspec/specs/`](openspec/specs/):

- [`add-openspec-ide`](openspec/changes/archive/2026-09-24-add-openspec-ide/tasks.md) —
  исходный план IDE;
- [`add-vscode-extension`](openspec/changes/archive/2026-09-24-add-vscode-extension/tasks.md) —
  переезд в расширение VS Code;
- [`rework-board-archive-preview`](openspec/changes/archive/2026-09-24-rework-board-archive-preview/tasks.md) —
  доска в VS Code и предпросмотр архивации. Макеты — экраны «Доска» и
  «Архивация» в [`docs/mockups/openspec-ide.html`](docs/mockups/openspec-ide.html).

Реализованы, но ещё не заархивированы:

- [`add-structure-conformance`](openspec/changes/add-structure-conformance/tasks.md) —
  проверка структуры папок;
- [`fix-cli-discovery`](openspec/changes/fix-cli-discovery/tasks.md) — поиск CLI
  OpenSpec вне PATH редактора;
- [`focus-context-map`](openspec/changes/focus-context-map/proposal.md) — карта
  контекста модулей, доменов и ADR вместо запуска агента из IDE;
- [`redesign-panel-ui`](openspec/changes/redesign-panel-ui/proposal.md) — новый
  интерфейс панели: вкладки разделов, палитра Ctrl+K, нить change, трассировка
  сценариев. Макеты — [`docs/mockups/panel-redesign.html`](docs/mockups/panel-redesign.html);
- [`validate-main-specs`](openspec/changes/validate-main-specs/proposal.md) —
  проверка основных спеков и строки замечаний по имени требования;
- [`add-spec-authoring`](openspec/changes/add-spec-authoring/proposal.md) —
  помощь при написании спеков, дельт и плана в редакторе;
- [`add-change-drift`](openspec/changes/add-change-drift/proposal.md) —
  пересечения changes, устаревшие дельты, забытые changes и пакетная архивация;
- [`add-conformance-check`](openspec/changes/add-conformance-check/proposal.md) —
  команда `openspec-ide-check` для CI и pre-commit;
- [`add-context-control`](openspec/changes/add-context-control/proposal.md) —
  контроль контекста: объём в токенах и бюджет, повторы и лишние файлы,
  пути в тексте и отставание контекста от кода.

`focus-context-map` и `redesign-panel-ui` оба изменяют требование «Панель
деталей change» спека `workflow-board` — это пересечение показывает и сама IDE:
при архивации второго из них дельту нужно свести с правками первого.
