# Договорённости

## Язык

- Пользовательские строки, комментарии в коде, сообщения коммитов, спеки и
  документация — на русском. Идентификаторы, пути и код — на английском.
- Нормативные формулировки спеков — ДОЛЖЕН/ДОЛЖНА (SHALL); у каждого
  требования есть сценарий с WHEN/THEN. Решение в design сопровождается
  рассмотренной альтернативой, пункт плана — метрикой приёмки.

## Процесс

- Любая заметная возможность начинается с change: proposal, дельта спека,
  design, tasks; затем реализация и `openspec validate <change> --strict`.
- Пункт плана ссылается на сценарий строкой `↳ <capability> / <сценарий>` —
  так трассировка и проверка `coverage` видят покрытие.
- Conventional commits: `feat(context): …`, `fix(cli): …`, `docs(openspec): …`.

## Код

- Обращение к CLI OpenSpec — только через обёртку `packages/server/src/openspec/`
  с JSON-выводом; git — через `execFile` без оболочки
  (`packages/server/src/git.ts`). Прямых `execSync` из интерфейса нет.
- Логика и правила — чистыми функциями в `core`, ввод-вывод — в `server`,
  провайдеры VS Code — тонкие обёртки над моделью.
- Замечание всегда несёт файл и строку (с 1): панель «Проблемы», раздел и CI
  показывают одно и то же место.
- Новое поле или маршрут, нужные интерфейсу, поднимают `API_REVISION` в
  `packages/core/src/constants.ts`.

## Проверка

- `npm run verify` — typecheck, eslint, Vitest; `npm run test:e2e` — сборка и
  Playwright поверх фикстур `tests/fixtures/`.
- Тесты пишут в копию фикстуры, сама фикстура в репозитории не меняется.
- `npm run check:openspec` — проверка самого репозитория, как в CI.
