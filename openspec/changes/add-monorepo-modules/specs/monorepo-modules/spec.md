# Spec Delta: monorepo-modules

## Purpose

Даёт IDE знание о модулях монорепозитория — сервисах, UI и библиотеках, чьи
спеки ведутся в одном корневом `openspec/`. Работу можно смотреть по модулю,
видеть зависимости между модулями и затронутых потребителей, вести сквозные
changes.

## ADDED Requirements

### Requirement: Карта модулей

Система ДОЛЖНА (SHALL) читать карту модулей из файла `openspec/modules.yaml`. Для
каждого модуля карта задаёт идентификатор, название, вид (сервис, UI или
библиотека), каталог кода относительно корня, префикс путей capability,
необязательную группу и список модулей, от которых он зависит. Карта ДОЛЖНА
проверяться при чтении, а ошибки — показываться с указанием модуля и поля.

#### Scenario: Корректная карта

- **WHEN** в репозитории есть корректный `openspec/modules.yaml`
- **THEN** IDE показывает модули, сгруппированные по группам и видам

#### Scenario: Ошибки в карте

- **WHEN** модуль зависит от неизвестного модуля, каталог кода не существует или префиксы двух модулей совпадают
- **THEN** ошибка показывается с идентификатором модуля и полем
- **AND** остальные модули работают

#### Scenario: Карты нет

- **WHEN** в репозитории нет `openspec/modules.yaml`
- **THEN** все разделы работают без группировки по модулям
- **AND** предлагается обнаружить модули автоматически

### Requirement: Обнаружение модулей

Система ДОЛЖНА (SHALL) находить модули по манифестам сборки — `package.json`,
`pom.xml`, `build.gradle` и `build.gradle.kts`, `go.mod`, `*.csproj`,
`pyproject.toml` — и зависимости между найденными модулями по ссылкам внутри
репозитория. Каталоги зависимостей и сборки (`node_modules`, `target`, `build`,
`dist`, `.git`) ДОЛЖНЫ пропускаться. Результат ДОЛЖЕН предлагаться как черновик
карты и сохраняться только после подтверждения пользователем.

#### Scenario: Монорепо на npm workspaces

- **WHEN** репозиторий содержит пакеты `services/*`, `ui` и `km/*` с `package.json`, и сервисы зависят от пакетов КМ
- **THEN** черновик содержит модуль на каждый пакет с каталогом кода
- **AND** зависимости сервисов от библиотек КМ перенесены в черновик

#### Scenario: Многомодульный Maven или Gradle

- **WHEN** модули описаны в `pom.xml` или `build.gradle`, а зависимости заданы между ними
- **THEN** черновик содержит эти модули и зависимости между ними

#### Scenario: Правка черновика

- **WHEN** пользователь меняет в черновике вид, название, префикс спеков или группу модуля либо убирает лишний модуль
- **THEN** изменения попадают в сохраняемый `openspec/modules.yaml`

#### Scenario: Карта уже есть

- **WHEN** обнаружение запускается при существующей карте
- **THEN** черновик показывает только новые модули и изменения зависимостей относительно карты
- **AND** существующие правки пользователя не перезаписываются без подтверждения

### Requirement: Принадлежность спеков и changes модулям

Система ДОЛЖНА (SHALL) относить capability к модулю с самым длинным совпадающим
префиксом пути, а change — ко всем модулям его дельт и к модулям, перечисленным
в ключе `modules` его `.openspec.yaml`. Capability, не попавшая ни в один
модуль, ДОЛЖНА показываться в группе «вне модулей».

#### Scenario: Вложенный префикс

- **WHEN** есть модули с префиксами `km` и `km/core`, а capability — `km/core/cache`
- **THEN** capability относится к модулю с префиксом `km/core`

#### Scenario: Change с дельтами в двух модулях

- **WHEN** change содержит дельты `billing/invoices` и `km/core/cache`
- **THEN** change относится к обоим модулям и помечен как сквозной

#### Scenario: Change без дельт

- **WHEN** change ещё не содержит дельт, но в его `.openspec.yaml` перечислены модули
- **THEN** change относится к перечисленным модулям

#### Scenario: Capability вне модулей

- **WHEN** путь capability не начинается ни с одного префикса модулей
- **THEN** она показывается в группе «вне модулей» и не пропадает из дерева

### Requirement: Представление по модулям

Система ДОЛЖНА (SHALL) группировать дерево рабочего пространства по модулям и давать
фильтр по одному или нескольким модулям на доске, в поиске и в метриках.
Выбранный фильтр ДОЛЖЕН сохраняться при переключении разделов.

#### Scenario: Дерево по модулям

- **WHEN** карта модулей задана
- **THEN** дерево показывает группы и модули, а под каждым модулем — его changes и спеки
- **AND** сквозной change виден под каждым из своих модулей с отметкой «сквозной»

#### Scenario: Фильтр доски

- **WHEN** пользователь выбирает на доске модуль `billing`
- **THEN** на доске остаются changes, относящиеся к `billing`, включая сквозные
- **AND** на каждой карточке показаны модули change

#### Scenario: Поиск в модуле

- **WHEN** пользователь ищет с фильтром по модулю
- **THEN** результаты ограничены спеками и changes этого модуля

#### Scenario: Метрики по модулям

- **WHEN** пользователь открывает сводку метрик с фильтром по модулю
- **THEN** сводка считается по changes выбранных модулей

### Requirement: Граф модулей и затронутые потребители

Система ДОЛЖНА (SHALL) показывать граф модулей с рёбрами зависимостей и активными
changes каждого модуля. Для change ДОЛЖНЫ быть показаны затронутые потребители —
модули, которые зависят от его модулей напрямую или через цепочку
зависимостей.

#### Scenario: Change в библиотеке

- **WHEN** change относится к библиотеке `km/core`, от которой зависят `billing` и `ui`, а от `billing` — `reports`
- **THEN** затронутыми потребителями change показаны `billing`, `ui` и `reports`
- **AND** на графе эти модули выделены, прямые и транзитивные потребители различимы

#### Scenario: Выбор модуля на графе

- **WHEN** пользователь выбирает модуль на графе
- **THEN** показаны его зависимости, его потребители, его активные changes и число спеков

#### Scenario: Цикл зависимостей

- **WHEN** в карте модулей есть цикл зависимостей
- **THEN** граф строится, цикл показывается как ошибка карты с перечнем модулей цикла

### Requirement: Сквозные changes

Система ДОЛЖНА (SHALL) позволять при создании change выбрать один или несколько
модулей, записывая их в `.openspec.yaml` change, и при добавлении дельты
предлагать пути capability внутри выбранных модулей. Детали change ДОЛЖНЫ
группировать дельты по модулям.

#### Scenario: Создание сквозного change

- **WHEN** пользователь создаёт change и выбирает модули `km/core` и `billing`
- **THEN** change создаётся командой CLI, а в его `.openspec.yaml` записан ключ `modules` с этими модулями
- **AND** остальное содержимое `.openspec.yaml` не меняется

#### Scenario: Добавление дельты

- **WHEN** пользователь добавляет в сквозной change дельту спека
- **THEN** путь capability предлагается начать с префикса одного из модулей change

#### Scenario: Дельты по модулям

- **WHEN** пользователь открывает дельты сквозного change
- **THEN** требования сгруппированы по модулям, к которым относятся их capability
