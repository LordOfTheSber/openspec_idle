# Design: модули монорепозитория

## Context

Спеки монорепо ведутся в одном корневом `openspec/`, capability сгруппированы
по модулям путями. CLI OpenSpec вложенные пути поддерживает: `openspec list
--specs` отдаёт `km/core/cache`, архивация переносит дельты по таким путям.
Понятия «модуль» у OpenSpec нет — это знание о репозитории, которое IDE
добавляет поверх.

Проверено на CLI 1.13.1: лишний файл `openspec/modules.yaml` и ключ `modules` в
`.openspec.yaml` change не мешают `list`, `status`, `validate` и `archive`.

## Goals / Non-Goals

### Goals

- Карта модулей общая для команды и живёт в git рядом со спеками.
- Без карты IDE работает как раньше.
- Затронутые потребители считаются по явным зависимостям модулей, а не по
  догадкам о коде.

### Non-Goals

- Разбор импортов в исходном коде. Зависимости берутся из манифестов сборки и
  карты.
- Несколько каталогов `openspec/` в одном репозитории. Выбранная раскладка — один
  корневой.
- Сборка и запуск модулей из IDE.

## Decisions

### 1. Карта — отдельный файл `openspec/modules.yaml`

**Решение.** Файл рядом с `config.yaml`:

```yaml
version: 1
modules:
  - id: billing
    title: Биллинг
    kind: service          # service | ui | library
    path: services/billing # каталог кода от корня репозитория
    specs: billing         # префикс путей capability
    group: Сервисы
    dependsOn: [km/core, km/auth]
  - id: km/core
    title: КМ Core
    kind: library
    path: km/core
    specs: km/core
    group: КМ
```

**Почему не в `config.yaml`.** Его формат определяет OpenSpec, и неизвестный
ключ может стать ошибкой в следующей версии CLI. Отдельный файл CLI не
читает, и совместимость от него не зависит.

**Почему не в `.openspec-ide/`.** Там локальные данные разработчика вне git, а
карта модулей — знание команды о репозитории: её правят в пулл-реквестах, как
спеки.

### 2. Принадлежность — по префиксу пути capability, самый длинный побеждает

**Решение.** `specs` модуля — префикс по сегментам пути. `km/core/cache`
относится к `km/core`, а не к `km`, даже если заданы оба. Сравнение идёт по
целым сегментам: `km/core` не захватывает `km/core-legacy`.

**Альтернатива** — список capability в каждом модуле. Он устаревает при
каждой новой capability; префикс работает сам.

### 3. Модули change — дельты плюс явный список

**Решение.** Модули change — объединение модулей его дельт и ключа `modules`
в `.openspec.yaml`. Список пишется при создании change, когда дельт ещё нет.

**Почему не только дельты.** Сквозной change начинается с proposal. Пока нет
дельт, он был бы «без модуля» и выпадал бы из фильтра сервиса, которому
адресован.

### 4. Обнаружение — черновик, а не запись

**Решение.** Сканер обходит репозиторий, пропуская каталоги зависимостей и
сборки и учитывая `.gitignore`, распознаёт манифесты и строит черновик карты с
зависимостями между найденными модулями:

| Манифест | Модуль | Зависимость |
| --- | --- | --- |
| `package.json` | `name` | `dependencies` и `devDependencies` на имя другого пакета репозитория |
| `pom.xml` | `artifactId` | `<dependency>` с `groupId:artifactId` другого модуля |
| `build.gradle(.kts)` | путь проекта | `project(':x')` |
| `go.mod` | `module` | `require` другого модуля репозитория или `replace` на путь внутри |
| `*.csproj` | имя проекта | `<ProjectReference>` |
| `pyproject.toml` | `name` | зависимость на имя другого пакета репозитория |

Вид модуля угадывается (фронтенд-зависимости → UI, нет точки запуска →
библиотека, иначе сервис), префикс спеков — из каталога. Пользователь
проверяет черновик и сохраняет.

**Почему не писать сразу.** Угадывание вида и префикса ошибается, а карта
общая для команды: молча записанная неверная карта хуже её отсутствия.

### 5. Затронутые потребители — обратный обход графа

**Решение.** Граф `dependsOn` разворачивается. Потребители change — модули,
достижимые обратными рёбрами от модулей change, с глубиной: 1 — прямой
потребитель, больше — транзитивный. Цикл не зацикливает обход (посещённые не
повторяются) и отдельно показывается как ошибка карты.

### 6. Модули — поле в существующих ответах API, фильтр — на клиенте

**Решение.** Дерево, доска и поиск получают у каждого change и capability поле
`modules`. Фильтр применяется в интерфейсе. Сводка метрик по модулю считается
на сервере, потому что сводит несколько changes.

**Альтернатива** — параметр `module` во всех запросах. Это умножает запросы при
смене фильтра, а данных в ответах немного: сотни changes и спеков.

## Risks / Trade-offs

- **Карта расходится с кодом.** Появился сервис, а карту не обновили. Смягчение:
  повторное обнаружение показывает только расхождения с картой.
- **Большой репозиторий.** Обход тысяч каталогов при обнаружении. Смягчение:
  обнаружение только по запросу, с пропуском игнорируемых каталогов; в обычной
  работе IDE следит только за `openspec/`.

## Migration Plan

Без карты ничего не меняется. Карта заводится обнаружением или вручную и
коммитится.
