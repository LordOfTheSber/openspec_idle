# Design: помощь при написании спеков и плана в редакторе

## Context

Мотивация — в `proposal.md`. В `core` уже есть разбор спеков
(`parseSpecMarkdown`), блоков требований (`requirementBlocks`), дельт
(`buildDeltaView`) и ссылок плана (`planReferences`, `buildTrace`). Языковых
функций у расширения нет: только коллекции диагностик.

## Decisions

### 1. Логика — в `core`, провайдеры VS Code — тонкие

**Решение.** Все ответы (символы, дополнения, исправления, наведение,
переходы, подсказки, проверки) считает чистый модуль
`packages/core/src/authoring.ts` по набору источников
`{ mainSpecs, changes: [{ deltas, plan }] }` и тексту текущего документа.
Провайдеры в `packages/vscode/src/authoring.ts` переводят позиции и вызывают
его.

**Альтернатива — Language Server (LSP) отдельным процессом.** Дал бы
поддержку других редакторов, но требует протокола, отдельной сборки и
процесса; расширение уже держит бэкенд в своём процессе, а другие редакторы
в планах нет.

**Альтернатива — логика прямо в провайдерах.** Не тестируется без VS Code,
и команда проверки для CI не смогла бы переиспользовать проверки ссылок.

### 2. Источники — из бэкенда, текущий документ — из редактора

**Решение.** `GET /api/authoring` отдаёт тексты основных спеков, дельт и
отслеживаемых артефактов активных changes (какие файлы дельты и какой план —
определяет схема change через дерево рабочего пространства). Расширение
держит копию и перечитывает её по событию `workspace-changed`. Текст
открытого документа всегда берётся из буфера редактора: подсказки и
проверки видят несохранённые правки.

**Альтернатива — читать файлы в расширении напрямую.** Пришлось бы
повторить в расширении определение файлов дельт и плана по схеме, которое
уже есть в бэкенде.

### 3. Какие файлы обслуживаются

**Решение.** Документ относится к OpenSpec, если его путь совпадает с
основным спеком `openspec/specs/**/spec.md`, с файлом дельты или с
отслеживаемым артефактом активного change из источников. Для VS Code
селектор — `{ scheme: 'file', pattern: '**/openspec/**/*.md' }`, а сам
документ уточняется по источникам: `proposal.md` и `design.md` ответов не
получают.

### 4. Проверки ссылок — свои, а не только CLI

**Решение.** Отсутствующее требование для MODIFIED/REMOVED/RENAMED и
существующее для ADDED — ошибки (архивация откажет), потерянные сценарии
MODIFIED — ошибка, неразрешённая ссылка плана — предупреждение. Считаются по
буферу при каждой правке с задержкой 300 мс и по источникам при их
обновлении; коллекция диагностик `openspec-authoring`.

**Альтернатива — положиться на `openspec validate`.** CLI сообщает только
первую неудачу архивации, уровнем INFO и без строки, и только после
сохранения.

### 5. Копирование требования из основного спека

**Решение.** Исправление заменяет строки блока MODIFIED от строки после
заголовка до следующего заголовка требования или секции на тело блока
основного спека (`requirementBlocks`), заголовок не трогает. Правки дельты,
уже сделанные в этом блоке, пропадут — поэтому действие предлагается как
отдельное, а не применяется само, и отменяется обычной отменой редактора.

**Альтернатива — дописывать только недостающие сценарии.** Бережнее к
правкам, но не решает главный случай — «начать MODIFIED с текущего текста»,
а слияние описаний без трёхстороннего сравнения ненадёжно.

### 6. Подсказки над строками — через существующие действия

**Решение.** CodeLens «Основной спек» открывает файл на строке требования;
«Не покрыт планом — добавить пункт» вызывает `POST /api/trace/item` (как
вкладка «Трассировка»); «Пунктов плана: N» открывает план на первом пункте.

## Risks / Trade-offs

- Копия источников может отставать от диска на время обработки события →
  текущий документ всегда из буфера, остальное обновляется за доли секунды.
- Большие проекты: источники — это тексты всех спеков → размер ответа растёт
  линейно; для сотен спеков это единицы мегабайт внутри процесса, без сети.
