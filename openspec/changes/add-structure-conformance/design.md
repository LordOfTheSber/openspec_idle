# Design: проверка структуры папок контекста и спецификаций

## Context

Мотивация — в `proposal.md`, требования — в дельтах `specs/`. У OpenSpec нет
понятия структуры папок проекта сверх `openspec/specs` и `openspec/changes`,
поэтому это собственная возможность IDE; CLI OpenSpec в ней не участвует.

## Decisions

### 1. Описание — YAML-дерево в `openspec/structure.yaml`

**Решение.** Описание — одно YAML-дерево от корня проекта, где ключ — имя
элемента, а значение — правило:

```yaml
version: 1
ignore: [".DS_Store", "Thumbs.db", ".gitkeep"]   # необязательно, это умолчание
structure:
  openspec:                 # строгая папка
    config.yaml: file
    structure.yaml: file
    specs: "*"              # жёстко до specs/, внутри — что угодно
    changes: "*"
    schemas?: "*"           # необязательная папка
  docs:
    context:
      README.md: file
      "*.md": file          # сколько угодно .md, и ничего больше
      adr: "*"
```

Дерево повторяет то, что человек видит в проводнике, поэтому читается без
документации и ревьюится в том же PR, что и перенос папок. Файл лежит в
`openspec/`, потому что структура — договорённость команды, как и
`config.yaml`, а не локальная настройка IDE из `.openspec-ide/`.

**Альтернатива — список путей-глобов** (`docs/context/**`,
`!docs/context/tmp`). Короче для простых случаев, но жёсткость «с точностью
до папки и файла» выражается отрицаниями и порядком правил, а ошибку в таком
списке трудно увидеть глазами.

**Альтернатива — JSON Schema для дерева файлов.** Стандарт, но для структуры
каталогов громоздок и непривычен тем, кто будет его править.

### 2. Семантика правил

- Строгая папка (вложенный перечень): каждый обязательный элемент должен быть,
  всё не описанное — лишнее. Пустой перечень `{}` — папка, которая должна быть
  пустой.
- `"*"` — папка с любым содержимым: её содержимое не обходится.
- `any` — элемент любого типа с любым содержимым.
- `?` в конце имени — необязательный элемент.
- Ключ со звёздочкой — шаблон: `*` соответствует любой последовательности
  символов, кроме `/`. Шаблон всегда необязателен (ноль совпадений допустим),
  поэтому `?` к нему — ошибка описания. Точное имя важнее шаблона; из
  нескольких шаблонов действует первый подходящий в порядке описания.
- Корень проекта не строгий: иначе описание пришлось бы дополнять каждым
  `src/`, `package.json` и прочим, к контексту и спекам не относящимся.
- Сравнение имён — с учётом регистра, как в git.

**Альтернатива — строгий корень.** Одно правило вместо исключения, но
описание превращается в перечень всего репозитория.

### 3. Проверка — чистая функция `core` с подставляемым чтением каталогов

`checkStructure(spec, readDir)` получает функцию чтения каталога и обходит
только то, что требует описание: строгие папки перечисляются, свободные — нет.
Файловая система, символические ссылки и Windows-пути остаются в `server`;
`core` проверяется тестами на таблице каталогов в памяти.

Результат — список нарушений и дерево описания с отметками для интерфейса. У
каждого нарушения есть путь, вид, ожидаемый и фактический тип и строка правила
в `structure.yaml`: для «нет элемента» и «не тот тип» — строка его ключа, для
«лишнего» — строка ключа родительской папки.

### 4. Номера строк — из разбора `yaml` с `LineCounter`

Сервер разбирает описание `parseDocument` с `LineCounter` и передаёт в `core`
обычное значение и функцию «путь ключа → строка». Так же уже устроен разбор
схем в `schemaRegistry`.

### 5. Когда проверять

- Сервер: по запросу `GET /api/structure`. Наблюдатель за файлами, кроме
  `openspec/`, следит за папками верхнего уровня из описания — они
  определяются при запуске бэкенда; новая папка верхнего уровня начнёт
  отслеживаться после перезапуска.
- Панель: при открытии раздела, по кнопке и по событию изменения файлов.
- VS Code: при активации, по событию изменения файлов от бэкенда, по
  созданию и удалению любых файлов рабочей области (с задержкой 500 мс) и по
  команде.

### 6. Диагностика в VS Code

Лишний файл получает диагностику на самом файле: в панели «Проблемы» он
виден под своим именем и открывается щелчком. Всё остальное — нет элемента,
не тот тип, лишняя папка (на папку диагностику не повесить) и ошибки описания —
ложится на строку правила в `openspec/structure.yaml`. Перевод нарушений в
диагностики — чистая функция, проверяемая без VS Code.

## Risks / Trade-offs

- **Большая свободная папка** не замедляет проверку: её содержимое не
  обходится. Большая строгая папка обходится целиком — это и есть проверка.
- **Регистр имён на Windows и macOS**: файловая система может не различать
  `README.md` и `readme.md`, а проверка различает — так же поступит git на
  Linux-сборке, и это предпочтительнее молчаливого расхождения.
