# Design: пересечения, устаревшие дельты и забытые changes

## Context

Мотивация — в `proposal.md`. Имена требований всех активных дельт уже
собирает карта связей (`buildCapabilityMap`), но только до уровня capability.
Разбор блоков требований есть в `specChange.ts`. У OpenSpec нет истории:
`.openspec.yaml` хранит только дату создания change (день), и то не у всех
changes. История есть у git.

## Decisions

### 1. Пересечение — по имени требования и capability

**Решение.** Затронутое требование — пара (capability, имя) для MODIFIED,
REMOVED, RENAMED FROM и ADDED; имена сравниваются как при архивации CLI —
точно, после обрезки пробелов по краям. Пересечение — два и более change на одной паре.
Вычисляется чисто в `core` по тем же источникам, что и функции редактора
(`/api/authoring`).

**Альтернатива — пересечение по capability.** Уже есть в «Дельтах» и
слишком грубое: два change, добавляющие разные требования в одну capability,
не конфликтуют.

### 2. Базовая версия требования — из git

**Решение.** Базовая версия — основной спек в первом коммите, где появился
файл дельты (`git log --diff-filter=A --format=%H -- <дельта>`, последний
результат), затем `git show <коммит>:openspec/specs/<cap>/spec.md`. Блоки
требования (базовый и текущий) сравниваются по тексту; разные — дельта
устарела, изменённые, добавленные и удалённые сценарии перечисляются. Дельта,
ещё не закоммиченная, написана по текущему спеку — не устарела.

**Альтернатива — хранить снимок спека в `.openspec-ide/` при создании
change.** Работает без git, но снимка нет у changes, созданных вне IDE, и он
не переживает клон репозитория другим членом команды.

**Альтернатива — дата `.openspec.yaml`.** День — слишком грубо: change,
созданный и архивированный в один день с другим, неразличим; и поле есть не
у всех changes. Используется только как запасной путь без git: архивные
changes с датой не раньше создания, менявшие то же требование, дают
отметку «возможно устарела».

### 3. Активность и дата создания

**Решение.** Последняя активность change — дата последнего коммита его
каталога; если в каталоге есть незакоммиченные правки — сейчас; без git —
время изменения файлов из дерева. Дата создания — `created` из
`.openspec.yaml`, иначе первый коммит каталога, иначе неизвестна (такие
changes архивируются в пакете последними, по имени). Порог «забыт» — 3 дня.

**Альтернатива — время изменения файлов.** После `git clone` оно равно
времени клона, и забытый месяц назад change выглядел бы свежим.

### 4. Git — через `execFile`, без оболочки, с кэшем

**Решение.** Вызовы `git` с аргументами-массивом в корне проекта; ответы
кэшируются до события изменения файлов. Нет git или каталог не репозиторий —
`git: false` в ответе, проверки работают по запасным путям.

### 5. Пакетная архивация — последовательно, с предпросмотром каждого

**Решение.** Команда VS Code: мультивыбор из changes «Готово к архивации»,
порядок — по дате создания. Перед каждым — предпросмотр архивации на
временной копии; отказ CLI (в том числе вызванный архивацией предыдущего
change пакета) — change пропускается с причиной. Одно подтверждение на весь
пакет со списком и порядком.

**Альтернатива — `openspec archive` подряд без предпросмотра.** Первая же
неудача оставила бы пакет наполовину выполненным без объяснения.

## Risks / Trade-offs

- Переименование файла дельты в git (`--diff-filter=A` не видит rename как
  добавление) → базовой версией станет коммит переименования; это даёт лишь
  более позднюю базу, ложных «устарела» не добавляет.
- Большая история → по одному вызову `git log` на файл дельты и на каталог
  change, результаты кэшируются.
