# Design: карта контекста модулей

## Context

Мотивация — в `proposal.md`, требования — в дельтах `specs/`. У OpenSpec нет
понятия модуля и контекста, поэтому это собственная возможность IDE; CLI
OpenSpec в ней не участвует — карта строится по файлам.

## Decisions

### 1. Связь модуля с доменами записана в модуле

**Решение.** Модуль перечисляет свои домены в поле `domains` frontmatter
`index.md`. Домен — путь спеки относительно `openspec/specs/` (допускаются и
вложенные пути вида `identity/auth`, и полный путь до `spec.md` — он
приводится к имени папки). Обратная сторона связи (какие модули у домена)
вычисляется.

**Альтернатива — поле `modules` в каждой спеке.** Спеки принадлежат OpenSpec
и переписываются при архивации: собственное поле в них потерялось бы или
мешало бы CLI. Отдельный файл связей (`openspec/context/links.yaml`) — ещё один
источник истины, который расходится с модулями при переименовании.

### 2. Идентификатор модуля — поле `module`, иначе имя папки

Папка может называться коротко (`master`), а модуль — как артефакт сборки
(`sds-master`); ссылки `depends_on` и ADR идут по идентификатору. Дубль
идентификатора — ошибка: первым по алфавиту папок остаётся описанный модуль,
второй в карту не попадает.

**Альтернатива — только имя папки.** Проще, но заставляет переименовывать
папки под имена артефактов и ломает ссылки при переносе.

### 3. Разбор — в `core`, файлы и YAML — в `server`

`buildContextMap` получает разобранные значения frontmatter и функцию «ключ →
строка», а также множество существующих путей кода; `core` остаётся без
Node API и внешних пакетов (тест чистоты). Сервер отделяет frontmatter,
разбирает его `yaml` с `LineCounter` и прибавляет смещение строки — так
замечание в VS Code попадает на строку поля.

### 4. Пути кода проверяются по префиксу

`code_paths` бывают шаблонами (`svc/src/**/*.java`) или сокращениями с `...`.
Проверяется часть до первого сегмента со звёздочкой или многоточием; шаблон с
самого начала (`**/*.java`) проверить нечем, он считается существующим. Путь
за пределами корня и абсолютный путь — не существуют. Отсутствующий путь —
предупреждение, а не ошибка: код могут переносить отдельно от контекста.

### 5. Раскладка графа — колонки и барицентры

Граф — три колонки: ADR → модули → домены; зависимости модулей — дуги слева
от колонки модулей со стрелкой. Порядок строк подбирается несколькими
проходами метода барицентров (узел ставится к среднему положению соседей),
этого хватает для десятков узлов без библиотек раскладки. Раскладка — чистая
функция в `web/lib`, проверяется тестом без браузера.

**Альтернатива — силовая раскладка (d3-force и т. п.).** Красивее на больших
графах, но недетерминирована между перерисовками и тянет зависимость в
панель VS Code; двудольная структура «модули × домены» колонками читается
лучше. Для плотных связей есть матрица.

### 6. Набор контекста для модуля

Для выбранного модуля собирается упорядоченный список файлов: общий контекст,
`context.md` модуля и транзитивно его зависимостей по `depends_on` (обход в
ширину, каждый модуль один раз — циклы не мешают), спеки их доменов и ADR,
ссылающиеся на эти модули. Список копируется строками `@путь` — в таком виде
его принимают агенты в терминале.

### 7. Удаление агента без миграции настроек

`.openspec-ide/config.json` содержал только настройки агента, поэтому модуль
конфигурации удалён целиком; каталог `.openspec-ide/` остаётся для метрик.
Файл в проектах не удаляется — он просто больше не читается.

## Risks / Trade-offs

- **Большие графы.** Сотни модулей в колонках дадут длинную прокрутку; для
  обзора есть матрица, для работы — выбор узла с подсветкой соседей.
- **Метрики расхода токенов** больше не пополняются из IDE: показывается только
  накопленная история. Удалять их или принимать данные извне — отдельное
  решение.
