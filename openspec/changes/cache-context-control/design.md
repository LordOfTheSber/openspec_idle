# Design: кэш контроля контекста

## Context

Мотивация и замеры — в `proposal.md`, требования — в дельте `specs/context-map`.

Карту строит `ContextMapService.build()` в `packages/server/src/contextMap.ts`:
читает файлы `openspec/context/` и спеки, проверяет существование путей и для
каждого модуля вызывает `#freshness`. Свежесть — четыре вызова `GitHistory`
(`packages/server/src/git.ts`), каждый — отдельный процесс `git`:

- `hasChanges(context.md)` — `git status --porcelain --untracked-files=all`;
- `lastCommit(context.md)` — `git log -1`;
- `lastCommitDate(префиксы кода)` — `git log -1`;
- `commitsAfter(коммит, префиксы кода)` — `git rev-list --count`.

Остальная сборка — чистые функции `core` и чтение файлов, на синтетическом
репозитории на 40 модулей — 30–45 мс против 650–900 мс с git.

Карту запрашивают три клиента: раздел «Контекст» (при монтировании и на каждую
ревизию рабочего пространства), расширение VS Code для панели «Проблемы» (при
запуске, на `workspace-changed` и на создание или удаление любого файла
рабочего пространства, с задержкой 500 мс) и `openspec-ide-check`. Раздел
рендерится условно (`section === 'context'` в `App.tsx`), поэтому при
переключении разделов размонтируется и теряет карту.

## Goals / Non-Goals

**Goals:**

- Повторная сборка карты без изменений в git — без запросов истории git, кроме
  одного снимка состояния.
- Результат кэша неотличим от расчёта без него.
- Возврат в раздел показывает данные сразу.

**Non-Goals:**

- Ускорение первой («холодной») сборки после запуска бэкенда.
- Кэш между перезапусками бэкенда.
- Кэш чтения файлов, проверки путей и расчётов `core`.

## Decisions

### 1. Кэшируется только свежесть, а не вся карта

**Решение.** Кэш — в `ContextMapService`, на уровне свежести одного модуля.
Файлы, существование путей и `buildContextMap` считаются при каждой сборке,
как сейчас.

**Альтернатива — кэш готовой карты, сбрасываемый наблюдателем файлов.**
Наблюдатель следит за `openspec/` и папками структуры, но не за кодом и не за
`.git/`: существование путей кода и ссылок из контекста, коммиты — вне его
поля зрения. Такой кэш показывал бы ненайденный путь найденным до следующей
правки в `openspec/`. Выигрыш сверх кэша свежести — десятки миллисекунд.

### 2. Ключ — состояние git и входы расчёта, а не время жизни

**Решение.** Ключ записи — снимок состояния git (коммит `HEAD`, время
изменения и размер файла индекса) плюс путь `context.md`, его текст и
отсортированные префиксы существующих путей кода. Почему этого достаточно:

- `lastCommit`, `lastCommitDate`, `commitsAfter` зависят только от истории,
  достижимой из `HEAD`, и от путей — оба в ключе;
- `hasChanges` сравнивает рабочее дерево, индекс и `HEAD` для одного файла:
  содержимое файла (текст), индекс (время и размер) и `HEAD` — в ключе.
  Неотслеживаемый `context.md` с тем же текстом при том же `HEAD` остаётся
  неотслеживаемым.

Текст `context.md` сервер уже прочитал, лишнего обращения к диску нет.
Снимок — один процесс на сборку: `git rev-parse HEAD --git-path index` выдаёт
коммит и путь индекса (относительно корня, с учётом worktree и `GIT_DIR`),
затем `stat` индекса. `GitHistory` передаёт git `GIT_OPTIONAL_LOCKS=0`,
поэтому собственные `git status` IDE индекс не переписывают и кэш не
сбрасывают.

**Альтернатива — время жизни записи (TTL).** Короткий TTL не спасает от волн
пересчёта во время сборки проекта, длинный — показывает отставание, которого
уже нет после коммита. Ключ по состоянию точен и не требует подбора чисел.

**Альтернатива — следить за `.git/HEAD`, `refs/` и `index` наблюдателем.**
Ветки в `packed-refs`, worktree с `.git`-файлом, `GIT_DIR` и сетевые диски
делают это хрупким; снимок через сам git учитывает их все.

### 3. Кэш хранит обещания, поколение — по снимку

**Решение.** Записи — `Map<ключ модуля, Promise<ModuleFreshness | null>>` под
одним снимком. Сборка с другим снимком заменяет всю `Map`: записи старого
состояния больше не понадобятся, и память ограничена числом модулей. В `Map`
кладётся обещание до завершения расчёта, поэтому одновременные сборки
(раздел и панель «Проблемы» после одного изменения файлов) ждут один расчёт.
Обещание с результатом `null` после запросов git (сбой или таймаут git)
удаляется из кэша по завершении: следующая сборка попробует снова. Если
снимок не получен (репозиторий без коммитов, сбой git), свежесть считается
без кэша, как сейчас.

**Альтернатива — общая незавершённая сборка всей карты.** Запрос, пришедший
после изменения файлов, получил бы карту, начатую до изменения. Обещания на
уровне модуля с ключом по тексту такой ошибки не дают.

### 4. Последняя карта на клиенте — переменная модуля

**Решение.** `ContextMap.tsx` хранит последнюю полученную карту в переменной
модуля и берёт её начальным состоянием при монтировании; запрос идёт как
раньше и заменяет карту, когда придёт ответ. Номер запроса в `useRef`
отбрасывает ответ, если после него уже применён более поздний. Переменная
живёт столько же, сколько страница: панель VS Code открыта с
`retainContextWhenHidden`, и карта переживает и переключение разделов, и
скрытие панели; в браузере — до перезагрузки страницы.

**Альтернатива — держать раздел смонтированным скрытым.** Раздел продолжал бы
перестраивать раскладку графа и запрашивать карту на каждую ревизию, даже
когда не виден, а остальным разделам такое поведение не нужно.

**Альтернатива — `localStorage`.** Карта переживала бы перезапуск, но
показывала бы данные другого состояния проекта до первого ответа, а
`lib/prefs` хранит только настройки вида.

### 5. Прогрев — существующими вызовами

**Решение.** Отдельного прогрева нет. В VS Code расширение запрашивает карту
для панели «Проблемы» сразу после запуска бэкенда — этот запрос заполняет кэш,
и первое открытие раздела обычно уже в него попадает.

**Альтернатива — сборка карты при запуске сервера.** Тратила бы процессы git
в режиме разработки и в `openspec-ide-check`, где раздел не откроют.

## Risks / Trade-offs

- [Изменение, которого нет в ключе: `git fetch --deepen` у мелкого клона
  меняет число коммитов без смены `HEAD`] → редкий случай; свежесть
  обновится со следующим коммитом или перезапуском бэкенда.
- [Две записи индекса в пределах разрешения времени файловой системы с
  одинаковым размером] → затрагивает только признак незакоммиченной правки
  `context.md`; правка самого файла меняет текст в ключе.
- [Пользователь сам запускает `git status`, и тот обновляет индекс] → снимок
  меняется, свежесть пересчитывается; лишняя работа, но не неверный
  результат.
- [Клиент показывает прежнюю карту до ответа] → данные устаревают не больше
  чем на время одного запроса и сразу заменяются; при ошибке запроса остаётся
  прежнее поведение — сообщение об ошибке.

## Migration Plan

Миграции нет: формат ответа и файлы проекта не меняются. Откат — отмена
изменения кода.
