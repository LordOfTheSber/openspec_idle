# Design: расширение VS Code вместо отдельной web-IDE

## Context

Мотивация — в `proposal.md`, раздел Why. Требования — в
`specs/vscode-extension/spec.md`. Здесь — как собрать.

Исходное состояние:

- `packages/core` — чистая логика без Node API (дерево, доска, метрики, правила
  SDD, разбор потока агента).
- `packages/server` — Fastify-приложение `createApp()` со всеми маршрутами
  `/api/*`, потоком событий `EventBus` и наблюдателем за файлами;
  `startServer()` вешает его на loopback-порт.
- `packages/web` — React-приложение. Весь доступ к API сосредоточен в двух
  функциях `get`/`send` из `lib/api.ts`, поток событий — в `lib/connection.ts`
  за интерфейсом `StreamTransport`.
- `packages/cli` — бинарь `openspec-ide`: разбор аргументов, `startServer`,
  открытие браузера. Им же пользуются `npm run dev` и e2e.

Ограничения среды:

- Код расширения исполняется хостом расширений VS Code — это Node, но модуль
  `vscode` существует только там. Загрузить VS Code в среду сборки этого
  репозитория нельзя: сеть к серверу обновлений VS Code закрыта.
- Webview — изолированный iframe: у него нет `fetch` к файлам расширения и нет
  `EventSource` к процессу расширения. Связь — только `postMessage`.
- Пакеты репозитория — ESM (`"type": "module"`), а хост расширений надёжно
  загружает CommonJS.

## Goals / Non-Goals

### Goals

- Не переписывать работающие разделы: маршруты бэкенда и React-компоненты
  переиспользуются как есть, меняется только транспорт и оболочка.
- Один редактор файла — редактор VS Code. Встроенный CodeMirror в расширении не
  используется.
- Коды ответов и тела не зависят от транспорта: всё, что проверено тестами
  HTTP-режима, остаётся верным и в панели.

### Non-Goals

- Нативная реализация доски, метрик, дельт и конструктора процессов средствами
  VS Code API (TreeView, CustomEditor). Возможна позже по одному разделу.
- Удалённые рабочие области (Remote SSH, Codespaces) проверяются только в той
  мере, в какой хост расширений работает на машине с проектом — отдельной
  поддержки не делается.

## Decisions

### 1. Гибрид: нативные дерево, редактор и диагностика, остальное — webview

**Решение.** В VS Code переезжает то, для чего у редактора есть родной
механизм: дерево рабочего пространства (`TreeDataProvider`), редактирование
(обычный текстовый редактор), замечания валидации (`DiagnosticCollection`),
команды и строка состояния. Доска, дельты, метрики, агент, процессы, настройки и
поиск остаются React-разделами в одной панели webview.

**Альтернатива — всё нативно.** Доска с колонками из схемы, граф конструктора
процессов и сравнение дельт в модель TreeView/QuickPick не ложатся, а переписать
их — это заново проделать группы 6–10 прежнего плана.

**Альтернатива — всё в webview.** Быстрее всего, но оставляет второй редактор
файлов со всеми его конфликтами — ровно ту проблему, ради которой переезд.

### 2. Бэкенд внутри процесса расширения через `inject()` Fastify

**Решение.** Расширение вызывает тот же `createApp()`, но не вешает его на порт,
а обслуживает запросы панели через `app.inject()` — Fastify прогоняет запрос по
маршрутам, хукам и обработчику ошибок в памяти. Для этого в `packages/server`
появляется `createEmbeddedBackend()`: собирает приложение без раздачи страницы,
запускает наблюдатель, отдаёт `request(method, path, body)`, подписку на
`EventBus` и `close()`. Токен сессии бэкенд прикладывает к запросу сам: панель
его не видит и не хранит.

**Альтернатива — `startServer()` на loopback и iframe с `localhost` внутри
webview.** Требует порта, токена, проброса порта в удалённых сценариях и
ослабления CSP до `http://127.0.0.1:*`. Именно эту инфраструктуру переезд и
убирает.

**Альтернатива — вынести маршруты в набор RPC-функций.** Чище по форме, но
удваивает поверхность: те же проверки аргументов и перевод ошибок в коды
пришлось бы поддерживать дважды, пока жив HTTP-режим разработки.

### 3. Сменяемый транспорт в `packages/web`

**Решение.** `lib/transport.ts` задаёт `ApiTransport` — `request(method, path,
body) → { status, body }`. `get`/`send` в `lib/api.ts` работают через него, а не
через `fetch` напрямую; разбор ошибок (409 с версией диска → `StaleWriteConflict`,
прочие → `ApiError`) остаётся общим. Реализаций две: `fetch` для HTTP-режима и
`postMessage` для webview. Поток событий в webview — ещё одна реализация уже
существующего `StreamTransport`. Выбор делает `lib/host.ts` по наличию
`acquireVsCodeApi`.

Протокол сообщений (виды, поля, проверки входящих сообщений) лежит в
`packages/core/src/hostProtocol.ts`: его используют обе стороны, он чистый и
проверяется без VS Code и без браузера.

**Альтернатива — перехватывать `window.fetch` в webview.** Меньше правок, но
подмена глобала неявна, а `EventSource` так не подменить.

### 4. Связь панели с хостом

В режиме VS Code панель:

- не показывает раздел «Обозреватель» — редактирование нативное;
- по выбору артефакта в своём дереве, результата поиска или элемента метрик
  шлёт `open-file` с путём и строкой, и файл открывается в редакторе VS Code;
- принимает `navigate` с разделом и выбранным change/capability — так
  контекстное меню дерева и команды палитры переключают уже открытую панель.

Расширение открывает только путь внутри корня: он канонизируется той же
`resolveInsideWorkspace`, что защищает файловые маршруты бэкенда.

### 5. Сборка: esbuild в CommonJS, интерфейс копируется в расширение

**Решение.** `packages/vscode/src/extension.ts` собирается esbuild в один
`dist/extension.cjs` (`platform: node`, `format: cjs`, внешний модуль —
`vscode`). Единственное обращение к `import.meta.url` в серверном коде
подменяется при сборке на `pathToFileURL(__filename)`. Интерфейс собирается
Vite с `base: './'` и копируется в `packages/vscode/media/web`; при открытии
панели расширение переписывает `<script>`/`<link>` на адреса
`webview.asWebviewUri` и вставляет CSP с nonce. `vsce package
--no-dependencies` упаковывает расширение: все зависимости уже в бандле.

**Альтернатива — ESM-расширение.** Не нужно подменять `import.meta`, но
поддержка ESM в хосте расширений появилась поздно и сужает круг версий VS Code.

**Альтернатива — `tsc` без бандла.** В `.vsix` пришлось бы класть `node_modules`
с символическими ссылками workspaces, которые упаковщик не разворачивает.

### 6. Диагностика — из `ValidationRunner`, по сохранению

Сохранение файла под `openspec/changes/<name>/` запускает
`GET /api/validate?change=<name>` через тот же встраиваемый бэкенд.
`ValidationRunner` уже отменяет устаревший прогон, поэтому серия быстрых
сохранений даёт один результат. Замечание с файлом и строкой ложится на эту
строку, без строки — на начало файла, без файла — на `proposal.md` change или
на его каталог. Перевод `ValidationEntry[]` в набор диагностик — чистая функция,
проверяемая без VS Code.

**Альтернатива — проверка на каждое изменение текста.** CLI проверяет файлы на
диске, а не буфер редактора; проверять несохранённый текст пришлось бы через
временные копии.

### 7. Тема панели из переменных VS Code

Webview получает от VS Code CSS-переменные `--vscode-*` и класс темы на `body`.
В режиме хоста `:root[data-host='vscode']` переопределяет токены интерфейса
(`--bg`, `--surface`, `--text`, `--accent`, `--border`, шрифты) через
`--vscode-editor-background`, `--vscode-foreground`,
`--vscode-focusBorder` и т. д.; цвета дельт берутся из
`--vscode-gitDecoration-*`, чтобы оставаться различимыми в любой теме.

### 8. Упразднение `packages/cli`

Бинарь, его разбор аргументов и открытие браузера удаляются. `npm run dev` и
e2e запускают бэкенд скриптом разработки `scripts/serve.mjs`, который вызывает
`startServer()` из собранного `packages/server` и печатает адрес так же, как
раньше. Этот режим — средство разработки интерфейса, в документации для
пользователей его нет.

### 9. Проверка без настоящего VS Code

- Модульные тесты: протокол сообщений, модель узлов дерева, перевод замечаний в
  диагностики, переписывание HTML панели с CSP, встраиваемый бэкенд (inject,
  коды ответов, события, закрытие).
- Дымовой тест собранного бандла: `dist/extension.cjs` загружается с
  подменённым модулем `vscode`, вызывается `activate` на фикстурном проекте,
  проверяется регистрация дерева и команд, узлы дерева, круговой запрос панели
  через `postMessage` и корректный `deactivate`.
- Интерфейс по-прежнему проверяется e2e в Chromium через HTTP-режим.

## Risks / Trade-offs

- **Поведение, которое видно только в настоящем VS Code** (раскладка webview,
  фокус, контекстные меню) → дымовой тест ловит ошибки загрузки и регистрации,
  остальное — ручная приёмка по сценариям спеки перед выпуском; задача приёмки
  стоит в плане отдельно.
- **Fastify и его зависимости в бандле esbuild** → бандл проверяется дымовым
  тестом, который реально поднимает бэкенд из собранного файла.
- **`inject()` не поддерживает потоковые ответы как настоящий сокет** → поток
  событий через `inject` не идёт: встраиваемый бэкенд подписывается на
  `EventBus` напрямую и пересылает события сообщениями.
- **Размер `.vsix`** (React, CodeMirror, Fastify) → приемлемо для локальной
  установки; CodeMirror в панели не используется и отсекается, если перестанет
  импортироваться разделами.
- **Одна рабочая область — один корень** → при нескольких папках берётся первая
  с OpenSpec, а выбранный корень показан в строке состояния и в подсказке
  дерева.

## Migration Plan

1. Встраиваемый бэкенд и протокол сообщений — без изменения поведения
   HTTP-режима.
2. Сменяемый транспорт в `web` — HTTP-режим и e2e продолжают работать.
3. Пакет `packages/vscode`: дерево, открытие файлов, диагностика, команды,
   панель.
4. Скрипт разработки вместо `packages/cli`, удаление `packages/cli`.
5. README: установка расширения из `.vsix`, раздел для разработчиков.

Откат — вернуть `packages/cli` из истории git: бэкенд и интерфейс сохраняют
HTTP-режим, так что прежний бинарь заработает без других правок. Данные
пользователя (`.openspec-ide/`, `openspec/`) переезд не трогает.
