# Spec Delta: workflow-designer

## Purpose

Позволяет команде построить собственный процесс работы вместо встроенного
`spec-driven`: собрать схему workflow из артефактов и их зависимостей, задать
шаблоны и инструкции, проверить её и назначить проекту или отдельному change —
в том виде, который понимает CLI OpenSpec, без параллельного формата описания.

## ADDED Requirements

### Requirement: Реестр схем проекта

Система ДОЛЖНА (SHALL) показывать все доступные схемы по данным
`openspec schemas --json`, отмечая для каждой источник разрешения — встроенная в
пакет или проектная — и указывая схему, заданную проектом по умолчанию. Для
выбранной схемы ДОЛЖЕН быть доступен путь её разрешения из
`openspec schema which <name> --json`, включая перечень затеняемых ею схем.

#### Scenario: Проект без собственных схем

- **WHEN** в проекте нет каталога собственных схем
- **THEN** реестр показывает только встроенные схемы
- **AND** предлагается создать собственную схему или форкнуть существующую

#### Scenario: Проектная схема затеняет встроенную

- **WHEN** проектная схема имеет то же имя, что и встроенная
- **THEN** в реестре она помечена как затеняющая
- **AND** показано, какая именно схема затенена

#### Scenario: Схема проекта не разбирается

- **WHEN** файл схемы содержит синтаксически некорректный YAML
- **THEN** схема показана в реестре как нечитаемая с текстом ошибки разбора
- **AND** остальные схемы остаются доступны

### Requirement: Создание схемы

Система ДОЛЖНА (SHALL) создавать новую проектную схему двумя путями: с нуля
командой `openspec schema init <name>` и копией существующей командой
`openspec schema fork <source> <name>`. Имя новой схемы ДОЛЖНО проверяться на
конфликт с уже существующими до выполнения команды.

#### Scenario: Создание схемы с нуля

- **WHEN** пользователь создаёт схему с незанятым именем
- **THEN** выполняется `openspec schema init` и схема появляется в реестре
- **AND** она открывается в конструкторе

#### Scenario: Форк существующей схемы

- **WHEN** пользователь создаёт схему копией встроенной
- **THEN** выполняется `openspec schema fork` с именем исходной схемы
- **AND** артефакты, шаблоны и инструкции исходной схемы переносятся в новую

#### Scenario: Имя схемы занято

- **WHEN** введённое имя совпадает с именем существующей проектной схемы
- **THEN** создание не выполняется
- **AND** предлагается другое имя или открытие существующей схемы

### Requirement: Конструктор схемы

Система ДОЛЖНА (SHALL) предоставлять три синхронных представления схемы: граф
артефактов с рёбрами зависимостей, форму свойств выбранного артефакта и текст
YAML схемы. Правка в любом из представлений ДОЛЖНА отражаться в остальных до
сохранения на диск.

#### Scenario: Добавление артефакта на графе

- **WHEN** пользователь добавляет артефакт на графе и связывает его зависимостью
- **THEN** артефакт появляется в YAML со своей зависимостью
- **AND** форма свойств открывается на этом артефакте

#### Scenario: Правка YAML вручную

- **WHEN** пользователь меняет текст YAML схемы
- **THEN** граф и форма свойств перестраиваются по новому тексту

#### Scenario: YAML временно некорректен

- **WHEN** текст YAML в процессе правки не разбирается
- **THEN** граф и форма показывают последнее корректное состояние, помеченное как устаревшее
- **AND** сохранение схемы заблокировано с указанием места ошибки разбора

#### Scenario: Свойства артефакта

- **WHEN** пользователь выбирает артефакт на графе
- **THEN** форма показывает его идентификатор, порождаемый путь, описание, шаблон, инструкцию и зависимости
- **AND** изменения любого поля попадают в YAML

#### Scenario: Удаление артефакта, от которого зависят другие

- **WHEN** пользователь удаляет артефакт, указанный в зависимостях другого
- **THEN** показывается список зависящих артефактов
- **AND** удаление выполняется только после подтверждения, а зависимости от удалённого снимаются

### Requirement: Редактирование шаблонов схемы

Система ДОЛЖНА (SHALL) позволять править файл шаблона каждого артефакта схемы и
создавать шаблон для артефакта, у которого он объявлен, но отсутствует на диске.

#### Scenario: Правка шаблона артефакта

- **WHEN** пользователь открывает шаблон артефакта и сохраняет изменения
- **THEN** файл шаблона в каталоге схемы обновляется
- **AND** новые артефакты этой схемы создаются уже по новому шаблону

#### Scenario: Объявленный шаблон отсутствует

- **WHEN** артефакт схемы ссылается на несуществующий файл шаблона
- **THEN** это показано как нарушение структуры схемы
- **AND** предлагается создать файл шаблона

### Requirement: Проверка схемы

Система ДОЛЖНА (SHALL) проверять схему в два слоя: структурно командой
`openspec schema validate <name>` и на соответствие спек-ориентированности по
правилам capability `sdd-conformance`. Результаты обоих слоёв ДОЛЖНЫ быть
показаны вместе, с различением слоя, к которому относится каждая запись.

#### Scenario: Структурная ошибка схемы

- **WHEN** в схеме образуется цикл зависимостей между артефактами
- **THEN** отчёт содержит запись структурного слоя с текстом ошибки от CLI
- **AND** сохранение схемы не блокируется, но назначение блокируется

#### Scenario: Схема структурно валидна, но не спек-ориентирована

- **WHEN** схема проходит структурную проверку, но нарушает правило SDD уровня «ошибка»
- **THEN** отчёт содержит запись слоя соответствия SDD
- **AND** назначение схемы заблокировано

#### Scenario: Схема проходит обе проверки

- **WHEN** оба слоя проверки не находят нарушений
- **THEN** схема помечена готовой к назначению

### Requirement: Назначение схемы

Система ДОЛЖНА (SHALL) позволять задавать схему проекта по умолчанию в
`openspec/config.yaml` и выбирать схему при создании change. Схема, нарушающая
правило SDD уровня «ошибка», ДОЛЖНА быть недоступна для назначения.

#### Scenario: Назначение схемы проекту

- **WHEN** пользователь выбирает схему по умолчанию для проекта
- **THEN** поле схемы в настройках проекта обновляется
- **AND** остальное содержимое файла настроек остаётся неизменным

#### Scenario: Попытка назначить несоответствующую схему

- **WHEN** пользователь выбирает схему с нарушением правила уровня «ошибка»
- **THEN** назначение не выполняется
- **AND** показывается перечень нарушений и способ их исправить

#### Scenario: Смена схемы проекта при существующих changes

- **WHEN** схема проекта меняется, а активные changes заведены по прежней схеме
- **THEN** уже существующие changes сохраняют свою схему
- **AND** пользователю сообщается, что новая схема применится только к новым changes

### Requirement: Предпросмотр процесса

Система ДОЛЖНА (SHALL) показывать, как схема выглядит в работе: порядок
артефактов, состав колонок доски и артефакт, по которому будет измеряться
прогресс, — до того, как схема назначена.

#### Scenario: Предпросмотр колонок доски

- **WHEN** пользователь открывает предпросмотр схемы
- **THEN** показан состав колонок доски в порядке зависимостей артефактов
- **AND** отмечен артефакт, объявленный отслеживаемым

#### Scenario: Схема не объявляет отслеживаемый артефакт

- **WHEN** в схеме отсутствует указание отслеживаемого артефакта
- **THEN** предпросмотр показывает, что прогресс по такому процессу измеряться не будет
