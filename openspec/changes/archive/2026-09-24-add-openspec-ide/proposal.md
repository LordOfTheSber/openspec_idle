# Change: OpenSpec IDE — локальная среда для спек-ориентированной разработки

## Why

Сегодня работа по OpenSpec живёт в двух несвязанных плоскостях: артефакты — это
markdown-файлы в `openspec/`, а состояние процесса — в голове разработчика и в
выводе CLI. Чтобы понять «где мы находимся», приходится вручную сопоставлять
`openspec list`, `openspec status`, `openspec validate` и содержимое файлов, а
дельты спеков читать глазами против основного спека. Нет ни одного места, где
видно прогресс по плану, стоимость работы агента и качество артефактов
одновременно.

Одновременно команда переходит на GigaCode CLI как на единственный разрешённый
канал к LLM. Сейчас агент вызывается из терминала вручную, его запуски нигде не
учитываются, а связь «задача из tasks.md → запуск агента → изменённые файлы»
теряется.

Третья проблема — процесс. Схема `spec-driven` подходит не всем: одним нужен
этап исследования перед предложением, другим — обязательное ревью спека, третьим
достаточно облегчённого цикла. OpenSpec это допускает: схемы workflow заводятся
командами `openspec schema init` и `openspec schema fork` и живут в
`openspec/schemas/`. Но `openspec schema validate` проверяет только структуру:
цикл в зависимостях артефактов она ловит, а процесс, где спеков нет вообще,
считает валидным. То есть построить собственный процесс можно, а убедиться, что
он остался спек-ориентированным, нечем — и команда незаметно уезжает из SDD в
свободное сочинение.

OpenSpec IDE закрывает все три проблемы: даёт единое локальное рабочее место над
существующим каталогом `openspec/`, где артефакты редактируются с живой
валидацией, процесс виден на доске, каждый пункт плана несёт измеримые метрики,
агент запускается из UI через GigaCode CLI с учётом бюджета и результата, а сам
процесс можно собрать под команду — но только такой, который остаётся SDD.

## What Changes

- **Новый инструмент `openspec-ide`** — локальный сервер + SPA, запускается в
  каталоге проекта и открывается в браузере. Источник истины остаётся на диске:
  IDE читает и пишет те же файлы, что и CLI, своей базы состояния артефактов нет.
- **Навигация по рабочему пространству** — дерево changes / specs / archive с
  индикаторами статуса артефактов, поиск по требованиям и сценариям, слежение за
  файловой системой и автообновление при внешних правках (включая правки агента).
- **Редактор артефактов** — markdown-редактор с подсветкой структуры OpenSpec,
  предпросмотром, вставкой шаблонов артефактов и живой валидацией
  (`openspec validate --strict`), где каждая ошибка кликабельна и ведёт в строку.
- **Просмотр дельт** — структурный разбор спеков change на требования и сценарии,
  трёхцветный diff ADDED / MODIFIED / REMOVED / RENAMED против основного спека и
  карта связей «capability ↔ changes».
- **Доска процесса** — канбан по фазам жизненного цикла change с прогрессом по
  отслеживаемому артефакту и запуском операций `validate` / `archive` из карточки.
  Колонки строятся из артефактов схемы, по которой заведён change, поэтому доска
  одинаково работает и для `spec-driven`, и для собственного процесса команды.
- **Метрики по каждому пункту плана** — для каждого пункта в артефакте, который
  схема объявила отслеживаемым (`apply.tracks`), и для change в целом IDE ведёт
  измерения: состояние, время в работе, число и исход запусков
  агента, израсходованные токены и время LLM, затронутые файлы, результат
  проверок из поля приёмки задачи. Метрики хранятся отдельно от артефактов и
  никогда не изменяют markdown, кроме отметки чекбокса.
- **Мост к агенту на GigaCode CLI** — единственный поддерживаемый провайдер LLM в
  MVP. Запуск headless-процессом с потоковым выводом в панель, ограничением
  бюджета по времени и вызовам инструментов, режимом подтверждений и связью
  запуска с конкретной задачей плана. Промпт собирается из
  `openspec instructions <artifact> --json`, так что агент получает ровно те
  инструкции, которые предписывает схема workflow.
- **Конструктор процессов** — раздел, где собирается собственная схема workflow:
  граф артефактов и их зависимостей, свойства артефакта (что порождает, шаблон,
  инструкция для агента), точка начала работ. Граф, форма свойств и YAML схемы
  синхронны: правка в любом из трёх сразу видна в остальных. Схема создаётся с
  нуля или форком существующей, сохраняется в `openspec/schemas/<name>/` и
  назначается проекту или отдельному change — ровно в том виде, который понимает
  CLI, без параллельного формата.
- **Проверка SDD-соответствия** — набор правил поверх структурной валидации CLI,
  отвечающий на вопрос «остался ли этот процесс спек-ориентированным». Проверяется
  наличие артефакта-контракта поведения, то, что работа по коду зависит от него, а
  не идёт параллельно, отслеживаемость выполнения и заполненность инструкций.
  Нарушение правила уровня «ошибка» блокирует назначение схемы; обойти его можно
  только явной отметкой в самой схеме с указанием причины, так что отказ от SDD
  остаётся видимым решением, а не случайностью.
- **Настройки подключения к LLM** — раздел настроек, где задаётся путь к
  исполняемому файлу GigaCode CLI, модель, режим подтверждений, бюджеты и способ
  передачи учётных данных. Секреты в репозиторий не попадают.

Не входит в этот change (зафиксировано как не-цели в design.md): совместная
многопользовательская работа, облачный хостинг IDE, поддержка провайдеров LLM
кроме GigaCode CLI, редактирование произвольного кода проекта.

## Capabilities

### New Capabilities

- `ide-runtime` — запуск IDE, разрешение корня OpenSpec, транспорт между SPA и
  сервером, безопасность локального доступа, конфигурация.
- `workspace-explorer` — навигация по changes, specs и архиву, поиск,
  синхронизация с файловой системой.
- `artifact-editor` — чтение, редактирование и сохранение артефактов change с
  живой валидацией и шаблонами.
- `spec-delta-viewer` — структурный просмотр требований и сценариев, diff дельт
  против основного спека, связи capability ↔ changes.
- `workflow-board` — доска фаз жизненного цикла change и операции над change.
- `task-metrics` — модель, сбор и отображение метрик по каждому пункту плана и по
  change целиком.
- `agent-bridge` — интеграция с GigaCode CLI: конфигурация, запуск, стриминг,
  бюджеты, привязка запусков к задачам.
- `workflow-designer` — реестр схем проекта, создание и правка собственной схемы
  workflow, назначение схемы проекту и change.
- `sdd-conformance` — правила спек-ориентированности процесса, отчёт о
  соответствии и последствия нарушений.

### Modified Capabilities

Нет — в проекте пока нет ни одного основного спека.

## Impact

- **Новый код**: монорепозиторий npm workspaces — `packages/server` (Fastify,
  обёртка над openspec CLI, адаптер GigaCode), `packages/web` (React + Vite SPA),
  `packages/core` (разбор markdown OpenSpec, модель метрик, общие типы),
  `packages/cli` (бинарь `openspec-ide`).
- **Внешние зависимости**: `@fission-ai/openspec` как peer-инструмент (вызывается
  как процесс, не как библиотека), Fastify, React, Vite, CodeMirror 6, Vitest,
  Playwright.
- **Внешние системы**: GigaCode CLI должен быть установлен и авторизован на
  машине пользователя. IDE не встраивает его и не хранит его учётные данные.
- **Данные**: каталог `.openspec-ide/` в корне проекта под метрики и журналы
  запусков агента; добавляется в `.gitignore` по умолчанию. Собственные схемы
  пишутся в `openspec/schemas/` — этот каталог, наоборот, версионируется вместе с
  проектом, потому что процесс общий для команды.
- **Экспериментальная область CLI**: команды `openspec schema` помечены как
  экспериментальные, их интерфейс может измениться между версиями OpenSpec.
- **Сеть**: сервер слушает только loopback; исходящих соединений IDE сама не
  делает — весь трафик к LLM идёт через процесс GigaCode CLI.
