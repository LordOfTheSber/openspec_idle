# Design: предпросмотр архивации и доска, удобная в VS Code

## Context

Мотивация — в `proposal.md`. Требования — в `specs/archive-preview/spec.md`,
`specs/workflow-board/spec.md`, `specs/spec-delta-viewer/spec.md` и
`specs/vscode-extension/spec.md`.

Исходное состояние:

- Архивация — `BoardService.archiveChange()`: `openspec archive <name> --yes`
  в корне проекта. Своей реализации слияния дельт у IDE нет и не должно быть:
  правила слияния у CLI нетривиальны (порядок RENAMED → REMOVED → MODIFIED →
  ADDED, отказ при потере сценария в MODIFIED, заглушка назначения у новой
  capability, нормализация заголовков) и меняются от версии к версии.
- У `openspec archive` нет режима «показать, но не делать». Флаги: `--yes`,
  `--skip-specs`, `--no-validate`, `--json`. С `--json` команда печатает
  `archive.totals` при успехе и `status[]` с `code`, `message`, `fix` при
  отказе; отказ ничего не меняет на диске.
- Доска (`Board.tsx`) получает только список схем, перечитывается при
  монтировании и после своих действий. Подробности выбранного change выводятся
  под сеткой колонок.
- В панели VS Code слева от любого раздела, кроме процессов и настроек, стоит
  дерево рабочего пространства — дубль нативного дерева расширения.

## Goals / Non-Goals

### Goals

- Предпросмотр, который не может разойтись с архивацией: тот же CLI, те же
  флаги, те же входные файлы.
- Доска, которой можно пользоваться в панели шириной 500–900 px без
  горизонтальной прокрутки ради поиска карточки.
- Всё, что делается с change, доступно с его карточки.

### Non-Goals

- Своя реализация слияния дельт — даже как запасной путь.
- Перетаскивание карточек. Фаза по-прежнему выводится из файлов.

## Decisions

### 1. Предпросмотр — настоящий `openspec archive` на временной копии

**Решение.** Сервис предпросмотра создаёт каталог `mkdtemp(tmpdir())`, копирует
в него `openspec/` проекта без `changes/`, затем копирует только
`changes/<name>/` и создаёт пустой `changes/archive/`. В этой копии выполняется
`openspec archive <name> --yes --json`. После прогона основные спеки копии
сравниваются с основными спеками проекта, копия удаляется в `finally`.

Копируется весь `openspec/` кроме чужих changes и архива, потому что CLI
читает оттуда `config.yaml`, схемы проекта (`openspec/schemas/`) и основные
спеки. Чужие changes и архив архивации не нужны, а архив со временем растёт.

Телеметрия CLI в прогоне предпросмотра отключается переменной
`OPENSPEC_TELEMETRY=0`: предпросмотр — не архивация, и считать его ею нельзя.

**Альтернатива — своя реализация слияния в `core`.** Быстрее (нет процесса и
копирования), но это вторая реализация правил, которые принадлежат CLI:
предпросмотр начал бы расходиться с архивацией при первом же обновлении CLI, а
именно расхождение предпросмотр и должен исключать.

**Альтернатива — импортировать модуль слияния из пакета CLI.** CLI находится в
проекте пользователя или в `PATH`, а не в зависимостях расширения; его
внутренние модули не являются публичным API и могут переехать в любой версии.

**Альтернатива — `git stash` / откат в самом проекте.** Трогает рабочее дерево
пользователя и ломается на незакоммиченных правках.

### 2. Исходы предпросмотра

- `ready` — CLI в копии завершился успешно; спеки после архивации известны.
- `validation-failed` — CLI отказал с кодом `archive_validation_failed`.
  Настоящая архивация тоже откажет, но пользователю всё равно важно увидеть,
  что станет со спеками после исправления ошибок. Поэтому делается второй
  прогон на новой копии с `--no-validate`, и если он успешен, спеки
  показываются с предупреждением «архивация сейчас будет отклонена проверкой».
- `refused` — любой другой отказ CLI (например, MODIFIED теряет сценарий
  основного спека). Спеков после архивации нет — CLI их не построил; показывается
  сообщение и подсказка `fix` из JSON.

Кнопка «Архивировать» в подтверждении доступна только при исходе `ready`: в
остальных случаях команда заведомо завершится ошибкой.

**Альтернатива — всегда прогонять с `--no-validate`.** Одним процессом меньше,
но предпросмотр обещал бы успех архивации, которая упадёт.

### 3. Изменения спека по требованиям — из сравнения «до» и «после»

Список «добавлено / изменено / удалено / без изменений» строится чистой
функцией `core` по двум текстам спека: требования сопоставляются по заголовку
так же, как их сопоставляет CLI (без учёта хвостовых `#` и пробелов по
краям). Сравнение текста не может отличить переименование от пары «удалено +
добавлено», поэтому пары переименований берутся из дельты change
(`RENAMED`), уже разобранной `buildDeltaView`. Переименованное требование,
текст которого тоже поменялся, отмечается и как изменённое.

Для изменённого требования перечисляются добавленные и пропавшие сценарии —
это то, что рецензент проверяет глазами в первую очередь.

**Альтернатива — брать список из дельты.** Дельта говорит о намерении, а не о
результате: при несовпадении заголовка MODIFIED или RENAMED результат другой, и
предпросмотр должен показать именно результат.

### 4. Построчное сравнение — LCS в `core`

Файлы спеков — сотни строк, поэтому достаточно классического LCS по строкам с
отсечением общего начала и конца; результат режется на фрагменты с тремя
строками контекста, как `diff -u`. Если после отсечения матрица больше
4 млн ячеек, файл показывается как полная замена — это защищает панель от
зависания на патологическом входе.

**Альтернатива — зависимость `diff`.** Лишний пакет в бандле расширения ради
одной функции на сорок строк; в `core` запрещены зависимости с Node API, а
чистота проверяется тестом.

### 5. VS Code: сравнение во встроенном редакторе diff

Расширение регистрирует провайдер виртуальных документов со схемой
`openspec-preview`. Правая сторона — документ «спек после архивации», левая —
файл спека на диске или пустой виртуальный документ для новой capability.
Содержимое правой стороны расширение берёт из своего запроса к бэкенду, а не из
сообщения панели: панель присылает только `{ kind: 'preview-archive', change,
capability }`. Так панель не может подсунуть в редактор произвольный текст под
видом спека.

Команда `openspec.previewArchive` доступна из палитры и из контекстного меню
change. Если затронуто несколько capability, предлагается выбрать одну или все;
«все» открывает сравнения по очереди.

Подтверждение архивации в расширении сначала строит предпросмотр и показывает
в модальном окне сводку по capability; при исходе, отличном от `ready`,
архивация не предлагается, а показывается причина.

**Альтернатива — только сравнение внутри webview.** Работает, но в VS Code у
пользователя уже есть привычный редактор сравнения с навигацией по изменениям,
переносом строк и поиском.

### 6. Раскладка доски

- Доска занимает всю ширину панели в обоих режимах — дерево рабочего
  пространства для неё не нужно: всё, что оно давало доске, есть на карточке и
  в панели деталей.
- Пустые колонки сворачиваются в полосы шириной 36 px с вертикальным
  заголовком и счётчиком; полоса разворачивается по щелчку. Переключатель
  «Пустые колонки: свернуть / показать» на панели инструментов.
- Режим «Список»: фазы идут секциями сверху вниз, карточки — строками. В
  режиме «Авто» доска переключается в список, когда её ширина меньше 640 px
  (`ResizeObserver` на контейнере — ширина панели webview, а не окна).
  Выбранный режим запоминается в `localStorage` с защитой от недоступного
  хранилища.
- Панель деталей change стоит справа от доски при ширине от 1100 px — так
  доске рядом с ней остаётся больше 640 px и режим «Авто» не переключается при
  открытии деталей. На более узкой панели детали занимают место доски; доска
  при этом только скрывается, а не размонтируется. Панель закрывается кнопкой
  и клавишей Esc.

**Альтернатива — горизонтальная прокрутка как сейчас.** Именно она делает
доску бесполезной в половине окна.

**Альтернатива — отдельная доска на каждую схему.** Прятала бы часть работы;
отклонено ещё в исходном проекте доски.

### 7. Переходы с доски

Доска получает от `App` две функции: `navigate(section, change)` — переключить
раздел панели с выбором change — и `openArtifact(change, artifactId)`. В VS Code
вторая шлёт `open-file` с путём первого файла артефакта (путь добавляется в
данные карточки на сервере), в браузере — открывает раздел «Обозреватель» на
этом артефакте. Проверка с доски — существующий `GET /api/validate`; её
результат показывается в панели деталей с переходом к файлу и строке.

### 8. Живое обновление

`App` уже считает события `workspace-changed` в `revision`. Доска, её панель
деталей и предпросмотр получают `revision` и перечитывают данные при его
изменении; предпросмотр — с задержкой 400 мс, чтобы серия сохранений не
запускала серию прогонов CLI.

## Risks / Trade-offs

- **Прогон CLI на копии стоит ~0,5 с и копирования `openspec/`** →
  предпросмотр строится по запросу (открытие подтверждения, вкладки, команды), а
  не на каждое изменение доски; копируется только нужное.
- **Временный каталог может остаться при аварийном завершении** → имя с
  префиксом `openspec-ide-preview-` в системном каталоге временных файлов,
  который ОС чистит сама; удаление в `finally` покрывает обычный путь.
- **Формат `--json` вывода `archive` может измениться** → при неразбираемом
  выводе предпросмотр отдаёт исход `refused` с выводом CLI целиком, а не
  выдумывает результат.
- **Дата в имени архива копии** не используется: сравниваются только
  `openspec/specs/`.

## Migration Plan

1. `core`: построчное сравнение и изменения спека по требованиям.
2. `server`: сервис предпросмотра, маршрут, пути файлов артефактов в карточке.
3. `web`: компонент предпросмотра, новая доска и панель деталей, вкладка в
   дельтах, тема VS Code для элементов управления.
4. `vscode`: провайдер виртуальных документов, команда, сообщение панели,
   сводка в подтверждении архивации.
5. Макеты и README.

Откат — удалить маршрут и компоненты: данные и файлы проекта не меняются.
