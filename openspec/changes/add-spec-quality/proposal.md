# Change: проверка качества спеков

## Why

`openspec validate` проверяет форму спека: разделы на месте, в требовании
есть SHALL, у требования есть сценарий с WHEN и THEN. Спека, которая проходит
`validate --strict`, всё равно может быть плохой, и дефекты всплывают только
на ревью или в реализации:

- код ошибки есть в тексте требования, но ни один сценарий его не проверяет —
  или наоборот, THEN ждёт код, правило для которого нигде не описано;
- условие «если …» в тексте не покрыто сценарием, из перечисления «как X, так
  и Y» проверен только X, на интервал [`minTtl`, `maxTtl`] нет сценариев на
  самих границах — мутант `>=` → `>` такую спеку переживает;
- THEN проверяет `sessionCache.getCacheSize()` или «сессия в кэш не
  создаётся» — то, что снаружи не видно и в контрактный тест не переводится;
- «валидный запрос», «корректный ответ», «и т. д.» — формулировки, по которым
  нельзя написать проверку;
- подлежащее скачет между «кластер» и «Master», Purpose обещает healthcheck,
  о котором нет ни одного требования.

Эти проверки детерминированы: их можно сделать регулярными выражениями и
разбором markdown, без LLM, и показывать там же, где остальные замечания, —
при наборе в редакторе и в CI.

## What Changes

Новая возможность `spec-quality` — линтер содержания требований основных
спеков и дельт активных changes. Правила (в скобках — номер из исходной идеи):

| Правило | Что проверяет | Уровень по умолчанию |
| --- | --- | --- |
| `error-code-trace` (R1) | коды ошибок текста и THEN совпадают | предупреждение |
| `branch-coverage` (R2) | условия «если / когда / при» покрыты WHEN | сведение |
| `enumeration-coverage` (R3) | каждый элемент перечисления из `кода` есть в сценарии | предупреждение |
| `boundary-values` (R4) | на интервалы и пороги есть сценарии на границе и за ней | предупреждение |
| `clamp-arithmetic` (R5) | THEN = clamp(x, min, max) для правил приведения к интервалу | предупреждение |
| `implementation-leak` (R6) | в WHEN/THEN нет вызовов методов и внутренних имён | предупреждение |
| `parameter-registry` (R7) | camelCase-параметры объявлены в Glossary/Configuration или настройках | предупреждение |
| `actor-dictionary` (R8) | подлежащее при SHALL — из словаря акторов | предупреждение |
| `vague-wording` (R9) | нет расплывчатых слов; плотность на 100 слов | предупреждение |
| `observable-then` (R10) | THEN проверяет наблюдаемое, а не кэш и внутреннее состояние | предупреждение |
| `negative-scenarios` (R11) | у требования с отказом есть и негативный, и позитивный сценарий | предупреждение |
| `atomicity` (R12) | нормативные предложения требования — об одном предмете | сведение |
| `purpose-coverage` (R13) | сущности из Purpose покрыты требованиями | сведение |
| `error-code-registry` | коды спек — в реестре кодов проекта, и наоборот | предупреждение / сведение |
| `metric-threshold` | сводная метрика не хуже порога | ошибка |

- **Где видно**: панель «Проблемы» VS Code — сразу при наборе, источник
  `openspec-quality`, код — имя правила; проверка `quality` команды
  `openspec-ide-check` с именем правила в каждом замечании.
- **Метрики**: `errorCodeTraceability`, `branchCoverage`, `boundaryCoverage`,
  `ambiguityDensity` — в итоге `openspec-ide-check` (text и json); пороги
  метрик в настройках превращают их в ошибку для CI.
- **Настройки** — необязательный `openspec/quality.yaml`: область проверки
  (все спеки или только дельты), уровни правил и их выключение, шаблон и
  реестр кодов ошибок, словарь акторов, глоссарий и параметры, пополнение и
  сокращение словарей, пороги метрик. Без файла действуют умолчания; правила,
  которым нужен словарь, без него молчат.

Не входит:

- **Уровень 2 исходной идеи** — извлечение decision table с помощью LLM и
  проверка полноты, противоречий и пересечений требований кодом. IDE не
  вызывает LLM (ADR-006); путь — навык для агента, который пишет таблицу в
  файл, и детерминированная проверка этого файла, — отдельный change.
- **Уровень 3** — генерация контрактных тестов из сценариев, трассируемость
  сценарий → тест и мутационное тестирование спеки; метрики
  `scenario_testability` и `mutation_score` не считаются.
- Сверка имён DTO и полей с OpenAPI и кластеризация синонимов терминов.
- Раздел или карточка в панели webview: замечания и метрики — в «Проблемах»
  и в CI.

## Capabilities

### New Capabilities

- `spec-quality` — проверка качества содержания спеков: правила, настройки,
  метрики, замечания в редакторе и в CI.

### Modified Capabilities

Нет.

## Impact

- **Код**: `packages/core/src/specQuality.ts` — разбор требований со строками
  и правила (чистые функции); `packages/core/src/specQualityConfig.ts` —
  разбор настроек и реестра кодов; `packages/server/src/quality.ts` — чтение
  `openspec/quality.yaml` и файлов реестра; `/api/authoring` отдаёт настройки
  в поле `quality`; `packages/vscode/src/authoring.ts` — коллекция
  диагностик `openspec-quality`; `packages/server/src/check.ts` и
  `packages/check` — проверка `quality` и строка метрик в отчёте.
- **API**: у `GET /api/authoring` новое поле `quality`; его читает только
  расширение в том же процессе, ревизия API не меняется.
- **Файлы проекта**: необязательный `openspec/quality.yaml`; в этом
  репозитории — строка `quality.yaml?: file` в `openspec/structure.yaml`.
- **Этот репозиторий**: проверка `quality` даёт предупреждения и сведения, но
  не ошибки — `npm run check:openspec` по-прежнему проходит с кодом 0.
