# Design: проверка основных спеков и точные строки замечаний

## Context

Мотивация — в `proposal.md`. CLI 1.13 умеет `validate --specs --json`; отчёт
тот же, что у changes, но путь замечания — это путь в модели спека
(`requirements[0]`, `requirements.0.scenarios`, `overview`), а не путь файла.

## Decisions

### 1. Один прогон на все спеки, а не по спеку

**Решение.** `openspec validate --specs --strict --json` одним процессом;
прогон, начатый до завершения предыдущего, прерывает его — так же, как
`ValidationRunner` поступает с changes.

**Альтернатива — `validate <spec> --type spec` на каждый изменённый спек.**
Быстрее на одном файле, но архивация меняет несколько спеков сразу, а
запуск Node-процесса CLI стоит дороже, чем проверка всех спеков внутри одного
процесса (на этом репозитории — 11 спеков за доли секунды).

### 2. Строка — по разбору файла, а не по тексту сообщения

**Решение.** Для основного спека индекс из `requirements[N]` или
`requirements.N` берётся по порядку заголовков `### Requirement:` в файле
(`parseSpecMarkdown`), `overview`/`purpose` — строка `## Purpose`. Для
замечаний change имя требования извлекается из сообщения по трём формам,
которые использует CLI, и ищется в файле дельты без учёта регистра и лишних
пробелов, как сравнивает заголовки сам OpenSpec.

**Альтернатива — только номер строки из текста сообщения.** Так сделано
сейчас, но CLI строк почти не сообщает, и замечания ложатся на начало файла.

### 3. Отдельная коллекция диагностик

**Решение.** Замечания основных спеков — в своей коллекции `openspec-specs`:
они снимаются и ставятся целиком за прогон и не смешиваются с замечаниями
changes, которые снимаются по change.

**Альтернатива — общая коллекция.** Пришлось бы помнить, какие файлы чьи;
при архивации change и одновременной перепроверке спеков это даёт гонки.

## Risks / Trade-offs

- Формат путей замечаний не документирован CLI → неизвестный путь даёт
  строку 1 файла спека, замечание не теряется.
