# Design: метрики запусков агента по задачам OpenSpec

## Context

Мотивация — в `proposal.md`, требования — в дельте `specs/task-metrics`.
Журнал метрик (`packages/server/src/metricsStore.ts`, файл `runs.jsonl` в
каталоге `.openspec-ide`), событие `run-finished` и свёртка в `ItemRecord.runs`
(`packages/core/src/metrics.ts`) уже есть; метод `MetricsService.recordRun`
(`packages/server/src/metrics.ts`) после ADR-006 никто не вызывает. Change
добавляет источник событий снаружи IDE и метрики, которые связывают расход
агента с качеством контекста.

Схема потока:

1. Агент работает в терминале или своём редакторе. Его хук после каждого
   ответа (`Stop` у Claude Code) пишет отчёт `openspec-run/1` в
   каталог `.openspec-ide/inbox`.
2. Бэкенд IDE (или `openspec-ide-check --only metrics` в CI) проверяет отчёт,
   привязывает запуск к change и пункту плана, пишет `run-finished` в журнал
   и удаляет отчёт.
3. Раздел «Метрики» показывает расход по задачам, changes, сценариям и
   модулям; модули с высокой долей разведки — кандидаты на промпт 3 навыка
   `context-audit`.

## Формат отчёта

Один файл `<runId>.json` на запуск; поля без значения пропускаются или равны
`null` — это «нет данных», а не ноль.

```json
{
  "schema": "openspec-run/1",
  "runId": "claude-code:<session_id>:<uuid последнего сообщения>",
  "agent": "claude-code",
  "model": "<идентификатор модели из транскрипта>",
  "startedAt": "2026-10-15T09:12:03Z",
  "finishedAt": "2026-10-15T09:19:40Z",
  "outcome": "success",
  "change": "add-limits",
  "item": "2.1",
  "tokens": { "input": 1200, "cacheRead": 48000, "cacheWrite": 6000, "output": 900 },
  "toolCalls": 40,
  "callsBeforeFirstEdit": 12,
  "searches": 7,
  "filesRead": ["packages/core/src/metrics.ts"],
  "filesEdited": ["packages/core/src/metrics.ts", "openspec/changes/add-limits/tasks.md"]
}
```

`outcome` — значения `RunOutcome` из `packages/core/src/metrics.ts`. Пути —
от корня рабочего пространства; пути вне корня отбрасываются.

Подключение адаптера Claude Code — хук в `.claude/settings.json` проекта:

```json
{ "hooks": { "Stop": [ { "hooks": [ { "type": "command",
  "command": "npx openspec-ide-check report-run" } ] } ] } }
```

## Decisions

### 1. Каталог inbox, а не запись в журнал напрямую

**Решение.** Хук пишет отдельный файл на запуск в inbox; в журнал пишет
только бэкенд IDE или `openspec-ide-check`.

**Альтернатива — хук дописывает строку в `runs.jsonl`.** Проще, но снимок
`metrics.json` хранит число применённых строк журнала, а несколько агентов
пишут параллельно; привязка к пункту плана требует разбора `tasks.md` и
событий доски, которых у хука нет. Inbox развязывает их: хук ничего не знает
о модели метрик, IDE может быть закрыта.

### 2. Отчёт не зависит от агента

**Решение.** Формат `openspec-run/1` описывает запуск через то, что есть у
любого агента: токены, вызовы инструментов, файлы. Адаптер Claude Code —
одна команда; для GigaCode, Codex и других — свой адаптер, пишущий тот же
формат.

**Альтернатива — OpenTelemetry агента.** Claude Code умеет отдавать метрики
расхода токенов и стоимости по OpenTelemetry. Но для этого нужен коллектор,
а в метриках нет прочитанных файлов и порядка вызовов — без них не посчитать
долю разведки. OpenTelemetry остаётся источником для командных дашбордов
вне IDE.

### 3. Привязка по цепочке правил

**Решение.** Явные поля отчёта (адаптер берёт их из переменных
`OPENSPEC_CHANGE` и `OPENSPEC_TASK`) → единственный пункт «в работе» →
единственный пункт, отмеченный во время запуска → change по изменённым
файлам → «вне change». Неоднозначность не угадывается: два отмеченных пункта
дают привязку к change без пункта.

**Альтернатива — только явная привязка.** Точная, но требует дисциплины:
забытая переменная — и все запуски «вне change». Цепочка покрывает типичный
поток `/opsx:apply`, где агент сам отмечает пункты.

### 4. Доля разведки вместо «промахов контекста»

**Решение.** Метрика контекста — доля вызовов инструментов до первой правки
файла, число поисков и файлов, прочитанных без правки. Она считается по
транскрипту без знания о наборе контекста.

**Альтернатива — промахи относительно набора контекста модуля** (чтения
файлов вне набора). Точнее говорит о контексте, но набор зависит от того, что
человек передал агенту строками `@путь`, а этого в отчёте нет; чтение кода
модуля — норма, а не промах. Промахи остаются метрикой задачных проб навыка
`context-audit`, где набор известен.

### 5. Токены по видам, без цены

**Решение.** Хранить `input`, `cacheRead`, `cacheWrite`, `output` и модель;
стоимость не считать.

**Альтернатива — стоимость в долларах.** Удобна, но цены меняются, у команд
разные тарифы, а пересчёт истории по новым ценам невозможен без видов токенов.
Виды токенов позволяют посчитать стоимость в экспорте по любой таблице цен.
Кэш показывается отдельно: у агентов с кэшем промпта `cacheRead` — основная
часть входа, и сумма без разбивки завышает цену задачи в разы.

### 6. Журнал остаётся локальным

**Решение.** Каталог `.openspec-ide` по-прежнему в `.gitignore`; командная
сводка — через существующий экспорт метрик (CI-артефакт или внешний отчёт).

**Альтернатива — коммитить сводку в каталог change при архивации.** История
расхода жила бы рядом с требованиями, но артефакты OpenSpec менялись бы
записью метрик — это запрещает требование «Хранение метрик отдельно от
артефактов» — и в репозиторий попадали бы данные одного разработчика.

## Risks / Trade-offs

- Формат транскрипта Claude Code не документирован как стабильный: адаптер
  читает только `message.usage`, `message.model` и блоки `tool_use`, при
  ошибке разбора молчит (код 0), а тест на записанном транскрипте ловит
  изменение формата.
- Отчёт содержит пути файлов и имя модели, но не текст промптов и ответов —
  inbox не становится копией переписки.
- Доля разведки зависит от стиля работы: задача «разберись, почему падает»
  законно состоит из одной разведки. Поэтому порог кандидата на аудит — по
  модулю и не меньше 5 запусков, а не по отдельному запуску.
