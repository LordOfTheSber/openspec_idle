# Change: спека модуля, связи между модулями и с кодом

## Why

В монорепо команды у каждого модуля — сервиса, UI, библиотеки КМ — одна
спека, которая описывает всю его логику: `specs/billing/spec.md`,
`specs/km/core/spec.md`. Такая спека быстро дорастает до десятков требований и
сотен сценариев, и в нынешнем виде IDE с ней неудобна:

- спека показывается сплошным списком требований, без разделов и оглавления;
  найти нужное требование можно только прокруткой или поиском по всему
  репозиторию;
- разбить спеку на разделы заголовками `##` нельзя: CLI OpenSpec молча
  теряет требования после такого заголовка (проверено на 1.13.1 — из трёх
  требований `show` вернул два, `validate` упал);
- требования одного модуля опираются на требования другого — сервис на
  библиотеку КМ, UI на сервис, — но эти связи живут только в голове: у
  требования нельзя увидеть, кто на него ссылается;
- связи требования с кодом нет: неизвестно, где требование реализовано, есть
  ли на него тесты и что из спеки не покрыто вовсе.

## What Changes

- **Чтение спеки модуля.** Разделы из имени требования `Раздел / Требование`:
  такой формат CLI принимает, включая дельты MODIFIED и архивацию. Оглавление
  с числом требований, поиск внутри спеки, прямые ссылки на требование,
  карточка требования со сценариями, статусом в активных changes и историей по
  архиву. Предупреждение о заголовках `##`, из-за которых CLI теряет
  требования.
- **Связи между модулями на уровне требований.** Ссылка — обычная
  markdown-ссылка на требование спеки другого модуля, которую GitHub и GitLab
  тоже показывают кликабельной. Вставка ссылки выбором требования, обратные
  ссылки («кто на меня ссылается»), битые ссылки, связи требований на графе
  модулей и их расхождение с зависимостями из карты модулей.
- **Связь с кодом.** Метка `@spec <модуль>: <требование>` в комментарии кода или
  теста на любом языке плюс тесты, названные по сценариям, как «вероятное»
  покрытие. У требования видны реализация и тесты с переходом к строке:
  фрагмент прямо в IDE или открытие в IntelliJ IDEA или VS Code. Покрытие
  спеки, требования без кода и тестов, битые метки после переименования.

## Capabilities

### New Capabilities

- `module-spec-view`: структура и навигация большой спеки модуля, карточка
  требования, статус в активных changes, история, проверка формата.
- `spec-cross-links`: ссылки на требования других модулей, их вставка и
  проверка, обратные ссылки, связи требований на графе модулей.
- `code-traceability`: метки `@spec` в коде и тестах, покрытие по именам
  сценариев, переход к коду и открытие в редакторе, покрытие спеки, битые метки.

### Modified Capabilities

Нет. Опирается на карту модулей из `add-monorepo-modules`: модулю
соответствует спека, путь которой совпадает с префиксом спеков модуля, а
метки ищутся в его каталоге кода.

## Impact

- `packages/core`: разбор разделов из имён требований, якоря в стиле GitHub,
  разбор ссылок между спеками, разбор меток `@spec`, расчёт покрытия.
- `packages/server`: индекс меток по каталогам кода модулей с инкрементальным
  обновлением, история требований по архиву, запуск внешнего редактора.
- `packages/web`: экран спеки модуля, выбор требования для ссылки, панель
  трассировки, связи требований на графе модулей.
- Соглашение для команды: формат имени требования с разделом и формат метки
  `@spec` описываются в README.
