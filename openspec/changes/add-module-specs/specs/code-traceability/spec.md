# Spec Delta: code-traceability

## Purpose

Связывает требования спеки модуля с кодом и тестами: где требование
реализовано, чем проверено, что в спеке не покрыто ничем. Связь задаётся меткой
в комментарии на любом языке и дополняется тестами, названными по сценариям.

## ADDED Requirements

### Requirement: Метки требований в коде

Система ДОЛЖНА (SHALL) находить в файлах каталога кода модуля метки вида
`@spec <модуль>: <имя требования>` в любом комментарии, независимо от языка.
Имя требования ДОЛЖНО сравниваться без учёта регистра и повторных пробелов.
Файл ДОЛЖЕН считаться тестом, если его путь подходит под шаблоны тестов
(по умолчанию каталоги `test`, `tests`, `__tests__` и имена `*Test.*`,
`*Tests.*`, `*.test.*`, `*.spec.*`, `*_test.*`); шаблоны настраиваются.

#### Scenario: Метка в реализации

- **WHEN** в файле `services/billing/src/main/kotlin/InvoiceNumbers.kt` есть комментарий `// @spec billing: Счета / Нумерация счетов`
- **THEN** у требования «Счета / Нумерация счетов» модуля `billing` показана реализация `InvoiceNumbers.kt` со строкой метки

#### Scenario: Метка в тесте

- **WHEN** метка стоит в файле `services/billing/src/test/kotlin/InvoiceNumbersTest.kt`
- **THEN** файл показан в тестах требования, а не в реализации

#### Scenario: Метка на требование другого модуля

- **WHEN** в коде `billing` стоит метка `@spec km/core: Кэш ответов`
- **THEN** место показано у требования `km/core` как использование в модуле `billing`

### Requirement: Вероятное покрытие по именам сценариев

Система ДОЛЖНА (SHALL) считать тест вероятно покрывающим сценарий, если в тестовом
файле модуля встречается строка или имя теста, совпадающее с именем сценария
без учёта регистра, пробелов и знаков препинания. Такое покрытие ДОЛЖНО
отличаться в интерфейсе от покрытия меткой.

#### Scenario: Тест назван по сценарию

- **WHEN** в тестовом файле модуля есть тест `` `Полный возврат` `` или строка `"полный возврат"`, а у требования есть сценарий «Полный возврат»
- **THEN** сценарий показан как вероятно покрытый этим тестом с пометкой «по имени»

#### Scenario: Совпадение вне тестов

- **WHEN** строка с именем сценария встречается только в нетестовом файле
- **THEN** это не считается покрытием

### Requirement: Переход к коду

Система ДОЛЖНА (SHALL) показывать у требования список мест реализации и тестов с
файлом и строкой, фрагмент кода вокруг метки прямо в IDE без возможности правки
и открытие места во внешнем редакторе на нужной строке. Внешний редактор —
IntelliJ IDEA или VS Code — ДОЛЖЕН выбираться в настройках вместе с командой
его запуска.

#### Scenario: Просмотр фрагмента

- **WHEN** пользователь раскрывает место реализации у требования
- **THEN** показан фрагмент файла вокруг строки метки с подсветкой этой строки

#### Scenario: Открытие в IntelliJ IDEA

- **WHEN** в настройках выбран IntelliJ IDEA и пользователь нажимает «Открыть в редакторе»
- **THEN** выполняется команда запуска IDEA с файлом и номером строки

#### Scenario: Открытие в VS Code

- **WHEN** в настройках выбран VS Code
- **THEN** выполняется `code -g <файл>:<строка>`

#### Scenario: Редактор не найден

- **WHEN** команда редактора не найдена
- **THEN** показывается сообщение с проверенными путями и ссылкой на настройки
- **AND** фрагмент в IDE остаётся доступен

### Requirement: Покрытие спеки

Система ДОЛЖНА (SHALL) показывать для каждого требования состояние покрытия: код и
тесты, только код, только тесты, вероятно по именам, нет покрытия, — и для
спеки модуля долю требований в каждом состоянии, с фильтром по состоянию.

#### Scenario: Требования без покрытия

- **WHEN** пользователь выбирает в обзоре модуля «без покрытия»
- **THEN** в спеке остаются показаны требования, у которых нет ни меток, ни тестов по именам

#### Scenario: Сводка покрытия

- **WHEN** спека модуля открыта
- **THEN** в обзоре показаны доли требований с кодом и тестами, только с кодом, только с тестами и без покрытия

### Requirement: Битые метки

Система ДОЛЖНА (SHALL) показывать метки, которые не разрешаются до требования: модуль
или требование не существуют. Для метки со старым именем переименованного
требования ДОЛЖНО предлагаться новое имя. Для требования, переименовываемого в
активном change, ДОЛЖНЫ перечисляться метки, которые придётся обновить.

#### Scenario: Требование переименовано

- **WHEN** метка ссылается на имя требования, переименованного в архивном change
- **THEN** метка показана битой с файлом и строкой и предложенным новым именем

#### Scenario: Переименование в активном change

- **WHEN** активный change содержит дельту RENAMED для требования с метками в коде
- **THEN** в деталях change перечислены метки, которые нужно обновить после реализации

### Requirement: Индекс меток

Система ДОЛЖНА (SHALL) строить индекс меток в фоне по каталогам кода модулей, не
блокируя работу, пропуская каталоги зависимостей и сборки и файлы из
`.gitignore`, и обновлять его по изменённым файлам. Время последней индексации
и её ход ДОЛЖНЫ быть видны.

#### Scenario: Первое открытие репозитория

- **WHEN** репозиторий открыт впервые
- **THEN** спеки доступны сразу, а покрытие показывает ход индексации до её завершения

#### Scenario: Код изменён

- **WHEN** разработчик добавил метку в файл и сохранил его
- **THEN** требование получает новое место реализации без полной переиндексации
