# Design: спека модуля, связи между модулями и с кодом

## Context

Каждый модуль монорепо — сервис, UI, библиотека КМ — описан одной спекой:
`openspec/specs/<модуль>/spec.md`. Модуль в карте `openspec/modules.yaml`
(change `add-monorepo-modules`) задаёт каталог кода и префикс спеков; при одной
спеке на модуль префикс совпадает с путём этой спеки.

Проверено на CLI OpenSpec 1.13.1:

- заголовок `##` после `## Requirements` обрывает раздел: требования ниже CLI
  не видит, `show` их не возвращает, `validate` падает;
- имя требования вида `Счета / Нумерация счетов` принимается `validate`,
  дельтой MODIFIED и архивацией;
- markdown-ссылка в тексте требования сохраняется в выводе `show --json` как
  есть.

## Goals / Non-Goals

### Goals

- Большая спека читается как документ с оглавлением, а не как список.
- Все соглашения — внутри форматов, которые понимает CLI и которые читаются
  без IDE: имя требования, markdown-ссылка, комментарий в коде.
- Связь с кодом работает для любого языка и не требует плагинов сборки.

### Non-Goals

- Разбор синтаксиса языков программирования. Метка ищется в тексте файла.
- Запуск тестов и чтение их отчётов. Покрытие — наличие меток и тестов по
  именам, а не результат прогона. Прогон остаётся за проверкой приёмки в
  метриках.
- Правка кода из IDE. Фрагмент показывается только для чтения, правка — во
  внешнем редакторе.

## Decisions

### 1. Раздел — в имени требования через ` / `

**Решение.** `### Requirement: Счета / НДС / Округление` — раздел «Счета»,
подраздел «НДС», требование «Округление». Разделитель — косая черта с
пробелами, чтобы не спутать с путями и датами внутри имени.

**Альтернативы.** Заголовки `##` внутри спеки ломают CLI (см. Context).
Разбить модуль на несколько capability (`billing/invoices`,
`billing/refunds`) — родной для OpenSpec путь, но команда выбрала одну спеку на
модуль, чтобы вся логика сервиса читалась в одном месте. Раздел в имени
сохраняет одну спеку и не ломает CLI.

**Цена.** Имя требования длиннее, а дельта MODIFIED повторяет его целиком,
вместе с разделом. Переименование раздела — это RENAMED всех его требований.

### 2. Ссылка — markdown со слагом в стиле GitHub

**Решение.** `[km/core: Кэш ответов](../km/core/spec.md#requirement-кэш-ответов)`.
Якорь строится как у GitHub: нижний регистр, пробелы в дефисы, знаки
препинания кроме дефиса убираются, буквы любого алфавита сохраняются. Для
`Requirement: Счета / Нумерация счетов` это
`#requirement-счета--нумерация-счетов`: двойной дефис остаётся на месте
удалённой косой черты. Путь относительный от файла спеки.

**Альтернатива** — короткая запись `@km/core: Кэш ответов` в тексте. Её проще
набирать, но вне IDE она — просто текст. Ссылку в markdown GitHub и GitLab
показывают кликабельной, а набирать её руками не нужно: есть вставка из
редактора.

**Ссылка из дельты.** Дельта лежит в `changes/<name>/specs/<cap>/spec.md`, а
после архивации текст переезжает в `specs/<cap>/spec.md`. Глубина каталогов у
них разная, поэтому путь относительно дельты сломался бы. IDE строит путь
относительно итогового места спеки — `specs/<cap>/` — и разрешает его так же в
обоих местах.

### 3. Метка в коде — `@spec <модуль>: <требование>` в любом комментарии

**Решение.** Метка ищется регулярным выражением по тексту файла, без разбора
языка: `@spec\s+([\w./-]+)\s*:\s*(.+?)\s*(?:\*/|-->|$)`. Хвост закрывающего
комментария отрезается. Регистр и повторные пробелы в имени требования не
важны.

**Почему без привязки к синтаксису комментариев.** В монорепо Kotlin, Java,
TypeScript, SQL и YAML. Разбор комментариев каждого языка — большая работа
ради мелкого выигрыша: ложное срабатывание в строковом литерале почти
невозможно, `@spec модуль: имя` в строке кода никто не пишет случайно.

**Что считать тестом.** Шаблоны путей по умолчанию покрывают соглашения
Maven и Gradle (`src/test/`), Jest и Vitest (`*.test.*`, `*.spec.*`,
`__tests__`), Go (`*_test.go`) и Python (`tests/`, `test_*.py`). Шаблоны
настраиваются в карте модулей на уровне репозитория.

### 4. Вероятное покрытие — только в тестах и только по имени сценария

**Решение.** Имя сценария нормализуется: нижний регистр, без пунктуации,
пробелы схлопнуты. Затем ищется в тестовых файлах модуля среди строковых
литералов и идентификаторов в обратных кавычках (Kotlin) или в `@DisplayName`.
Совпадение отмечается «по имени» и визуально отличается от метки.

**Почему отдельно от меток.** Совпадение имени — догадка. Смешать её с явной
меткой значит завысить покрытие.

### 5. Индекс меток — в фоне, инкрементально, с кэшем

**Решение.** Индекс строится в рабочем потоке сервера: обход каталогов кода
модулей с пропуском каталогов зависимостей и сборки и файлов из `.gitignore`,
только текстовые файлы до 1 МБ. Кэш — в `.openspec-ide/code-index.json` по
пути, размеру и времени изменения; при следующем открытии перечитываются
только изменённые файлы. Во время работы за каталогами кода следит наблюдатель
с тем же фильтром.

**Альтернатива** — искать через `git grep` по запросу. Это быстро, но не
работает вне git-репозитория и не даёт сводного покрытия без полного прохода.

### 6. Внешний редактор — команда из настроек

**Решение.** В настройках выбирается редактор и команда: IDEA —
`idea --line <n> <файл>` (на Windows `idea64.exe`), VS Code —
`code -g <файл>:<n>`. Команда запускается без оболочки, через разбор обёрток
из `packages/server/src/process/platform.ts`. Если команда не найдена,
показываются проверенные пути, а фрагмент в IDE остаётся доступным.

### 7. История требования — по дельтам архива

**Решение.** История собирается разбором дельт в
`openspec/changes/archive/*/specs/<cap>/spec.md` по имени требования, с учётом
цепочки RENAMED. Дата — из имени каталога архива (`YYYY-MM-DD-<name>`).

**Альтернатива** — `git log` по файлу спеки. Он показывает коммиты, а не
changes. К тому же без git история была бы недоступна.

## Risks / Trade-offs

- **Метки устаревают.** Переименовали требование — метки в коде битые. Это
  видно сразу, с предложенным новым именем, а change с RENAMED заранее
  перечисляет метки, которые нужно обновить.
- **Большой монорепо.** Первая индексация на десятках тысяч файлов занимает
  секунды. Спеки при этом доступны сразу, а кэш делает повторные открытия
  быстрыми.
- **Длинные имена требований.** Цена раздела в имени. Смягчается тем, что
  IDE показывает внутри раздела только короткое имя.

## Migration Plan

Существующие спеки без разделов показываются разделом «Общее». Переход к
разделам — переименование требований обычным change с дельтами RENAMED.
Спеки с заголовками `##` внутри требований IDE находит и показывает, какие
требования CLI сейчас не видит.
