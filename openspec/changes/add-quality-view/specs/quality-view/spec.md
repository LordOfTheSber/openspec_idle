# Spec Delta: quality-view

## ADDED Requirements

### Requirement: Раздел «Качество»

Панель ДОЛЖНА (SHALL) иметь раздел «Качество» между «Метриками» и
«Контекстом» и команду VS Code «OpenSpec: Качество спеков». Раздел ДОЛЖЕН
показывать четыре метрики проекта (трассируемость кодов ошибок, покрытие
ветвлений, покрытие границ, расплывчатость) с числителем и знаменателем и
порогом из настроек, фильтр по уровню со счётчиками, переключатель «по
файлам / по правилам», поиск по тексту, файлу и правилу и флажок «только
активные changes». В режиме «по файлам» слева ДОЛЖНЫ быть правила по группам
с числом замечаний (правила без замечаний свёрнуты, щелчок фильтрует), справа
— файлы по убыванию ошибок и предупреждений с метриками каждого; щелчок по
файлу ДОЛЖЕН открывать его замечания, сгруппированные по требованиям, с
переходом к строке в редакторе. Изменение файлов проекта ДОЛЖНО
пересчитывать раздел без действий пользователя.

#### Scenario: Файлы по убыванию предупреждений

- **WHEN** у дельты `data-export` одно предупреждение `vague-wording`, и пользователь открывает раздел «Качество»
- **THEN** в таблице файлов есть строка `data-export` с одним предупреждением, а плитка расплывчатости показывает «1 слово»

#### Scenario: Изменение файлов проекта

- **WHEN** раздел открыт, и в дельту `data-export` вне IDE дописано второе расплывчатое слово
- **THEN** счётчик предупреждений раздела становится 2 без действий пользователя

#### Scenario: Замечания файла по требованиям

- **WHEN** пользователь щёлкает строку `data-export`
- **THEN** справа открываются замечания файла под заголовком требования «Выгрузка данных» с номером строки и кнопкой перехода в редактор

### Requirement: Уровень правила из раздела

Карточка правила в режиме «по правилам» ДОЛЖНА (SHALL) показывать название,
описание правила и все его замечания по файлам и давать выбрать уровень:
«по умолчанию», ошибка, предупреждение, сведение или «выключено». Выбор
ДОЛЖЕН записываться в `rules` файла `openspec/quality.yaml` (отсутствующий
файл создаётся, комментарии сохраняются), «по умолчанию» — убирать правило
из `rules`. Выключенное правило ДОЛЖНО помечаться в списке правил «выкл.» и не
давать замечаний.

#### Scenario: Правило выключено из раздела

- **WHEN** пользователь выбирает для `vague-wording` уровень «выключено»
- **THEN** в `openspec/quality.yaml` появляется `vague-wording: off`, а правило в списке помечено «выкл.»

#### Scenario: Уровень по умолчанию

- **WHEN** у правила `vague-wording` в `rules` записан `off`, и пользователь выбирает «по умолчанию»
- **THEN** строка `vague-wording` уходит из `rules`, а у правила снова уровень «предупреждение» и его замечания

### Requirement: Исключения правил

Система ДОЛЖНА (SHALL) читать из ключа `exclude` файла
`openspec/quality.yaml` список исключений: правило (`rule`, пусто — все
правила), путь (`path`: файл, каталог со всем содержимым или шаблон с `*`,
`**`, `?`; пусто — любой файл), требование (`requirement`, пусто — всё
требования файла) и причину (`reason`). Замечание, подходящее под
исключение, НЕ ДОЛЖНО попадать в панель «Проблемы» и в проверку `quality`
команды `openspec-ide-check`. Файл, исключённый целиком (без `rule` и
`requirement`), ДОЛЖЕН не входить в сводные метрики и пороги. Ошибки самих
настроек исключаться НЕ ДОЛЖНЫ. Исключение без правила, пути и требования и
исключение с неизвестным правилом ДОЛЖНЫ давать ошибку настроек.

#### Scenario: Правило в требовании

- **WHEN** в `exclude` записано `rule: vague-wording`, `path` дельты и `requirement: Выгрузка данных`
- **THEN** предупреждения `vague-wording` этого требования нет ни в «Проблемах», ни в отчёте `openspec-ide-check`, а в соседнем требовании оно остаётся

#### Scenario: Старые спеки исключены целиком

- **WHEN** в `exclude` записано только `path: openspec/specs/legacy/**`
- **THEN** у спеков `legacy` нет замечаний, и их слова не входят в метрику расплывчатости проекта

#### Scenario: Исключение без условий

- **WHEN** в `exclude` записано только `reason: просто так`
- **THEN** есть ошибка настроек «не задаёт ни rule, ни path, ни requirement», а исключение не действует

### Requirement: Исключение из раздела

Строка замечания в разделе ДОЛЖНА (SHALL) давать исключить его правило в
этом требовании или во всём файле с необязательной причиной — запись в
`exclude` файла `openspec/quality.yaml`. Раздел ДОЛЖЕН показывать список
исключений с правилом, местом, причиной, числом снятых замечаний и кнопкой
«Снять», а флажок «исключённые (N)» — показывать снятые замечания с причиной
и ссылкой «снять исключение».

#### Scenario: Исключить с причиной

- **WHEN** пользователь у замечания `vague-wording` выбирает «в требовании «Выгрузка данных»», вводит причину «формат из договора» и подтверждает
- **THEN** в `exclude` появляется исключение с этими правилом, путём, требованием и причиной, а счётчик предупреждений становится 0

#### Scenario: Снять исключение

- **WHEN** пользователь нажимает «Снять» у этого исключения
- **THEN** исключение уходит из `openspec/quality.yaml`, а предупреждение возвращается

### Requirement: Пороги, ошибки настроек и отсутствие настроек

Раздел ДОЛЖЕН (SHALL) показывать невыполненный порог метрики плашкой с
последствием для CI и переходом к строке порога, ошибки
`openspec/quality.yaml` — списком со строками, а без файла настроек —
пояснение, что действуют умолчания, и кнопку «Создать quality.yaml», которая
создаёт файл из заготовки с закомментированными примерами. Без спеков и
дельт раздел ДОЛЖЕН объяснять, откуда берутся данные.

#### Scenario: Порог не выполнен

- **WHEN** в настройках порог `ambiguityDensity: 0.05`, а расплывчатость проекта 0,08
- **THEN** раздел показывает плашку «Порог не выполнен: расплывчатых слов на 100 0,08 при пороге 0,05» со ссылкой на строку порога

#### Scenario: Создать настройки

- **WHEN** файла `openspec/quality.yaml` нет, и пользователь нажимает «Создать quality.yaml»
- **THEN** файл создан с `version`, `scope` и `rules` и закомментированными примерами остальных ключей, пояснение об умолчаниях исчезает

### Requirement: Цитата нашлась в другом модуле

Замечание `code-message` ДОЛЖНО (SHALL), если цитата не найдена в коде
модулей домена, но есть в коде другого модуля карты контекста, называть этот
файл и модуль и предлагать добавить домен в `domains` модуля или поправить
спеку.

#### Scenario: Сообщение в модуле без домена

- **WHEN** цитата «Проект не инициализирован» спека домена `runtime` есть только в `packages/vscode/tree.ts` модуля `vscode`, у которого домена `runtime` нет
- **THEN** замечание `code-message` говорит «есть в `packages/vscode/tree.ts` модуля vscode: добавьте домен «runtime» в domains модуля vscode»

### Requirement: Качество на доске и в дереве

Карточка change с ошибками или предупреждениями качества его дельт и
артефактов ДОЛЖНА (SHALL) показывать на доске чип «качество N» с их числом;
панель деталей change — блок «Качество» с разбивкой по файлам и
правилам и переходом в раздел «Качество», ограниченный этим change. Узлы
change и основных спеков в дереве VS Code ДОЛЖНЫ получать в описании
«⚠ N» — число ошибок и предупреждений качества; сведения не считаются.
Качество НЕ ДОЛЖНО блокировать архивацию.

#### Scenario: Чип и переход с доски

- **WHEN** у дельты change `full-feature` одно предупреждение качества, и пользователь открывает его панель деталей и нажимает «Открыть в «Качестве»»
- **THEN** на карточке был чип «качество 1», а раздел «Качество» открывается с пометкой «Только change full-feature» и строкой его дельты

#### Scenario: Счётчик в дереве

- **WHEN** у change `add-x` три предупреждения качества, а у основного спека `billing` одно
- **THEN** описание узла `add-x` в дереве — «3/5 · ⚠ 3», узла `billing` — «⚠ 1»

### Requirement: Узкая панель

Раздел ДОЛЖЕН (SHALL) уже 760 px раскладываться в одну колонку: плитки
метрик — 2×2, файлы — карточками с главной метрикой, список правил — в режиме
«по правилам», замечания файла — вместо списка файлов.

#### Scenario: Панель рядом с редактором

- **WHEN** ширина раздела 420 px
- **THEN** плитки метрик стоят по две в ряд, а файлы показаны карточками без таблицы
