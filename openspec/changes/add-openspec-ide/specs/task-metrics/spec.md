# Spec Delta: task-metrics

## Purpose

Ведёт измеримую картину исполнения плана: по каждому пункту `tasks.md` и по
change целиком собираются состояние, затраченное время, расход работы агента,
затронутые файлы и результат проверки приёмки, чтобы прогресс можно было
оценивать числами, а не ощущением.

## ADDED Requirements

### Requirement: Идентификация пунктов плана

Система ДОЛЖНА (SHALL) присваивать каждому пункту `tasks.md` устойчивый идентификатор,
складывающийся из имени change, порядкового номера группы и номера задачи внутри
группы. При изменении формулировки задачи идентификатор и накопленные метрики
ДОЛЖНЫ сохраняться.

#### Scenario: Разбор списка задач

- **WHEN** IDE читает `tasks.md` с группами и задачами вида `- [ ] 2.3 Текст`
- **THEN** каждая задача получает идентификатор, включающий change, группу и номер
- **AND** текст задачи и её группа сохраняются как атрибуты

#### Scenario: Переформулировка задачи

- **WHEN** текст задачи изменён, а её номер и группа сохранены
- **THEN** метрики задачи остаются привязанными к тому же идентификатору
- **AND** новая формулировка отражается в интерфейсе

#### Scenario: Перенумерация задач

- **WHEN** задача получает новый номер, а её текст совпадает с прежним не менее чем на порог схожести
- **THEN** метрики переносятся на новый идентификатор
- **AND** факт переноса фиксируется в журнале с прежним и новым идентификатором

#### Scenario: Удалённая задача

- **WHEN** задача исчезает из `tasks.md`
- **THEN** её метрики сохраняются и помечаются как относящиеся к удалённой задаче
- **AND** они исключаются из текущих сводных показателей change

#### Scenario: Строка без чекбокса

- **WHEN** в `tasks.md` встречается строка без скобок чекбокса
- **THEN** она не считается задачей и не участвует в метриках

### Requirement: Набор метрик пункта плана

Система ДОЛЖНА (SHALL) хранить для каждого пункта плана: состояние, момент первого
взятия в работу, момент завершения, суммарное время в работе, число запусков
агента и их исходы, израсходованные токены запроса и ответа, время работы
модели, число вызовов инструментов, список затронутых файлов и результат
последней проверки приёмки.

#### Scenario: Задача не начиналась

- **WHEN** по задаче не было ни одного запуска агента и она не бралась в работу
- **THEN** её состояние — «не начата»
- **AND** числовые метрики равны нулю, а временные отметки отсутствуют

#### Scenario: Завершённая задача

- **WHEN** задача отмечена выполненной
- **THEN** фиксируется момент завершения
- **AND** суммарное время в работе перестаёт расти
- **AND** вычисляется время цикла от первого взятия в работу до завершения

#### Scenario: Задача возвращена в работу

- **WHEN** с выполненной задачи снимается отметка
- **THEN** момент завершения очищается
- **AND** накопленные значения расхода агента сохраняются
- **AND** число возвратов в работу увеличивается на единицу

#### Scenario: Метрики недоступны для части показателей

- **WHEN** запуск агента не сообщил расход токенов
- **THEN** соответствующий показатель отображается как «нет данных»
- **AND** он не подменяется нулём в сводных значениях

### Requirement: Метрика приёмки задачи

Система ДОЛЖНА (SHALL) извлекать из текста задачи её критерий приёмки — часть
формулировки, описывающую способ проверки, — и позволять привязать к задаче
команду проверки. Результат выполнения команды ДОЛЖЕН сохраняться как последний
результат приёмки задачи.

#### Scenario: Критерий приёмки в тексте задачи

- **WHEN** задача сформулирована как «... и проверить, что тест X проходит»
- **THEN** в карточке задачи отдельно показан критерий приёмки
- **AND** он не редактируется отдельно от текста задачи

#### Scenario: Задача без критерия приёмки

- **WHEN** в формулировке задачи не удаётся выделить способ проверки
- **THEN** задача помечается как не имеющая критерия приёмки
- **AND** это отражается в сводном показателе качества плана

#### Scenario: Запуск проверки приёмки

- **WHEN** пользователь запускает привязанную к задаче команду проверки
- **THEN** сохраняются код возврата, длительность и момент запуска
- **AND** задача получает признак «приёмка пройдена» только при нулевом коде возврата

#### Scenario: Отметка выполнения при непройденной приёмке

- **WHEN** пользователь отмечает выполненной задачу, чья последняя проверка приёмки завершилась неуспешно
- **THEN** отметка выполняется
- **AND** задача дополнительно помечается признаком расхождения с приёмкой

### Requirement: Сводные метрики change

Система ДОЛЖНА (SHALL) вычислять по change: долю выполненных задач, суммарный и средний
расход токенов на задачу, суммарное время работы агента, число задач без
критерия приёмки, число задач с расхождением приёмки и время с момента
последнего изменения файлов change.

#### Scenario: Просмотр сводки change

- **WHEN** пользователь открывает панель метрик change
- **THEN** показаны доля выполненных задач, расход токенов и время работы агента
- **AND** значения сопровождаются указанием числа задач, на которых они посчитаны

#### Scenario: Сводка при отсутствии данных

- **WHEN** ни по одной задаче change нет данных о расходе
- **THEN** показатели расхода отображаются как «нет данных»
- **AND** доля выполненных задач по-прежнему вычисляется из `tasks.md`

#### Scenario: Сравнение задач по расходу

- **WHEN** пользователь сортирует задачи по израсходованным токенам
- **THEN** задачи упорядочиваются по убыванию значения
- **AND** задачи без данных помещаются в конец списка

### Requirement: Хранение метрик отдельно от артефактов

Система ДОЛЖНА (SHALL) хранить метрики в каталоге `.openspec-ide/` рабочего пространства
в виде журнала событий с добавлением в конец и производного снимка состояния.
Файлы артефактов OpenSpec ДОЛЖНЫ изменяться только при отметке выполнения задачи
и никогда — при записи метрик.

#### Scenario: Запись события метрики

- **WHEN** завершается запуск агента по задаче
- **THEN** в журнал добавляется событие с идентификатором задачи, временем и показателями
- **AND** файлы `openspec/` не изменяются

#### Scenario: Восстановление снимка из журнала

- **WHEN** файл снимка отсутствует или повреждён, а журнал доступен
- **THEN** снимок пересобирается из журнала при запуске
- **AND** интерфейс сообщает о выполненном восстановлении

#### Scenario: Журнал повреждён частично

- **WHEN** отдельные строки журнала не разбираются
- **THEN** они пропускаются с записью в журнал сервера
- **AND** остальные события применяются

#### Scenario: Каталог метрик исключён из системы контроля версий

- **WHEN** IDE впервые создаёт каталог `.openspec-ide/`
- **THEN** в него записывается правило игнорирования содержимого
- **AND** пользователю сообщается о созданном каталоге

### Requirement: Экспорт метрик

Система ДОЛЖНА (SHALL) выгружать метрики задач и changes в машиночитаемом формате с
указанием версии схемы данных, чтобы показатели можно было переносить во внешние
отчёты.

#### Scenario: Экспорт метрик change

- **WHEN** пользователь запрашивает экспорт метрик выбранного change
- **THEN** выдаётся структура с метриками каждой задачи и сводкой change
- **AND** в ней присутствует версия схемы данных

#### Scenario: Экспорт всего рабочего пространства

- **WHEN** пользователь запрашивает экспорт по всем changes, включая архивные
- **THEN** выдача содержит метрики активных и архивных changes
- **AND** архивные помечены соответствующим признаком
