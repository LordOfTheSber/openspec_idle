# Design: OpenSpec IDE

## Context

Мотивация — в `proposal.md`, раздел Why. Требования — в `specs/`. Здесь только то,
как это собрать.

Существенные внешние ограничения:

- **CLI OpenSpec уже даёт машиночитаемый интерфейс.** `list`, `show`, `status`,
  `validate`, `instructions`, `templates`, `context` поддерживают `--json`.
  Формат дельт, правила валидации и состав артефактов задаются схемой workflow
  (`openspec/config.yaml` → `schema: spec-driven`), которую CLI отдаёт сам.
- **Схема workflow не обязана быть неизменной.** Набор артефактов приходит из
  `openspec status --json` полем `artifactPaths`; зашивать список
  proposal/specs/design/tasks в код нельзя.
- **GigaCode CLI — форк Qwen Code, который, в свою очередь, форк Gemini CLI.**
  Наследуемый неинтерактивный интерфейс: позиционный промпт, `--output-format
  json|stream-json`, `--approval-mode plan|default|auto-edit|auto|yolo`,
  `--max-wall-time`, `--max-tool-calls`, `--include-directories`, `-m`,
  `--session-id`, `--resume`. Точный состав флагов конкретной сборки GigaCode
  проверить до начала работ не удалось — пакет не публикуется в открытом
  npm-реестре.
- **Проект изначально пуст.** Нет легаси, которое нужно сохранять.

## Goals / Non-Goals

### Goals

- Один источник истины — файлы на диске. IDE читает и пишет те же файлы, что и
  CLI; после закрытия IDE проект остаётся полноценным OpenSpec-проектом.
- Все операции, меняющие структуру OpenSpec (создание change, архивация),
  выполняются самим CLI, а не повторной реализацией внутри IDE.
- Метрики — надстройка. Их потеря не ломает проект и не меняет ни одного
  артефакта.
- Работоспособность IDE не зависит от доступности LLM: без настроенного
  GigaCode CLI недоступен ровно один раздел.

### Non-Goals

- Многопользовательская работа и синхронизация между машинами. Сервер —
  однопользовательский, слушает loopback.
- Поддержка других провайдеров LLM в MVP. Точка расширения закладывается
  (см. решение 6), но второй адаптер не пишется.
- Редактирование произвольного кода проекта. IDE редактирует артефакты
  OpenSpec; код меняет агент или обычный редактор.
- Контроль версий внутри IDE. Git остаётся снаружи.
- Собственная реализация разбора спеков там, где его отдаёт CLI (см. решение 3).

## Decisions

### 1. Локальный сервер + SPA вместо расширения к существующей IDE

**Решение.** Бинарь `openspec-ide` поднимает Fastify на loopback и отдаёт
собранную React-страницу; браузер — только средство отрисовки.

**Почему не расширение VS Code.** Расширение привязывает к одному редактору и
его модели вкладок, а доска и метрики в неё ложатся плохо. Отдельное окно даёт
полную свободу в раскладке и не мешает работать в привычном редакторе
параллельно — типичный сценарий как раз такой: код в редакторе, процесс в IDE.

**Почему не TUI.** Дельты, доска и метрики — задачи визуальные; терминал их
сжимает. Кроме того, `openspec view` уже занимает эту нишу.

**Цена решения.** Нужен браузер и нужна защита локального порта (решение 7).

### 2. Монорепозиторий из четырёх пакетов

`packages/core` — типы, разбор markdown OpenSpec, модель метрик; без ввода-вывода.
`packages/server` — Fastify, обёртка над CLI, наблюдение за файлами, адаптер агента.
`packages/web` — SPA.
`packages/cli` — бинарь, разбор аргументов, запуск сервера.

**Почему.** `core` не зависит от Node API, поэтому его правила разбора и
вычисления метрик покрываются быстрыми тестами и переиспользуются обеими
сторонами. Альтернатива — один пакет — быстрее стартует, но смешивает чистую
логику с процессами и файловой системой, и тесты сразу становятся
интеграционными.

### 3. Вся работа с OpenSpec — через CLI, разбор markdown только там, где CLI молчит

**Решение.** Один модуль `openspecCli` запускает `openspec <cmd> --json` и
разбирает вывод. Собственный разбор markdown применяется только к `tasks.md`.

**Почему.** CLI — исполняемая спецификация формата. Свой разбор дельт неизбежно
разойдётся с ним при обновлении OpenSpec, и IDE начнёт показывать не то, что
увидит `validate`.

**Исключение для `tasks.md`.** CLI отдаёт только счётчики
(`completedTasks`/`totalTasks`), а метрикам нужны отдельные пункты с их номерами,
текстом и позицией в файле. Поэтому `core` разбирает список задач сам, повторяя
правило CLI: выполненной считается задача, чьи скобки содержат `x` в любом
регистре и с любыми пробелами; строка без чекбокса задачей не является.
Расхождение ловится тестом: разобранное число выполненных сверяется с
`completedTasks` из `openspec list --json` на фикстурных проектах.

**Цена.** Накладные расходы на запуск процесса (десятки миллисекунд на вызов).
Снимается кэшированием по времени изменения файлов.

### 4. Отметка задачи — точечная правка строки, а не перезапись файла

**Решение.** Переключение чекбокса меняет ровно диапазон символов внутри скобок в
известной позиции; остальной файл не перечитывается и не переписывается.

**Почему.** `tasks.md` — артефакт, который правят и человек, и агент.
Перезапись файла из разобранной модели неизбежно нормализует пробелы, порядок и
форматирование, что даёт шумные диффы и конфликты. Требование «остальные строки
остаются побайтово неизменными» проверяется тестом на файле с намеренно
неровным форматированием.

### 5. Метрики — журнал событий с добавлением в конец плюс производный снимок

**Решение.** `.openspec-ide/runs.jsonl` — неизменяемые события (начало запуска,
завершение, отметка задачи, прогон проверки приёмки). `.openspec-ide/metrics.json` —
снимок, пересобираемый из журнала.

**Почему не одна мутируемая JSON-структура.** Запуски агента идут параллельно с
правками файлов; перезапись общего состояния теряет события при сбое. Журнал с
добавлением в конец устойчив к обрыву: битая последняя строка отбрасывается,
остальное применяется.

**Почему не SQLite.** Данных мало (сотни событий на change), а текстовый журнал
читается глазами и диффится — для отладки это важнее скорости запроса.

**Устойчивость идентификатора задачи.** Идентификатор — `change/группа/номер`.
Изменение текста его не трогает. Перенумерация обрабатывается отдельно: при
исчезновении идентификатора ищется задача с новым номером, чей текст совпадает с
прежним по нормализованному сравнению не ниже порога; при совпадении метрики
переносятся, и факт переноса пишется в журнал. Порог намеренно консервативный —
ложный перенос хуже потери метрик, потому что молча приписывает задаче чужой
расход.

### 6. Адаптер агента: интерфейс CLI вынесен в конфигурацию

**Решение.** Модуль `agent/gigacode` описывает запуск декларативно — имя
исполняемого файла, шаблон аргументов, формат вывода — и это описание переопределяется
в `.openspec-ide/config.json`. Значения по умолчанию соответствуют интерфейсу
Qwen Code, который GigaCode CLI наследует.

**Почему.** Точный набор флагов установленной сборки GigaCode проверить на этапе
проектирования не удалось. Зашитая в код строка запуска сделала бы IDE
неработоспособной при малейшем расхождении, а переопределяемое описание
превращает расхождение в правку одной настройки.

**Проверка вместо предположений.** Перед первым запуском выполняется проба:
версия CLI и приём запрошенного формата вывода. Если потоковый формат не
поддерживается, IDE переходит на одноразовый вывод и сообщает об этом —
вместо того чтобы показывать пустую панель.

**Разбор потока — нормализующий.** События приводятся к внутренней модели
(сообщение, вызов инструмента, итог, расход) по типу; неизвестные типы
сохраняются как есть и не прерывают обработку. Это прямо требуется спекой, и это
же защищает от изменений формата в новых сборках.

**Точка расширения.** Второй провайдер — это второй файл описания. Никакого
плагинного механизма в MVP не вводится: одна реализация не оправдывает абстракцию.

### 7. Безопасность: loopback, токен сессии, канонизация путей

**Решение.** Сервер привязывается к `127.0.0.1`; при запуске генерируется токен
сессии, который встраивается в отдаваемую страницу и требуется на каждом запросе
к API; все пути перед операцией канонизируются (с разрешением символических
ссылок) и проверяются на принадлежность корню.

**Почему токен, а не только loopback.** Любой процесс на машине, включая код в
открытой вкладке браузера, может обратиться к localhost. Токен отсекает запросы,
не пришедшие с отданной страницы.

**Почему канонизация обязательна.** Сервер по запросу от страницы читает и пишет
файлы; без разрешения ссылок и относительных переходов это произвольный доступ к
файловой системе. Проверка выполняется после `realpath`, а не над строкой пути.

**Секреты.** В конфигурацию пишется только имя переменной окружения. Значения
секретов вырезаются из сохраняемых записей о запусках — иначе промпт с ключом
осядет в журнале на диске.

### 8. Транспорт обновлений — SSE

**Решение.** Изменения файлов, события агента и результаты валидации идут одним
потоком SSE от сервера к странице; действия страницы — обычными HTTP-запросами.

**Почему не WebSocket.** Двунаправленность не нужна: поток данных
односторонний. SSE проще, переподключается сам и не требует отдельного
протокола поверх.

**Почему не опрос.** Поток событий агента должен быть виден по мере поступления;
опрос с приемлемой задержкой создаёт лишнюю нагрузку и всё равно отстаёт.

**Объединение событий.** Наблюдатель за файлами объединяет изменения в окне в
сотни миллисекунд — архивация меняет десятки файлов разом, и каждое обновление
по отдельности вызвало бы шквал перерисовок и лавину запросов валидации.

## Risks / Trade-offs

- **Интерфейс GigaCode CLI отличается от унаследованного от Qwen Code** →
  запуск описан конфигурацией (решение 6), перед первым запуском выполняется
  проба возможностей, разбор потока терпим к неизвестным событиям. Первая
  задача этапа интеграции — сверить реальные флаги установленной сборки и
  поправить значения по умолчанию.
- **Формат JSON-вывода OpenSpec меняется между версиями** → версия CLI
  фиксируется в `package.json`, ответы разбираются через схемы с понятной
  ошибкой при несовпадении, обновление CLI проходит через тесты на фикстурах.
- **Метрики расходятся с реальностью при правках файлов вне IDE** →
  метрики никогда не являются источником истины о составе плана: список задач
  всегда перечитывается из `tasks.md`, метрики только присоединяются к нему.
  Задачи, для которых метрики есть, а в файле их уже нет, показываются отдельно
  как удалённые.
- **Запуск CLI на каждое обновление дерева тормозит интерфейс** → результаты
  кэшируются по времени изменения файлов, валидация запускается с задержкой и
  отменяет предыдущий запуск.
- **Агент правит файлы под открытым редактором** → правка не теряется: при
  расхождении содержимого сохранение блокируется и показывается сравнение
  версий. Это заметнее «тихого» автослияния и требуется спекой.
- **Режим `yolo` превращает запуск в неконтролируемое изменение репозитория** →
  режим по умолчанию требует подтверждения правок, а полное автоподтверждение
  включается только через явное согласие с предупреждением.

## Migration Plan

Миграции нет: проект новый, состояния для переноса не существует. Порядок ввода:

1. Каркас (`core` + `cli` + пустой сервер) — проверяется запуском и разрешением корня.
2. Обёртка над CLI и обозреватель — IDE становится полезной только на чтение.
3. Редактор с валидацией — появляется запись в артефакты.
4. Дельты и доска — поверх уже готовой обёртки.
5. Метрики — надстройка над разобранным `tasks.md`.
6. Мост к агенту — последним, потому что требует внешней зависимости и
   единственный может быть заблокирован недоступностью GigaCode CLI.

Откат на любом этапе — удаление каталога `.openspec-ide/`; файлы `openspec/`
остаются валидным проектом OpenSpec.
