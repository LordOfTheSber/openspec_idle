# Change: согласованность спеков, артефактов, тестов и кода

## Why

Проверка качества (`add-spec-quality`) смотрит на одно требование. Самые
дорогие дефекты лежат между артефактами — и их не видит ни `openspec
validate`, ни линтер требования. Разовый замер на этом репозитории:

- 14 из 67 решений в design без рассмотренной альтернативы, хотя
  `openspec/config.yaml` требует её у каждого решения: правила `config.yaml`
  читает агент, но никто не проверяет;
- 3 из 8 ссылок плана на тесты битые: `add-context-antipatterns` переименовал
  e2e-тест, а планы `add-context-control` и `add-context-usefulness`
  по-прежнему ссылаются на старое имя; `add-context-selection` ссылается на
  `lib/…` без пакета;
- 4 цитаты сообщений из THEN не находятся в коде модулей своего домена:
  «проект не инициализирован» живёт в `packages/vscode`, а домен
  `ide-runtime` по карте контекста — только `packages/server`;
- в разных спеках один и тот же WHEN ведёт к разным THEN — пока это
  взаимодополняющие исходы, но расхождение никто не заметит;
- требование с двумя кодами отказа без порядка проверок — частая причина
  разных ответов разных реализаций (в спеках IDE кодов нет, но для
  сервисных спек это первый дефект);
- абсолютные пороги метрик неприменимы к проекту с накопленным долгом: нужен
  запрет ухудшать, а не требование сразу быть идеальным.

## What Changes

Новая возможность `spec-consistency` — правила в том же конвейере, что и
проверка качества: замечания в «Проблемах» (`openspec-quality`, код — имя
правила) и в проверке `quality` команды `openspec-ide-check`.

| Правило | Что проверяет | Уровень |
| --- | --- | --- |
| `error-order` | у требования с двумя и более кодами ошибок задан порядок проверок | предупреждение |
| `scenario-conflict` | в одном требовании одинаковый WHEN не ведёт к разным THEN | предупреждение |
| `scenario-overlap` | одинаковый WHEN в разных требованиях с разными THEN — сверить | сведение |
| `scenario-duplicate` | сценарий не повторяет дословно другой | сведение |
| `artifact-rule` | исполняемые правила артефактов из `artifacts` в `openspec/quality.yaml` | предупреждение (или `level` правила) |
| `plan-test-ref` | файл теста из плана есть, тест с указанным именем в нём есть | предупреждение |
| `code-message` | цитата из THEN находится в коде модулей домена (`code_paths`) | предупреждение |
| `code-constant` | числовая граница текста находится в коде литералом | сведение |
| `metric-regression` | метрики и число замечаний не хуже, чем в `--baseline <ревизия>` | ошибка |

- **Исполняемые правила**: `artifacts` — список правил «артефакт → файл,
  раздел или пункт плана → `require` / `forbid` шаблон → сообщение». В этом
  репозитории `openspec/quality.yaml` переводит в проверки два правила
  `config.yaml`: альтернатива у решения design и метрика приёмки у пункта
  плана.
- **Сверка с кодом** опирается на карту контекста: домен → модули →
  `code_paths`. Без модулей проверка молчит.
- **Регресс**: `openspec-ide-check --baseline origin/main` строит отчёт по
  спекам и артефактам ревизии git с текущими настройками и сравнивает.
- Ссылки плана на тесты в этом репозитории исправлены (3 пункта в трёх
  changes).

Не входит: LLM-извлечение decision table (уровень 2 исходной идеи),
генерация тестов и мутационное тестирование (уровень 3), сверка с OpenAPI,
команды и настройки `package.json`, отставание спеков от кода по git.

## Capabilities

### New Capabilities

- `spec-consistency` — согласованность спеков между собой, с артефактами
  change, с тестами плана и с кодом модулей домена; регресс качества
  относительно ревизии git.

### Modified Capabilities

Нет.

## Impact

- **Код**: `packages/core/src/specConsistency.ts` — сравнение сценариев,
  правила артефактов, ссылки на тесты, сверка с кодом, регресс (чистые
  функции); `packages/core/src/specQuality.ts` — правило `error-order`,
  новые правила в общем списке; `packages/core/src/specQualityConfig.ts` —
  ключ `artifacts`; `packages/server/src/quality.ts` — код модулей домена,
  файлы тестов, спеки ревизии git; маршрут `GET /api/quality/project`;
  `/api/authoring` отдаёт файлы артефактов changes; `packages/server/src/check.ts`
  и `packages/check` — `--baseline`; `packages/vscode/src/authoring.ts` —
  замечания по диску в коллекции `openspec-quality`.
- **API**: новый маршрут и поле `artifacts` у changes в `/api/authoring`;
  их читает только расширение в том же процессе, ревизия API не меняется.
- **Файлы проекта**: `openspec/quality.yaml` этого репозитория с двумя
  правилами артефактов; исправлены ссылки на тесты в планах
  `add-context-control`, `add-context-usefulness`, `add-context-selection`.
