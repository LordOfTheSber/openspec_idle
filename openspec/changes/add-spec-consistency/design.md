# Design: согласованность спеков, артефактов, тестов и кода

## Context

Мотивация — в `proposal.md`, требования — в дельте `specs/spec-consistency`.
Строится поверх `add-spec-quality`: разбор требований со строками, уровни
правил, настройки `openspec/quality.yaml`, коллекция `openspec-quality` в
VS Code и проверка `quality` в CI уже есть. Новые правила — чистые функции
`core/specConsistency.ts`; то, что требует диска и git, сервер готовит
заранее и передаёт данными.

## Decisions

### 1. Одни правила — один конвейер

**Решение.** Новые правила — те же `QualityRule`: уровни и `off` в `rules`,
коллекция `openspec-quality`, проверка `quality`. Правила по текстам
источников (`error-order`, сценарии, `artifact-rule`) считает `specQuality`
— в редакторе при наборе; правила по диску (`plan-test-ref`, `code-*`) —
маршрут `/api/quality/project` при перечитывании источников.

**Альтернатива — отдельная проверка `consistency`.** Второй набор уровней,
второй файл настроек и вторая коллекция «Проблем» ради разницы, которую
пользователю не нужно знать.

### 2. Сравнение сценариев — по нормализованному WHEN

**Решение.** Ключ сценария — шаги GIVEN и WHEN в нижнем регистре, без
кавычек, `кода`, пунктуации и точки в конце. Внутри требования одинаковый
WHEN с разными THEN — предупреждение: это противоречие или один сценарий,
разрезанный на два. Между требованиями — сведение: в этом репозитории все 11
таких пар — дополняющие исходы («дерево показывает артефакты схемы» в
`workspace-explorer` и `vscode-extension`), но расходиться им нельзя.
Дельта и основной спек одной capability не сравниваются — MODIFIED и RENAMED
повторяют сценарии по определению, даже под новым именем требования.

**Альтернатива — сравнение по похожести (доля общих слов).** Нашло бы
перефразированные дубли, но порог похожести на русском тексте без
морфологии даёт шум; точное совпадение после нормализации — без ложных
срабатываний.

### 3. Порядок ошибок — по кодам и словам порядка

**Решение.** Два и больше кодов ошибок требования (те же, что считает
трассируемость: из текста об ошибках и из THEN, без входных значений WHEN)
без слов «сначала / затем / прежде / приоритет / порядок / первым» и
английских аналогов — предупреждение. Это детерминированная часть
«неоднозначности» из уровня 2 идеи.

**Альтернатива — искать пересечение условий (decision table).** Требует
перевода условий в структуру — уровень 2 и LLM (ADR-006).

### 4. Исполняемые правила — `require` / `forbid` по файлу, разделу или пункту

**Решение.** Правило из `artifacts`: `artifact` — идентификатор артефакта
схемы, `each` — `file`, `section` (заголовок по шаблону `heading`, по
умолчанию `^#{2,3}\s`; раздел без текста пропускается, чтобы «## Decisions»
перед «### 1.» не был нарушением) или `item` (пункт плана со строками
продолжения), `require` / `forbid` — регулярные выражения без учёта
регистра, `message`, `level`. Файлы артефактов отдаёт `/api/authoring` по
схеме change.

```yaml
artifacts:
  - id: design-alternative
    artifact: design
    each: section
    heading: '^###\s'
    require: 'альтернатив'
    message: 'Решение без рассмотренной альтернативы'
```

**Альтернатива — разбирать `rules` из `openspec/config.yaml`.** Там правила
— фразы для агента («каждое решение сопровождается альтернативой»):
перевести их в проверку может только LLM, а менять формат `config.yaml`
нельзя — им владеет CLI OpenSpec.

### 5. Ссылки на тесты — по имени файла теста и «кавычкам»

**Решение.** Ссылка — путь в `` `…` `` с `/`, похожий на файл теста
(`.test.`/`.spec.` у JS/TS, `_test.go`, `Test.java`, `test_*.py`), и идущие
за ним имена в «кавычках» через запятую или «и»; вложенные «кавычки»
разбираются парами. Имя ищется в тексте файла подстрокой; «…» на конце —
начало имени. Пути с выходом за корень не читаются.

**Альтернатива — запускать тест-раннер со списком тестов.** Точнее (учтёт
`describe` + `it`), но зависит от фреймворка проекта и медленно для
редактора.

### 6. Сверка с кодом — через карту контекста

**Решение.** Домен → модули с ним в `domains` → их `code_paths`; файлы кода и
ресурсов (`.ts`, `.java`, `.py`, `.json`, `.yaml`…) без тестов, `node_modules`,
`dist`, `media`, не больше 512 КБ и 5 000 файлов на путь. Цитата THEN
ищется по самой длинной постоянной части: числа, «…», `<имя>`, `{имя}`
— переменные (`Пунктов плана: 2` находит шаблон `` `Пунктов плана: ${n}` ``);
цитата из одного слова не ищется — это имя файла или раздела. Число-граница
ищется литералом и в записи `8_000`, проценты — и долей.

**Альтернатива — искать по всему репозиторию.** Нашло бы больше, но
пропустило бы главное: сообщение есть в коде, но не в модуле, который карта
связывает с доменом, — значит, неверна карта или спека.

### 7. Регресс — те же правила по ревизии git

**Решение.** `--baseline <ревизия>`: `git ls-tree` и `git show` дают
основные спеки, дельты и файлы артефактов активных changes ревизии
(идентификатор артефакта — имя файла, как у `spec-driven`); отчёт строится
с текущими настройками. Ошибка — на каждую ухудшившуюся метрику и на рост
числа предупреждений и ошибок (без сведений, порогов и самого регресса) с
разбивкой по правилам. Проектные правила (`plan-test-ref`, `code-*`) не
сравниваются: для ревизии нужен её код целиком.

**Альтернатива — хранить снимок метрик в репозитории.** Снимок устаревает и
конфликтует при слиянии; ревизия git уже есть в любом CI.

**Замер на этом репозитории.** `error-order` — 0 (в спеках IDE нет кодов
ошибок). `scenario-overlap` — 11, `scenario-conflict` и
`scenario-duplicate` — 0. `artifact-rule` — 14 решений без альтернативы в 5
changes, пунктов плана без проверки — 0. `plan-test-ref` — 3 до исправления
планов, 0 после. `code-message` — 4: «проект не инициализирован»,
«спеки не затрагиваются», «приёмка пройдена», «не проходит валидацию» — их
нет в коде модулей домена; `code-constant` — 0. `--baseline HEAD` на
неизменённом дереве — без регресса; `npm run check:openspec` проходит с
кодом 0.

## Risks / Trade-offs

- Сравнение сценариев точное: перефразированный дубль не найдётся.
- Цитата THEN может быть описанием («показано сообщение об ошибке»), а не
  текстом интерфейса — такие пишутся без кавычек; кавычки в THEN считаются
  обещанием конкретного текста.
- Проектные правила пересчитываются при изменении файлов `openspec/`; правка
  только кода видна после следующего перечитывания источников.
- Регресс по числу замечаний растёт и от новых спек: новый спек должен
  приходить без предупреждений — это и есть цель ворот.
