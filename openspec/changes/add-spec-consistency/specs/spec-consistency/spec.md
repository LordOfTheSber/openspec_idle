# Spec Delta: spec-consistency

## ADDED Requirements

### Requirement: Порядок ошибок требования

Система ДОЛЖНА (SHALL) давать предупреждение `error-order` на требование,
которое называет два и более кода ошибок (в тексте или в THEN, без входных
значений WHEN) и в тексте которого нет слов о порядке проверок («сначала»,
«затем», «прежде», «приоритет», «порядок», «первым» и английских аналогов):
иначе неизвестен код ответа на запрос, который нарушает оба условия.

#### Scenario: Два кода без порядка

- **WHEN** требование отклоняет запрос без заголовка с кодом `HEADER_REQUIRED` и запрос с длинным TTL с кодом `TTL_TOO_LONG`, а запрос нарушает оба условия
- **THEN** на строке требования есть предупреждение `error-order` с обоими кодами

#### Scenario: Порядок задан

- **WHEN** текст того же требования добавляет «Заголовок проверяется первым.»
- **THEN** предупреждения `error-order` нет

### Requirement: Противоречия и дубли сценариев

Система ДОЛЖНА (SHALL) сравнивать сценарии основных спеков и дельт активных
changes по шагам GIVEN и WHEN без учёта регистра, кавычек и пунктуации:

- в одном требовании одинаковый WHEN с разными THEN — предупреждение
  `scenario-conflict` на втором сценарии;
- в разных требованиях одинаковый WHEN с разными THEN — сведение
  `scenario-overlap` у каждого сценария;
- одинаковые WHEN и THEN — сведение `scenario-duplicate`.

Дельта и основной спек одной capability, а также дельты разных changes одной
capability друг с другом сравниваться НЕ ДОЛЖНЫ: это версии одного спека.

#### Scenario: Противоречие внутри требования

- **WHEN** у требования два сценария с WHEN «клиент продлевает сессию» и THEN «TTL продлевается» и «ответ — ошибка 409»
- **THEN** на строке второго сценария есть предупреждение `scenario-conflict`

#### Scenario: Один триггер в двух спеках

- **WHEN** в спеках `a` и `b` есть сценарии с WHEN «запрос без заголовка» и разными THEN
- **THEN** у каждого из них есть сведение `scenario-overlap` со ссылкой на другой

#### Scenario: Копия требования в дельте

- **WHEN** дельта MODIFIED повторяет сценарий основного спека своей capability с другим THEN
- **THEN** сведений `scenario-overlap` и предупреждений `scenario-conflict` нет

### Requirement: Исполняемые правила артефактов

Система ДОЛЖНА (SHALL) проверять файлы артефактов активных changes правилами
из ключа `artifacts` файла `openspec/quality.yaml`. Правило задаёт
идентификатор артефакта схемы (`design`, `tasks` и другие), что
проверять — файл целиком, раздел под заголовком (шаблон `heading`, по
умолчанию заголовки второго и третьего уровня; раздел без текста не
проверяется) или пункт плана с продолжением, — и шаблон, который должен
найтись (`require`) или не должен (`forbid`). Нарушение ДОЛЖНО давать
замечание `artifact-rule` с сообщением правила на строке файла, раздела или
пункта, с уровнем правила (`level`) или уровнем `artifact-rule`. Правило без
артефакта, без шаблонов или с неразбираемым шаблоном ДОЛЖНО давать ошибку
настроек.

#### Scenario: Решение без альтернативы

- **WHEN** правило `design-alternative` требует «альтернатив» в каждом разделе `### ` артефакта `design`, а решение «2. Отдельный файл» альтернативы не содержит
- **THEN** на строке заголовка «2. Отдельный файл» есть предупреждение `artifact-rule` с сообщением правила

#### Scenario: Пункт плана без проверки

- **WHEN** правило артефакта `tasks` с `each: item`, `require: провер` и `level: error` проверяет план, а пункт «1.2 Настройки» слова «проверка» не содержит
- **THEN** на строке пункта есть ошибка `artifact-rule`

#### Scenario: Пустой раздел не проверяется

- **WHEN** правило проверяет разделы по умолчанию, а раздел «## Decisions» сразу продолжается заголовком «### 1.»
- **THEN** замечания на строке «## Decisions» нет

### Requirement: Ссылки плана на тесты

Система ДОЛЖНА (SHALL) находить в планах активных changes ссылки на файлы
тестов (`` `*.test.ts` ``, `` `*.spec.ts` ``, `` `*_test.go` ``,
`` `*Test.java` `` и подобные) с необязательными именами тестов в «кавычках»
после них, в том числе с вложенными «кавычками», и давать предупреждение
`plan-test-ref` на ссылку на отсутствующий файл и на имя теста, которого в
файле нет. Имя с
«…» на конце ДОЛЖНО искаться как начало имени.

#### Scenario: Тест переименован

- **WHEN** пункт плана ссылается на `tests/e2e/context.spec.ts` «вид Контроль показывает объём, лишнее и ненайденные пути», а тест в файле называется «вид «Контроль» показывает объём, лишнее, антипаттерны и ненайденные пути»
- **THEN** на строке пункта есть предупреждение `plan-test-ref` с прежним именем теста

#### Scenario: Файла теста нет

- **WHEN** пункт плана ссылается на `src/export.test.ts`, которого нет в проекте
- **THEN** на строке пункта есть предупреждение `plan-test-ref` «такого файла нет»

#### Scenario: Начало имени

- **WHEN** пункт плана ссылается на тест «разбор: …», а в файле есть тест «разбор: шаги и сценарии»
- **THEN** предупреждения `plan-test-ref` нет

### Requirement: Сверка спека с кодом модулей домена

Система ДОЛЖНА (SHALL) для спека, capability которого указана в `domains`
модулей карты контекста, собирать код из `code_paths` этих модулей (без
тестов, зависимостей и сборок) и давать предупреждение `code-message` на шаг
THEN с цитатой в «кавычках», постоянная часть которой (без чисел, «…» и
подстановок `<имя>`) не находится в этом коде, и сведение `code-constant` на
предложение текста требования с числовой границей, которой нет в коде
литералом (`8000`, `8_000`, для процентов — и доля `0.3`). Цитата из одного
слова (имя файла, название раздела) искаться НЕ ДОЛЖНА. Спеки без модулей в
карте контекста не проверяются.

#### Scenario: Сообщение изменилось в коде

- **WHEN** THEN сценария говорит «показано сообщение «Выгрузка готова к скачиванию»», а код модуля `export` домена `data-export` такой строки не содержит
- **THEN** на строке шага есть предупреждение `code-message`, называющее модуль `export` и домен

#### Scenario: Число найдено в другой записи

- **WHEN** текст требования говорит «больше 8000 токенов», а код содержит `const HEAVY = 8_000`
- **THEN** сведения `code-constant` о 8000 нет

#### Scenario: Граница без литерала

- **WHEN** текст требования говорит «при ширине меньше 640 px», а в коде модуля числа 640 нет
- **THEN** есть сведение `code-constant` о границе 640

### Requirement: Регресс качества относительно ревизии

Команда `openspec-ide-check` ДОЛЖНА (SHALL) с параметром `--baseline
<ревизия>` строить отчёт качества по основным спекам, дельтам и артефактам
активных changes из этой ревизии git с текущими настройками и давать ошибку
`metric-regression` на каждую ухудшившуюся метрику (доля — ниже, плотность
расплывчатых слов — выше) и на рост числа предупреждений и ошибок качества
(с разбивкой по правилам). Ревизия, которой нет в git, ДОЛЖНА давать ошибку
запуска с кодом 2.

#### Scenario: Расплывчатые слова в PR

- **WHEN** после коммита в дельту добавлено «в корректном формате CSV и т. д.», и выполняется `openspec-ide-check --only quality --baseline HEAD`
- **THEN** есть ошибка `metric-regression` «расплывчатых слов на 100 ухудшилась относительно HEAD» и ошибка «стало больше, чем в HEAD: 0 → 1 (vague-wording +1)», код завершения 1

#### Scenario: Неизвестная ревизия

- **WHEN** выполняется `openspec-ide-check --only quality --baseline нет-такой`
- **THEN** код завершения 2 и сообщение «Ревизии «нет-такой» нет в git»

### Requirement: Замечания согласованности в редакторе

Расширение ДОЛЖНО (SHALL) показывать замечания согласованности в панели
«Проблемы» с источником `openspec-quality` и кодом — именем правила:
противоречия, порядок ошибок и правила артефактов — по текстам источников,
ссылки плана на тесты и сверку с кодом — после перечитывания источников,
которое следует за изменением файлов `openspec/`; пересчёт открытого
документа эти замечания сохраняет.

#### Scenario: Правило артефактов в «Проблемах»

- **WHEN** `openspec/quality.yaml` требует «## Risks» в `proposal`, а план ссылается на несуществующий `src/limits.test.ts`
- **THEN** в «Проблемах» у `proposal.md` есть замечание с кодом `artifact-rule`, а у плана — с кодом `plan-test-ref`
