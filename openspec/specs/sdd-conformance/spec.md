# sdd-conformance Specification

## Purpose
Отвечает на вопрос, остаётся ли построенный командой процесс спек-ориентированным:
задаёт проверяемые правила SDD поверх структурной валидации CLI, объясняет каждое
нарушение и определяет последствия — вплоть до запрета назначить такую схему.

## Requirements

### Requirement: Правила спек-ориентированности процесса

Система ДОЛЖНА (SHALL) проверять схему workflow по набору правил, каждое из
которых имеет уровень «ошибка» или «предупреждение». Правила уровня «ошибка»
означают, что процесс не является спек-ориентированным; правила уровня
«предупреждение» — что он им является, но описан неполно.

Проверяются правила уровня «ошибка»:

- в схеме есть хотя бы один артефакт, порождающий дельты спеков, — контракт
  поведения, с которым можно сверить реализацию;
- артефакт, с которого начинается работа по коду, транзитивно зависит от
  артефакта-контракта, то есть код не пишется параллельно с определением поведения;
- объявлен отслеживаемый артефакт, и он существует среди артефактов схемы;
- все артефакты достижимы по зависимостям от артефактов без зависимостей.

Проверяются правила уровня «предупреждение»:

- артефакт-контракт зависит от артефакта, объясняющего мотивацию изменения;
- у каждого артефакта заполнена инструкция для агента.

#### Scenario: Процесс без артефакта-контракта

- **WHEN** проверяется схема, ни один артефакт которой не порождает дельт спеков
- **THEN** отчёт содержит нарушение уровня «ошибка» об отсутствии контракта поведения
- **AND** объяснение называет, какое поле артефакта задаёт порождение спеков

#### Scenario: Работа по коду не зависит от спеков

- **WHEN** артефакт, с которого начинается работа, не зависит от артефакта-контракта ни прямо, ни через цепочку зависимостей
- **THEN** отчёт содержит нарушение уровня «ошибка»
- **AND** объяснение показывает найденную цепочку зависимостей этого артефакта

#### Scenario: Отслеживаемый артефакт не объявлен

- **WHEN** в схеме отсутствует указание отслеживаемого артефакта
- **THEN** отчёт содержит нарушение уровня «ошибка»

#### Scenario: Отслеживаемый артефакт не существует

- **WHEN** схема объявляет отслеживаемым артефакт, отсутствующий среди её артефактов
- **THEN** отчёт содержит нарушение уровня «ошибка» с указанием несуществующего идентификатора

#### Scenario: Недостижимый артефакт

- **WHEN** артефакт схемы не достижим по зависимостям ни от одного артефакта без зависимостей
- **THEN** отчёт содержит нарушение уровня «ошибка» с именем этого артефакта

#### Scenario: Спеки без мотивации

- **WHEN** артефакт-контракт не зависит от артефакта, объясняющего мотивацию
- **THEN** отчёт содержит предупреждение
- **AND** назначение схемы не блокируется

#### Scenario: Артефакт без инструкции

- **WHEN** у артефакта схемы не заполнена инструкция
- **THEN** отчёт содержит предупреждение с именем этого артефакта
- **AND** объяснение указывает, что агент не сможет работать по такому артефакту

#### Scenario: Схема, созданная командой инициализации

- **WHEN** проверяется схема, только что созданная командой `openspec schema init`
- **THEN** отчёт содержит предупреждения о незаполненных инструкциях всех её артефактов
- **AND** правила уровня «ошибка» не нарушены

#### Scenario: Встроенная схема

- **WHEN** проверяется встроенная схема `spec-driven`
- **THEN** отчёт не содержит нарушений

### Requirement: Отчёт о соответствии

Отчёт о соответствии ДОЛЖЕН (SHALL) содержать для каждого нарушения: уровень,
идентификатор правила, затронутый артефакт, если правило относится к артефакту,
объяснение на языке процесса и предлагаемый способ исправления. Правила, которые
проверка прошла, ДОЛЖНЫ быть перечислены отдельно, чтобы был виден полный состав
проверок, а не только замечания.

#### Scenario: Просмотр отчёта

- **WHEN** пользователь открывает отчёт о соответствии схемы
- **THEN** нарушения показаны сгруппированными по уровню, ошибки выше предупреждений
- **AND** отдельно перечислены пройденные правила

#### Scenario: Переход к причине нарушения

- **WHEN** пользователь выбирает нарушение, относящееся к артефакту
- **THEN** этот артефакт выделяется на графе схемы
- **AND** форма свойств открывается на поле, которого касается нарушение

#### Scenario: Нарушений нет

- **WHEN** схема не нарушает ни одного правила
- **THEN** отчёт показывает состояние соответствия
- **AND** все правила перечислены как пройденные

### Requirement: Последствия нарушений

Система ДОЛЖНА (SHALL) блокировать назначение схемы проекту или change при
наличии хотя бы одного нарушения уровня «ошибка». Предупреждения назначение не
блокируют. Сохранение схемы в конструкторе не блокируется ни в одном случае,
чтобы процесс можно было дорабатывать постепенно.

#### Scenario: Назначение при нарушении уровня «ошибка»

- **WHEN** пользователь пытается назначить схему с нарушением уровня «ошибка»
- **THEN** назначение не выполняется
- **AND** показывается отчёт с нарушениями, которые нужно устранить

#### Scenario: Назначение при предупреждениях

- **WHEN** схема имеет только предупреждения
- **THEN** назначение выполняется
- **AND** предупреждения показываются один раз при назначении

#### Scenario: Сохранение несоответствующей схемы

- **WHEN** пользователь сохраняет схему с нарушением уровня «ошибка»
- **THEN** схема сохраняется на диск
- **AND** в реестре она помечена как непригодная к назначению

### Requirement: Явный отказ от правила

Схема ДОЛЖНА (SHALL) иметь возможность объявить отказ от конкретного правила SDD
с обязательным указанием причины. Отказ ДОЛЖЕН задаваться в самой схеме, быть
адресным — по идентификатору правила — и снимать блокировку назначения только для
названного правила.

#### Scenario: Отказ от правила с причиной

- **WHEN** схема объявляет отказ от правила уровня «ошибка» с непустой причиной
- **THEN** это правило не блокирует назначение схемы
- **AND** в отчёте оно показано как отклонённое с текстом причины

#### Scenario: Отказ без причины

- **WHEN** схема объявляет отказ от правила, не указывая причину
- **THEN** отказ не применяется
- **AND** правило продолжает блокировать назначение

#### Scenario: Отказ от несуществующего правила

- **WHEN** схема объявляет отказ от правила с неизвестным идентификатором
- **THEN** отчёт содержит предупреждение о нераспознанном идентификаторе правила

#### Scenario: Отказы видны в реестре и на доске

- **WHEN** схема с действующим отказом назначена проекту
- **THEN** в реестре схем и на карточках changes этой схемы виден признак отказа от правила SDD
- **AND** признак раскрывается в перечень отклонённых правил с причинами
