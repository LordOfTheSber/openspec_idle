# Аудит и заполнение контекста для больших репозиториев

Навык дополняет `context-fill`: тот описывает, **как писать** файлы контекста
(раскладка, правила, объём), этот — **что заполнять в первую очередь, как
проверить написанное и как измерить, помогает ли оно агенту**. Правила
написания отсюда не повторяются — перед правкой файлов прочитай
`.claude/skills/context-fill/SKILL.md`.

Контекст хорош не объёмом и не процентом «полезности», а тем, что агент с
набором контекста модуля решает задачу в этом модуле: находит нужные файлы,
не нарушает инварианты и не тратит токены на поиск по всему репозиторию.
Поэтому аудит заканчивается задачными пробами (промпт 5), а не только
проверкой текста.

## Метрики аудита

Считаются в каждом отчёте; значения переносятся из отчёта в отчёт, чтобы был
виден тренд.

| Метрика | Как считать | Цель |
| --- | --- | --- |
| Покрытие кода | доля исходных файлов под `code_paths` какого-либо модуля (без сборочных, сгенерированных, фикстур) | ≥ 90 % |
| Покрытие доменов | доля спеков `openspec/specs/` хотя бы в одном `domains`; домены без модулей — список | 100 % действующих |
| Актуальность спеков | changes, выполненные полностью, но не заархивированные; действующие спеки, описывающие удалённое | 0 |
| Свежесть | модули с отставанием контекста от кода (`commitsAfter` в разделе «Контроль» или сведение `stale-context`) | 0 модулей старше 10 коммитов |
| Точность | доля проверенных утверждений контекста, подтверждённых кодом (промпт 3, шаг C) | ≥ 95 % |
| Доля своего контекста | токены собственных файлов модуля / токены набора модуля; остальное — спеки доменов, зависимости, ADR | не меньше 10 %; ниже — набор состоит из спеков, а не из знания об устройстве |
| Бюджет | набор модуля / `max_tokens`; самый тяжёлый набор | ≤ 100 % |
| Полнота файлов | recall файлов в задачных пробах: доля файлов реального коммита, которые агент назвал по набору | ≥ 80 % |
| Промахи контекста | доля файлов, которые агенту пришлось искать вне набора, от всех прочитанных | ≤ 20 % |
| Инварианты | нарушения инвариантов в планах проб (то, что поймал бы тест или ревью) | 0 |

Механические метрики (покрытие доменов, свежесть, бюджет, повторы, пропавшие
пути, антипаттерны) даёт `npm run check:openspec -- --only structure,context`
и раздел «Контекст» → «Контроль» IDE. Их не пересчитывай вручную — бери
оттуда; вручную считаются только смысловые метрики.

## Общие правила (для всех промптов)

- **Доказательство вместо мнения.** Каждый вывод о контексте — с
  доказательством: `файл:строка` в коде, вывод команды или хеш коммита.
  Вывод без доказательства помечается «(не проверено)» и в метрики не идёт.
- **Чтение по выборке — честно.** Если в модуле больше утверждений, чем можно
  проверить, проверяй случайную выборку не меньше 20 штук и пиши размер
  выборки рядом с процентом.
- **Только чтение, пока не попросили править.** Промпты 1, 3, 4, 5 ничего не
  меняют в репозитории; правки — отдельным шагом по промптам `context-fill`.
- **Большой репозиторий — по модулю на агента.** Один модуль, его код и его
  набор контекста — в одном контекстном окне. Если у тебя есть подагенты,
  раздай модули им и собери отчёты; если нет — иди по модулям по очереди и
  не держи в рассуждении код соседних модулей.
- **Не придумывай задач и путей.** Задачи проб — из истории git, пути — из
  `git ls-files`, имена — найденные поиском.

## Промпт 1. Инвентаризация большого репозитория

> Подготовь карту репозитория для контекста агентов. Ничего не меняй.
>
> 1. Единицы сборки: пакеты, сервисы, библиотеки — по манифестам (`package.json`
>    workspaces, `pom.xml`/`build.gradle`, `go.mod`, `Cargo.toml`, `*.csproj`…).
>    Для каждой: путь, язык, объём кода (`git ls-files <путь> | xargs wc -c`,
>    токены ≈ байты / 4), зависимости от других единиц.
> 2. Активность: коммитов за полгода (`git log --since=6.months --oneline --
>    <путь> | wc -l`), число changes в `openspec/changes/**` (включая архив),
>    которые упоминают путь или домены единицы.
> 3. Что уже описано: модули в `openspec/context/` (их `code_paths`), спеки в
>    `openspec/specs/`, незаархивированные changes и их готовность по
>    `tasks.md`.
> 4. Разбиение на модули контекста: модуль — единица, которую меняют целиком
>    одной задачей; объединяй мелкие единицы с общим владельцем и сборкой,
>    дроби единицы больше ~200 тыс. токенов кода по подсистемам. Группы
>    (`modules/back/`) — для общего у нескольких модулей: сборка, стек, общие
>    договорённости. Разделы (`functions/`) — для сквозных функциональных
>    доменов, если они есть.
> 5. Приоритет заполнения: `активность × (1 + changes) × log(объём)`; первыми —
>    модули, которые часто меняют и в которых больше всего неочевидного.
>
> Результат — таблица «модуль — папка в `openspec/context/` — `code_paths` —
> `depends_on` — домены — объём кода — активность — приоритет», список кода,
> не вошедшего ни в один модуль (с причиной: сборочное, сгенерированное,
> мёртвое), и покрытие кода в процентах.

## Промпт 2. Заполнение волнами

> Заполни контекст по карте из промпта 1. Правила написания — навык
> `context-fill`.
>
> - **Волна 0 — точка входа.** Если в корне нет `CLAUDE.md` или `AGENTS.md`,
>   предложи короткий (до ~300 токенов) файл: что за проект, где контекст
>   (`openspec/context/`), как собрать набор модуля, команды проверки. Не
>   копируй в него контекст — только маршрут: агент без него не узнает, что
>   `openspec/context/` существует.
> - **Волна 1 — общий контекст** (промпт 1 `context-fill`) и `glossary.md`:
>   термины, которые встречаются в коде больше чем одного модуля.
> - **Волна 2 — модули по приоритету**, по одному на агента (промпт 2
>   `context-fill`). Перед модулем прочитай его код и тесты, после — проверь
>   пути и объём. Модули одной группы — после `.md` группы.
> - **Волна 3 — ADR** из design-документов changes, которые меняли
>   архитектуру (промпт 3 `context-fill`).
> - После каждой волны — `npm run check:openspec -- --only structure,context`:
>   новые ошибки и предупреждения исправить до следующей волны.
>
> Остановись после волны 2 для первых трёх модулей и прогони на них промпты 3
> и 5: дешевле поправить подход на трёх модулях, чем на тридцати.

## Промпт 3. Аудит контекста

> Проведи аудит контекста `<модуль | весь контекст>`. Ничего не меняй — на
> выходе отчёт и список правок.
>
> **A. Механика.** Запусти `npm run check:openspec -- --only
> structure,context,validate` и выпиши: ошибки, предупреждения, модули с
> отставанием от кода, наборы сверх бюджета, файлы с полезностью ниже 50 %,
> антипаттерны с наибольшей экономией.
>
> **B. Состояние спеков.** Спеки доменов — большая часть каждого набора, и
> агент считает их правдой. Найди:
> - changes, у которых все пункты `tasks.md` выполнены, а каталог не в
>   `archive/`: их требования есть в коде, но не в основных спеках — набор
>   модуля их не содержит;
> - основные спеки возможностей, которых в коде уже нет (по ADR со статусом
>   `superseded` и по поиску в коде);
> - домены, которых нет ни в одном `domains`, и код, реализующий требования
>   спеки, которой нет в `domains` его модуля.
>
> **C. Точность.** Для каждого файла контекста модуля выпиши проверяемые
> утверждения: «файл X делает Y», «функция Z вызывается из W», «инвариант
> проверяется тестом T», «команда C делает D». Проверь каждое чтением кода
> (если утверждений больше 20 — случайная выборка из 20). Вердикт: верно /
> неверно / устарело / не проверить — с `файл:строка`. Отдельно — имена
> (функции, классы, маршруты, настройки), которых нет в коде.
>
> **D. Пробелы.** Что агенту нужно знать для типичной задачи в модуле, но в
> контексте нет:
> - точки входа и основные потоки, не названные ни в одной части;
> - инварианты, которые есть в коде (проверки в тестах, правила линтера,
>   assert, комментарии «не менять без …»), но не в контексте;
> - типовые изменения за последние полгода (`git log --since=6.months
>   --stat -- <code_paths>`): если одни и те же файлы меняются вместе, а
>   контекст этого не говорит — это пробел «как менять»;
> - команды проверки модуля: как прогнать только его тесты.
>
> **E. Лишнее.** Абзацы, которые пересказывают спеки, повторяют общий контекст
> или описывают очевидное из имён файлов; `depends_on`, без которого модуль
> можно менять; домены, поведение которых модуль не реализует.
>
> **Отчёт:** таблица метрик (раздел «Метрики аудита», с выборками), затем
> находки по шагам A–E — каждая с доказательством, серьёзностью (блокирует /
> вредит / шум) и конкретной правкой (файл, что заменить на что). В конце —
> 5 правок с наибольшим эффектом на единицу усилий.

## Промпт 4. Независимая перепроверка

> Ты — второй аудитор. Тебе дан отчёт первого аудита контекста `<модуль>`
> (только находки и правки, без рассуждений) и доступ к репозиторию.
> Перепроверь его. Ничего не меняй.
>
> 1. Каждую находку проверь заново по коду сам, не опираясь на
>    доказательство первого аудитора. Вердикт: подтверждаю / опровергаю (с
>    `файл:строка`) / не воспроизводится.
> 2. Каждую предложенную правку проверь на вред: не удаляет ли она нужное
>    агенту, не вносит ли неверное, не дублирует ли другой файл, не выходит ли
>    набор за бюджет.
> 3. Найди то, что первый аудит пропустил: возьми 10 утверждений контекста,
>    которых нет в его выборке, и проверь их; просмотри последние 20 коммитов
>    в `code_paths` модуля и найди изменения, которых контекст не отражает.
> 4. Согласие без собственной проверки запрещено: если не удалось проверить —
>    так и пиши.
>
> Итог — три списка: подтверждённые правки (их можно вносить), отклонённые (с
> причиной), новые находки; и исправленная таблица метрик.

Перепроверку запускай в отдельной сессии или отдельным подагентом, которому не
видны рассуждения первого аудита: иначе второй агент наследует ошибки первого.

## Промпт 5. Задачные пробы

> Измерь, помогает ли контекст модуля `<модуль>` решать задачи. Ничего не меняй.
>
> 1. Выбери из `git log -- <code_paths>` 5–10 коммитов последних месяцев,
>    каждый — законченная задача (фича, исправление, рефакторинг), без
>    массовых переименований и обновлений зависимостей. Для каждого
>    сформулируй задачу так, как её поставил бы человек: по сообщению
>    коммита, связанному change и диффу — но без имён файлов и решения.
> 2. Для каждой задачи — отдельный агент (или чистая сессия) на ревизии
>    **родителя** коммита. Ему дан только набор контекста модуля (строки
>    `@путь` из карточки модуля или «Копировать пути») и текст задачи. Он
>    отвечает планом: какие файлы изменит, какие инварианты и договорённости
>    соблюдёт, какие тесты добавит и запустит. Он может читать код, но каждое
>    чтение файла вне набора и каждый поиск по репозиторию записывает с
>    причиной.
> 3. Сравни план с реальным коммитом:
>    - recall файлов: доля файлов коммита (без тестов и сгенерированных),
>      названных в плане; precision — доля названных, которые коммит менял;
>    - промахи контекста: чтения и поиски вне набора, и что агент искал;
>    - нарушенные инварианты: что в плане противоречит контексту, тестам или
>      договорённостям; что ревью или CI отклонили бы;
>    - токены: сколько стоил ответ, если агент это сообщает.
> 4. Для каждого промаха и нарушения назови, какой абзац контекста его
>    предотвратил бы, и в какой файл он ложится.
>
> Итог — таблица проб (задача, коммит, recall, precision, промахи,
> нарушения), средние значения и список абзацев, которые стоит добавить.
> Повтори пробы на тех же коммитах после правок — разница и есть эффект
> правок.

Пробы — дорогая часть аудита: делай их для модулей из верхней трети
приоритета и после крупных правок контекста, а не на каждый аудит.

## Промпт 6. Регулярный аудит

> Проведи короткий аудит контекста после изменений с `<ревизия>`.
>
> 1. `git diff --stat <ревизия>..HEAD`: какие модули затронуты по
>    `code_paths`, какие changes заархивированы или выполнены.
> 2. Для затронутых модулей — шаги A и B промпта 3 и шаг C только для
>    утверждений об изменённых файлах.
> 3. Если change выполнен, но не заархивирован, — первым пунктом отчёта:
>    без архивации основные спеки и наборы модулей не содержат его требований.
> 4. Сравни метрики с прошлым отчётом; ухудшение любой метрики — находка.
>
> Отчёт — до одной страницы: метрики с дельтой, находки, правки.

## Порядок для нового большого репозитория

1. Промпт 1 — карта и приоритеты.
2. Промпт 2, волны 0–1 и три первых модуля.
3. Промпты 3, 4 и 5 на этих трёх модулях; поправить подход.
4. Промпт 2 для остальных модулей волнами, после каждой — шаг A промпта 3.
5. Промпт 5 для верхней трети модулей — исходные значения метрик.
6. Дальше — промпт 6 после каждого релиза или раз в спринт и промпт 4 на
   выборочных модулях.
