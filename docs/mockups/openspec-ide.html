Дельта читается как требования, а не как markdown

Операции разнесены по группам ADDED / MODIFIED / REMOVED / RENAMED — каждая со своим глифом и подписью, так что смысл читается и без цвета. Для изменённого требования IDE достаёт его текст из основного спека и показывает, что именно меняется: OpenSpec требует, чтобы MODIFIED содержал требование целиком, и именно здесь видно, не потерялась ли при копировании часть сценариев.

Слева — карта связей: одна capability под двумя активными changes подсвечивает пересекающиеся требования как конфликт до того, как он всплывёт при архивации.

Запуск агента — операция с бюджетом, а не свободный чат

Промпт не сочиняется IDE: его основа — вывод openspec instructions <artifact> --json, то есть ровно те инструкции, которые схема workflow предписывает для этого артефакта. К ним добавляется текст пункта плана и его критерий приёмки. Итоговый текст показывается и правится до запуска.

Предел по времени и по числу вызовов инструментов передаётся самому CLI, поэтому превышение — это отдельный исход запуска, а не зависшая вкладка. Собранные до обрыва показатели всё равно попадают в метрики задачи 2.3.

Единственный канал к модели — GigaCode CLI

IDE сама никуда не ходит по сети: весь трафик к модели идёт через процесс GigaCode CLI, авторизованный на машине разработчика. В конфигурацию попадают путь к бинарю, модель, режим, бюджеты и имя переменной окружения — значение ключа не сохраняется, не отображается и вырезается из сохраняемых промптов.

Проверка подключения выясняет версию CLI и поддержку потокового вывода. Если установленная сборка потоковый режим не принимает, IDE переходит на одноразовый вывод и честно предупреждает, что ход работы будет виден только по завершении.

Свой процесс — но всё ещё спек-ориентированный

Схема собирается графом, формой свойств и YAML одновременно: правка в любом из трёх сразу видна в остальных. Здесь у команды свой цикл — исследование перед предложением и обязательное ревью спека перед дизайном, — и IDE ничего про эти этапы не знает заранее: доска, метрики и редактор читают их из схемы.

Сохраняется всё в openspec/schemas/<name>/schema.yaml — тот самый файл, который понимает CLI. Никакого параллельного формата: коллега из терминала и агент по слэш-командам работают по этому же процессу.

Правая колонка — то, чего у CLI нет. openspec schema validate проверяет структуру и спокойно пропускает процесс, где спеков нет вообще; правила SDD отвечают на другой вопрос — остался ли процесс спек-ориентированным. Ошибка блокирует назначение схемы, но не сохранение: черновик дорабатывают постепенно. Отказаться от правила можно, но адресно и с причиной, записанной в самой схеме — чтобы отказ от SDD попал в код-ревью вместе с процессом, а не растворился в локальных настройках.
