# 17. Шаблон архитектурного документа: контекст для ИИ-агентов

[← 16 — эксплуатация](16-context-operations.md) · [оглавление](README.md)

Шаблон для архитектуры работы с контекстом в большом модульном проекте на
OpenSpec. Каждый раздел — наводящие вопросы и ссылка на документ этого
каталога, где разобраны варианты.

## Оформляйте архитектуру как change

Архитектура контекста — изменение проекта, и её удобно вести тем же
процессом, который она описывает:

| Артефакт change `add-context-architecture` | Что в нём |
| --- | --- |
| `proposal.md` | разделы 1–3 шаблона: зачем, замер, требования |
| `design.md` | разделы 4–13: модель, правила, бюджеты, проверки, владение, агенты, репозитории; у каждого решения — альтернатива |
| `tasks.md` | раздел 14: миграция по фазам, каждый пункт с проверкой |
| ADR | раздел 16: решения, которые должны попадать в срезы |
| `openspec/structure.yaml`, `quality.yaml` | исполняемая часть: раскладка и правила |

Так у архитектуры будет ревью плана, трассировка и архивация, а решения
попадут в срезы агентов через ADR.

## Скелет для копирования


## Разделы

### 1. Цель и рамки

- Какую проблему решаем: контекст не помещается, агент читает не то,
  контекст устаревает? Что из этого болит сильнее? ([01](01-problem.md))
- Какие задачи будут делать агенты: вопросы, правки модулей, сквозные фичи,
  ревью, миграции?
- Что не цель: автоматический подбор контекста, точный счёт токенов, замена
  документации для людей?

### 2. Текущее состояние (замер)

Таблица — обязательна, без неё бюджеты будут выдуманными:

| Показатель | Значение |
| --- | --- |
| репозиториев / модулей / capabilities | |
| весь контекст, ≈ токенов, и разбивка: общий, модули, ADR, спеки, активные changes, README | |
| самые тяжёлые файлы (топ-10) | |
| активных changes и их объём | |
| срезы модулей: медиана, максимум | |
| домены без модулей, модули без контекста | |

Источник — раздел «Контекст» → «Контроль». Пример заполненной таблицы —
[01](01-problem.md#масштаб-на-этом-репозитории) и
[03](03-slicing.md#замер-на-этом-репозитории).

### 3. Требования к контексту

Измеримые формулировки, по одной на атрибут качества
([01](01-problem.md#атрибуты-качества)):

- «Срез модуля ≤ 40 тыс. токенов для 95 % модулей»
- «Один и тот же выбор узлов даёт один и тот же набор файлов»
- «Отставание `context.md` от кода < 10 коммитов»
- «Ошибка связи графа ломает PR»
- «Контекст не содержит секретов»

### 4. Модель узлов и уровни

- Уровни: система, подсистема, модуль, код ([12](12-large-project.md#уровни)).
- Правило имён модулей (`<подсистема>-<модуль>`), вложенность доменов
  (`specs/<подсистема>/<capability>/`), папки ADR (`adr/<подсистема>/`).
- Что в общем контексте и сколько он весит.

### 5. Правила декомпозиции

- Критерии модуля и домена, когда делить и объединять
  ([13](13-decomposition.md)).
- Целевая форма матрицы — блочная диагональ; как поступать со сквозными
  capabilities.

### 6. Правила связей

- `depends_on`: формулировка («без чего нельзя менять»), лимиты прямых
  зависимостей и глубины ([12](12-large-project.md#ограничения-графа)).
- `domains`: только по коду; лимит на модуль.
- Границы подсистем: только через модули-контракты ([14](14-contracts.md)).
- ADR: узкая привязка `modules`/`domains` ([09](09-adr.md#привязка-к-графу)).

### 7. Бюджеты

Таблица бюджетов по уровням ([12](12-large-project.md#бюджеты-по-уровням)) и
правило: превышение — сначала чистка, потом бюджет.

### 8. Срезы по типам задач

Какой срез собирается для каждой задачи из раздела 1
([12](12-large-project.md#срезы-по-типам-задач)).

### 9. Проверки и ворота

- Какие проверки на каждом этапе: редактор, pre-commit, PR, ночь,
  архивация ([16](16-context-operations.md#ci-в-большом-репозитории)).
- Пороги и как они ужесточаются по фазам миграции.
- Какие договорённости переводятся в `quality.yaml`.

### 10. Владение и процессы

- Файл владельцев: модули, домены, ADR, общий контекст
  ([16](16-context-operations.md#владение)).
- Контекст и архивация — часть Definition of Done.
- Ритм: архивация, обзоры «Контроля», обзор ADR.
- Разбор инцидентов контекста ([16](16-context-operations.md#инцидент-контекста)).

### 11. Агенты

- Один агент или роли: планировщик, исполнители, ревьюер, хранитель,
  оркестратор ([08](08-multi-agent.md#роли)).
- Права на запись по ролям, один писатель на файл.
- Навыки и промпты: где лежат, кто ревьюит (`.claude/skills/`,
  `.agents/skills/`).

### 12. Репозитории

Монорепозиторий, федерация с заглушками или с архитектурным репозиторием
([15](15-polyrepo.md#варианты)); кто владеет заглушками.

### 13. Безопасность

Что запрещено в контексте; как это ловится
([16](16-context-operations.md#безопасность-контекста)).

### 14. Миграция

Фазы по уровням зрелости ([10](10-adoption.md#уровни-зрелости)), для каждой
— признак готовности и метрика. Существующий проект — от changes, а не от
описания всего сразу ([10](10-adoption.md#существующий-проект-brownfield)).

### 15. Риски

| Риск | Признак | Мера |
| --- | --- | --- |
| граф не поддерживают | растут домены без модулей и отставание | контекст в DoD, владельцы, CI |
| `depends_on` разрастаются | срезы ползут к бюджету | лимиты, модули-контракты, ревью архитектором |
| общий контекст раздувается | каждый срез тяжелеет одинаково | бюджет ≤ 3 тыс., ревью архитектором |
| changes копятся | объём активных changes растёт | еженедельная архивация |
| команды пишут по-разному | полезность и антипаттерны расходятся по модулям | навык `context-fill`, единые правила |
| эвристика токенов врёт для вашей модели | бюджеты не совпадают с реальным расходом | замер токенизатором своей модели на выборке файлов, поправочный коэффициент в бюджетах |

## Решения, которые надо принять

| № | Вопрос | Варианты | Критерий выбора | Рекомендация |
| --- | --- | --- | --- | --- |
| D1 | гранулярность модуля | пакет · сервис · слой | своя сборка, свой владелец, `context.md` ≤ 3 тыс. | пакет или сервис, не слой |
| D2 | гранулярность capability | по сервису · по предметной области | одна семья целей, ≤ 5 тыс. токенов | по предметной области, вложенно |
| D3 | репозитории | монорепо · федерация · федерация + архитектурный | число команд, частота сквозных изменений | монорепо, пока возможно |
| D4 | общий контекст | подробный · минимальный | он в каждом срезе | минимальный, ≤ 3 тыс. |
| D5 | правило `depends_on` | «с кем общается» · «без чего нельзя менять» | размер замыкания | «без чего нельзя менять», лимит 3–4 |
| D6 | границы подсистем | любые связи · только через контракт | рост срезов при росте проекта | только через модули-контракты |
| D7 | язык контекста | язык команды · английский | цена токенов (≈ 27 % на этом репозитории по оценке IDE) против удобства ревью и точности формулировок | язык команды для спеков (их читают люди и продукт); английский можно для `context.md` и ADR, если команде удобно ревьюить |
| D8 | ADR | общие · по подсистемам | сколько решений и чьи | подпапки `adr/<подсистема>/`, системные — в корне `adr/` |
| D9 | пороги CI | только ошибки · ошибки и предупреждения | зрелость | начать с `--fail-on error`, ужесточать по фазам |
| D10 | владение | общее · по модулям | число команд | файл владельцев на код и контекст модуля |
| D11 | агенты | один · роли | объём сквозных изменений, потребность в независимой проверке | начать с исполнитель + ревьюер со свежим срезом |
| D12 | бюджеты | по умолчанию · по замеру | наличие замера | по замеру + 25 % |

Для каждого решения в design.md — **Решение.** и **Альтернатива — …**; для
D3, D5, D6, D7 — ещё и ADR.

## Вопросы владельцам модулей

Короткое интервью перед тем, как описывать модуль (дальше — навык
`context-fill`, промпт 2):

1. Что модуль делает и чего сознательно не делает?
2. Без контекста каких модулей нельзя безопасно поменять этот? (→ `depends_on`)
3. Требования каких спеков реализует код модуля? (→ `domains`)
4. Что модуль отдаёт наружу и какие гарантии даёт? (→ модуль-контракт)
5. Какие правила нельзя нарушать и чем они проверяются? (→ «Инварианты»)
6. Какие решения по модулю приняты и какие альтернативы отвергнуты? (→ ADR)
7. Где новичок или агент ошибается чаще всего? (→ «Подводные камни»)

## Критерии готовности архитектуры

- [ ] замер текущего состояния записан
- [ ] требования измеримы
- [ ] модель уровней и правила имён утверждены
- [ ] правила связей и лимиты записаны, граница подсистем — через контракты
- [ ] бюджеты по уровням — из замера
- [ ] для каждой задачи агента описан срез
- [ ] ворота и пороги CI по фазам
- [ ] владельцы назначены в файле владельцев
- [ ] решения D1–D12 приняты, ключевые — ADR
- [ ] план миграции — `tasks.md` с проверками
- [ ] `structure.yaml` и `quality.yaml` отражают правила
