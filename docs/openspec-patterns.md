# Управляемый контекст для ИИ-агентов: постановка и паттерны

Документ в двух частях. **Часть I** — архитектурная постановка: какую
проблему решает OpenSpec IDE, на каких решениях она построена и почему.
**Часть II** — как эти решения применяются в самом репозитории: матрица
модулей и доменов, раскладка файлов, работа с агентом. Нормативная часть —
[`openspec/config.yaml`](../openspec/config.yaml),
[`openspec/context/02-conventions.md`](../openspec/context/02-conventions.md) и
разделы README «Контекст модулей» и «Контроль контекста».

# Часть I. Архитектурная постановка

## 1. Проблема

Качество работы агента определяется тем, что лежит у него в контексте. На
маленьком проекте это не вопрос: весь README, все спеки и описание кода
помещаются в окно. На большом — десятки модулей и сервисов, сотни
capabilities, история решений — описание проекта разрастается, и
появляются три проблемы, которые сами по себе не решаются.

1. **Всё не помещается, а «всё» и не нужно.** Положить в окно весь контекст
   проекта дорого, а там, где он и влезает, агент вязнет в нерелевантном:
   внимание размывается, нужное теряется в середине. Задаче «поменять
   репликацию» нужны спека репликации, контекст двух модулей, которые её
   реализуют, и решение о синхронной записи — а не описание UI и биллинга.
2. **Агент сам выбирает, что читать, — неуправляемо.** Поиск по репозиторию
   находит то, что похоже по словам, и пропускает неочевидное: модуль, от
   которого зависит изменяемый, ADR, запрещающий очевидное решение, спеку
   соседнего домена. Выбор не воспроизводится: два запуска на одной задаче
   читают разное, и нельзя сказать, *что именно* агент знал.
3. **Контекст гниёт молча.** Его пишут один раз, а код уходит вперёд: пути
   пропадают, модули переименовываются, абзацы копируются из файла в файл,
   остаются заготовки «TODO». Ошибка в контексте не роняет сборку — она
   незаметно ухудшает каждый следующий запуск агента. Чем больше проект, тем
   больше такого балласта и тем дороже он обходится.

## 2. Цель

Сделать контекст **инженерным артефактом** — таким же, как код:
структурированным, адресуемым по частям и проверяемым автоматически.

Из этого две функции, ради которых создана IDE:

- **Подшивка среза.** Для задачи собирается не весь контекст, а
  детерминированный набор файлов — только то, что относится к затронутым
  модулям и доменам, с их зависимостями и решениями.
- **Валидация.** Связи, объём, содержимое и соответствие коду проверяются
  так же, как тесты: в редакторе («Проблемы» VS Code) и в CI
  (`openspec-ide-check`). Сломанный контекст ломает PR.

Вторая функция — условие первой: срез точен ровно настолько, насколько
точны связи, по которым он собирается.

## 3. Атрибуты качества

| Атрибут | Требование | Чем обеспечено |
| --- | --- | --- |
| **Масштабируемость** | объём набора растёт с размером *затронутой* части, а не всего проекта | срез по графу модулей и доменов, бюджет `max_tokens` на набор |
| **Воспроизводимость** | один и тот же выбор даёт один и тот же набор | чистая функция `contextBundle` в `core` без ввода-вывода (ADR-004) |
| **Проверяемость** | каждая связь и каждый путь проверяются машиной | правила карты и контроля контекста, одни и те же в IDE и CI (ADR-002) |
| **Прозрачность** | видно, что именно агент получил и сколько это стоит | набор строками `@путь`, оценка токенов и полезности у каждого файла |
| **Независимость от агента** | работает с любым агентом в терминале или редакторе | контекст — markdown с frontmatter, IDE агентов не запускает (ADR-006) |
| **Без своей инфраструктуры** | никакой БД, сервиса индексации, ключей API | всё — файлы в git рядом с кодом, источник истины — диск и CLI OpenSpec (ADR-003) |

## 4. Ограничения

- Источник истины — файлы `openspec/` и CLI `@fission-ai/openspec`; IDE не
  хранит своего состояния проекта.
- IDE не вызывает LLM: ни для подбора контекста, ни для проверки. Все
  проверки — детерминированные правила.
- Токенизатора модели нет: объём оценивается эвристикой (латиница / 4 +
  прочее / 2,5) с точностью около ±35 % по файлу — поэтому везде «≈».

## 5. Ключевая идея: контекст как граф по двум осям

Контекст проекта раскладывается по двум независимым осям — **домены** и
**модули** — и связывается явными ссылками.

| Ось | Что описывает | Файл | Как меняется |
| --- | --- | --- | --- |
| **Домен** (capability) | *что* система должна делать — требования и сценарии | `openspec/specs/<домен>/spec.md` | через changes OpenSpec, медленно |
| **Модуль** | *где и как* это сделано — устройство, контракты, инварианты кода | `openspec/context/modules/<модуль>/context.md` | вместе с кодом |
| **ADR** | *почему* так, а не иначе | `openspec/context/adr/ADR-NNN-*.md` | дописывается, не переписывается |
| **Общий контекст** | что нужно в любой задаче | `openspec/context/NN-*.md` | редко |

Узлы графа — эти файлы. Рёбра — поля frontmatter:

```
              domains (многие-ко-многим)
   модуль ────────────────────────────────► домен (спека)
     │  ▲                                     ▲
     │  │ modules                    domains  │
     │  └──────────────── ADR ────────────────┘
     │
     ├── depends_on ──► модуль        (без чьего контекста нельзя менять этот)
     └── code_paths ──► каталоги кода (связь с реальностью)
```

**Почему две оси, а не одна.** Задачи в большом проекте приходят с обеих
сторон: «поменять поведение репликации» (домен) и «переписать хранилище в
`sds-master`» (модуль). Одно и то же поведение реализуют несколько модулей,
один модуль обслуживает несколько доменов. Матрица позволяет войти с любой
стороны и автоматически получить вторую.

Рассмотренные альтернативы:

- **Только модули** (файл-описание в каждой папке, вроде `AGENTS.md`):
  требование, которое реализуют три модуля, либо копируется в три файла,
  либо теряется. Нет места для поведения, которое не принадлежит одному
  каталогу.
- **Только домены** (одни спеки): агент знает, *что* сделать, но не знает
  устройства кода, его контрактов и инвариантов.
- **Один большой документ**: нельзя взять часть, нельзя проверить, к какому
  коду относится абзац.
- **Семантический поиск / RAG**: подбор по похожести не воспроизводится, его
  нельзя проверить и нельзя отревьюить. Явные связи пишет и проверяет
  человек, их видно в диффе PR.

**Метаданные отделены от содержимого.** Граф описан во frontmatter
`index.md` модуля и ADR, а текст для агента — в `context.md`. `index.md` в
набор не входит: связи разбираются машиной и не тратят токены агента.

## 6. Подшивка среза

### Алгоритм

Пользователь выбирает узлы: модули `M`, домены `D`, ADR `A`. Набор
(`contextBundle` в `packages/core/src/contextMap.ts`) — это:

```
M*   = M ∪ транзитивное замыкание M по depends_on
набор = общий контекст
      ∪ context.md каждого модуля из M*
      ∪ спеки доменов модулей M* ∪ спеки D
      ∪ действующие ADR, ссылающиеся на модули M* или домены D
      ∪ A (явно выбранные — даже недействующие)
```

- Порядок загрузки фиксирован: общий контекст → модули → спеки → ADR;
  каждый файл входит один раз; циклы и неописанные модули не ломают обход.
- Флажками можно отключить зависимости (`depends_on`) и спеки доменов
  модулей — тогда в наборе только явно выбранное.
- Недействующие ADR (`superseded`, `deprecated`…) в набор не входят: история
  решений не должна спорить с действующими.
- Результат отдаётся агенту строками `@путь` — в таком виде его принимают
  агенты в терминале — вместе с оценкой токенов и долей полезных.

### Пример

Фикстура [`tests/fixtures/context-map`](../tests/fixtures/context-map/)
моделирует распределённое хранилище сессий:

```
sds-master ── depends_on ──► sds-impl ── depends_on ──► sds-router
  domains: session-lifecycle,            domains: replication,
           session-data, replication              servant-master-api
ADR-001 (синхронная репликация): modules [sds-master, sds-impl], domains [replication]
```

| Выбор | Что попадёт в набор | Что не попадёт |
| --- | --- | --- |
| домен `replication` | общий контекст, спека `replication`, ADR-001 | контекст модулей, остальные спеки |
| модуль `sds-impl` | общий контекст, `context.md` `sds-impl`, спеки `replication` и `servant-master-api`, ADR-001 | `sds-master` и его домены `session-*`, спека `cm-cluster-api` |
| модуль `sds-master` | то же плюс `context.md` `sds-master` и спеки `session-lifecycle`, `session-data` | спека `cm-cluster-api` |

Зависимость направлена в одну сторону: чтобы менять `sds-master`, нужны
контракты `sds-impl`, а чтобы менять `sds-impl`, контекст `sds-master` не
нужен — то, что сломается у зависимых, ловят тесты и проверки.

### Дисциплина связей — условие масштабирования

Срез маленький, только пока связи узкие. Два правила держат его таким:

- **`depends_on` — «без чего нельзя менять», а не «с кем общается».**
  Модуль, который вызывает пять сервисов, зависит по контексту только от
  тех, чьи контракты нужно знать при правке. Иначе транзитивное замыкание
  быстро становится всем проектом и срез теряет смысл.
- **`domains` — то, что код модуля действительно реализует**, проверенное
  по коду, а не по названию. Лишний домен — лишняя спека в каждом наборе;
  пропущенный — агент не узнает о требовании.

Бюджет `max_tokens` в `index.md` делает это измеримым: набор, вышедший за
бюджет, — предупреждение, и первая реакция на него — сузить связи и убрать
повторы, а не поднять бюджет.

## 7. Валидация

Граф контекста ошибается двумя способами: **громко** (набор не собирается)
и **тихо** (набор собирается, но без нужного файла или с мусором). Тихие
ошибки опаснее — агент работает с неполной картиной, и этого никто не
видит. Поэтому проверки разбиты на уровни по тому, что они защищают.

| Уровень | Что ловит | Почему это важно для среза | Уровень замечания |
| --- | --- | --- | --- |
| **Целостность графа** | домен из `domains` не найден в `openspec/specs/`; модуль из `depends_on` или ADR не описан; цикл и зависимость от себя; два модуля с одним `module`; нет `index.md` или frontmatter не разбирается | набор молча теряет спеку или модуль | ошибка |
| **Полнота покрытия** | домен не относится ни к одному модулю; нет `context.md`; путь из `code_paths` не найден | спеку никто не подошьёт; модуль без описания; связь с кодом разорвана | предупреждение |
| **Объём** | файл больше 8000 токенов; набор модуля больше `max_tokens` | срез перестаёт быть срезом | предупреждение |
| **Содержимое** | абзацы-повторы между файлами; пустой `context.md`; файл в `openspec/context/`, который не входит ни в один набор; низкий коэффициент полезности; антипаттерны (большие блоки кода, base64, псевдографика, HTML, «вода», капс) | токены тратятся на балласт; файл вне наборов агент не увидит никогда | предупреждение / сведение |
| **Связь с реальностью** | путь из текста не найден; контекст модуля отстаёт от кода на N коммитов (по git, после последней правки `context.md`); модуль без `code_paths` | описание расходится с кодом | предупреждение / сведение |

В фикстуре `context-map` это выглядит так: `sds-router` в `depends_on` не
описан — ошибка; спека `cm-cluster-api` не относится ни к одному модулю —
предупреждение; каталог кода `sds-impl/src` не найден — предупреждение.

Свойства валидации:

- **Одни правила везде.** Замечание с файлом и строкой одинаково видно в
  разделе «Контекст», в панели «Проблемы» VS Code и в
  `openspec-ide-check --only context` в CI — всё это вызывает одни и те же
  функции `core` через встроенный бэкенд (ADR-002, ADR-004).
- **Сведение — не ошибка.** Отставание от кода, низкая полезность и
  антипаттерны — подсказки человеку: решать, устарело ли описание, ему.
  Порог CI по умолчанию — `--fail-on error`.
- **Оценки честные.** Токены и экономия — со знаком ≈; формулы и замеры на
  этом репозитории — в design changes `add-context-control`,
  `add-context-usefulness`, `add-context-antipatterns`.
- **Правило, которое можно проверить, проверяется.** Договорённость из
  `config.yaml`, которую агент может прочитать и забыть, переносится в
  `quality.yaml` как машинная проверка.

## 8. Решения

| ADR | Решение | Что даёт постановке |
| --- | --- | --- |
| [ADR-003](../openspec/context/adr/ADR-003-cli-source-of-truth.md) | источник истины — файлы и CLI OpenSpec | контекст живёт в git, ревьюится в PR, повторяется из терминала |
| [ADR-004](../openspec/context/adr/ADR-004-pure-core.md) | чистый `core` без Node API | сборка набора и правила детерминированы и тестируются без диска |
| [ADR-002](../openspec/context/adr/ADR-002-embedded-backend.md) | бэкенд в процессе расширения, тот же — в CI | правила IDE и CI совпадают по построению |
| [ADR-006](../openspec/context/adr/ADR-006-context-not-agents.md) | IDE готовит контекст, а не запускает агентов | инструмент не привязан к агенту; фокус — на управляемом контексте |
| [ADR-005](../openspec/context/adr/ADR-005-agent-in-ide.md) | *(отменено)* запуск агента из IDE | показал, что не хватает не запуска, а управляемого контекста |

## 9. Не цели

- **Не автоматический подбор контекста.** Связи задаёт человек; IDE их
  проверяет и подсказывает пробелы (например, у замечания `code-message` в
  разделе «Качество» — «цитата нашлась в другом модуле», то есть связь
  домена с модулем, вероятно, пропущена), но не дописывает сама.
- **Не точный счёт токенов** — для этого нужен токенизатор конкретной
  модели.
- **Не запуск агентов и не вызов LLM.**
- **Не замена документации для людей**: контекст пишется для агента —
  коротко, проверяемо, без пересказа спеков.

# Часть II. Как это применяется в репозитории

## 10. Матрица этого репозитория

Модули — пакеты монорепозитория, зависимости — по сборке и импортам:

```
core ──► server ──► vscode
  │         └─────► check
  └────► web
```

| Модуль | `code_paths` | `depends_on` | `max_tokens` |
| --- | --- | --- | --- |
| `core` | `packages/core` | — | 22000 |
| `server` | `packages/server` | `core` | 30000 |
| `web` | `packages/web` | `core` | 25000 |
| `vscode` | `packages/vscode` | `server` | 36000 |
| `check` | `packages/check` | `server` | 30000 |

Модули × основные спеки (`openspec/specs/`):

| Домен ↓ / модуль → | core | server | web | vscode | check | модулей |
| --- | :-: | :-: | :-: | :-: | :-: | :-: |
| `workflow-board` | ✓ | | ✓ | | | 2 |
| `spec-delta-viewer` | ✓ | | ✓ | | | 2 |
| `task-metrics` | ✓ | ✓ | ✓ | | | 3 |
| `workflow-designer` | ✓ | ✓ | ✓ | | | 3 |
| `workspace-explorer` | ✓ | ✓ | | ✓ | | 3 |
| `sdd-conformance` | ✓ | | | | | 1 |
| `ide-runtime` | | ✓ | | | | 1 |
| `artifact-editor` | | ✓ | | ✓ | | 2 |
| `archive-preview` | | ✓ | ✓ | | | 2 |
| `vscode-extension` | | | | ✓ | | 1 |
| `agent-bridge` | | | | | | 0 — удаляется change `focus-context-map` |

Правила ведения матрицы:

- **Домен без модулей** — сигнал: либо поведение никто не реализует (как
  `agent-bridge` после ADR-006), либо модуль забыл его перечислить.
- **Модуль без доменов** (`check`) допустим для инфраструктуры поверх чужого
  поведения: `check` запускает те же проверки, что и IDE.
- **В `domains` — только существующие основные спеки.** Capabilities, которые
  пока живут в дельтах активных changes (`context-map`, `quality-view`,
  `spec-quality`, `spec-consistency`, `change-drift`, `conformance-check`,
  `spec-authoring`, `structure-conformance`, `panel-ui`,
  `change-traceability`), в `domains` не попадают — ссылка на
  несуществующий спек даёт ошибку. Домен добавляется в `index.md` модулей
  при архивации change, который создаёт спек.
- **Матрица задаёт форму плана.** Пункты `tasks.md` группируются по модулям в
  порядке зависимостей — «1. Модель (`core`) → 2. Сервер → 3. Интерфейс
  (`web`) → 4. VS Code → 5. Документация». Каждая группа проверяема
  отдельно и даёт агенту отдельный шаг со своим срезом.

## 11. Структура файлов

```
openspec/
  config.yaml                 схема spec-driven, контекст проекта для CLI, rules по артефактам
  structure.yaml              разрешённая раскладка папок (проверяется IDE и CI)
  quality.yaml                машинно-проверяемые правила качества, пороги, исключения
  specs/
    <домен>/spec.md           основные спеки — ось «домены»
  changes/
    <глагол>-<что>/           активный change
      .openspec.yaml          schema, created
      proposal.md             Why / What Changes / Не входит / Capabilities / Impact
      design.md               Context / Decisions (решение + альтернатива) / замер
      tasks.md                группы по модулям, пункты с проверкой и ↳-ссылками
      specs/<домен>/spec.md   дельта: ADDED / MODIFIED / REMOVED / RENAMED Requirements
    archive/
      YYYY-MM-DD-<имя>/       заархивированные changes
  context/
    01-project.md             общий контекст: продукт, источник истины, устройство, термины
    02-conventions.md         договорённости: язык, процесс, код, проверка
    modules/<модуль>/         ось «модули»
      index.md                только frontmatter — узел и рёбра графа: module, description,
                              domains, code_paths, depends_on, max_tokens
      context.md              текст для агента: назначение, устройство, контракты,
                              инварианты, как менять, подводные камни
    adr/
      ADR-NNN-<slug>.md       status, date, modules, domains; Контекст / Решение /
                              Рассмотренная альтернатива / Последствия

  mockups/*.html              HTML-макеты интерфейса до change
  openspec-patterns.md        этот файл
.claude/skills/, .claude/commands/opsx/
                              навыки и команды OpenSpec для Claude Code
.agents/skills/               те же навыки для других агентов (отличаются только
                              именами команд: /openspec-* вместо /opsx:*)
tests/fixtures/<сценарий>/openspec/
                              фикстурные OpenSpec-проекты для тестов и e2e
```

### Именование

- **Change** — kebab-case с глаголом-префиксом: `add-*` (новая
  возможность), `fix-*` (исправление), `rework-*` / `redesign-*`
  (переделка), `validate-*`, `focus-*` (сужение/замена).
- **Архив** — `YYYY-MM-DD-<имя>`; связанные changes архивируются пачкой.
- **Домен** — kebab-case, путь может быть вложенным (`identity/auth`). Имя в
  `Capabilities` proposal — точный путь спека.
- **Общий контекст** — `NN-тема.md`: номер задаёт порядок в наборе.
- **ADR** — `ADR-NNN-<slug>.md`, номера не переиспользуются. Отменённое
  решение не переписывается: `status: superseded` + `superseded_by` (ADR-005
  → ADR-006).

### Форма артефактов

- **proposal.md** — `## Why` (проблема, ссылка на макет), `## What Changes`,
  явное «Не входит: …», `## Capabilities` с New / Modified и точными путями,
  `## Impact` — код, API (маршруты, `API_REVISION`), файлы проекта.
- **Дельта спека** — `### Requirement:` с нормативом «ДОЛЖЕН/ДОЛЖНА
  (SHALL)», у каждого минимум один `#### Scenario:` с **WHEN**/**THEN** на
  конкретных данных фикстур.
- **design.md** — `## Context` со ссылками на proposal, дельту, макеты и
  change, поверх которого строится; `## Decisions` — `### N.` с
  **Решение.** и **Альтернатива — …**; для эвристик — «Замер на этом
  репозитории».
- **tasks.md** — группы по модулям; пункт `- [ ] N.M …; проверка — <тест>`,
  под ним `↳ <домен> / <сценарий>`. Последняя группа — «Документация»:
  README, контекст затронутых модулей, `verify`, `test:e2e`,
  `openspec validate <change> --strict`.

## 12. Работа с агентом

### Роли

IDE не запускает агента: агент работает в терминале или редакторе, IDE
готовит ему срез, проверяет результат и подхватывает изменения файлов.
Человек решает, что делать (proposal, макет, ревью) и поддерживает связи
графа; агент пишет артефакты, код и контекст по плану; проверки ловят
расхождения.

### Жизненный цикл change

```
explore ──► mockups ──► propose ──► (update) ──► apply ──► archive
```

1. **Explore** (`/opsx:explore`) — обсуждение без кода; артефакты change —
   только после явного подтверждения объёма.
2. **Макеты** — для UI сначала `docs/mockups/<тема>.html` отдельным
   коммитом `docs(mockups): …`.
3. **Propose** (`/opsx:propose`) — все артефакты за один шаг, коммит
   `docs(openspec): change <имя>` **до** кода.
4. **Update** (`/opsx:update`) — новое решение сначала в артефакты, потом в
   код.
5. **Apply** (`/opsx:apply`) — по группам `tasks.md`, на каждую группу —
   срез её модуля; после группы — `npm run verify`; пункт `[x]` — только
   когда его проверка прошла. Коммит `feat(<scope>): …`.
6. **Archive** (`/opsx:archive`) — после `openspec validate --strict`;
   дельты сливаются в основные спеки, новые домены добавляются в `domains`
   модулей.

Один PR — одна фича или серия связанных changes. Крупную возможность режут
на серию changes поверх незаархивированных (`focus-context-map` →
`add-context-selection` → `add-context-control` → `add-context-usefulness`
→ `add-context-antipatterns`); пересечения их дельт показывает раздел
«Пересечения».

### Контекст — часть change

- **Агенту дают срез, а не репозиторий**: набор модуля или нескольких узлов
  строками `@путь` из карточки модуля или панели «Набор контекста».
- **Контекст обновляется в том же change, что и код** — последний пункт
  плана. Иначе отставание от кода растёт, и IDE отметит его сведением.
- **Контекст пишет агент по навыку `context-fill`**
  (`.claude/skills/context-fill/SKILL.md`): общий контекст, модуль, ADR,
  обновление после изменений, сжатие перегруженного набора. Правила навыка
  — те же, что проверяет валидация: проверяемые пути и имена, без пересказа
  спеков, без повторов и заготовок, неизвестное — «(проверить)».
- **Решение — в ADR** с `modules` и `domains`, 200–600 токенов: так оно
  попадёт ровно в те срезы, где нужно.

### Самопроверка агента

| Что менял | Команда |
| --- | --- |
| код | `npm run verify` (typecheck, eslint, Vitest) |
| интерфейс | `npm run test:e2e` |
| артефакты change | `openspec validate <change> --strict` |
| контекст, структуру | `npm run check:openspec -- --only structure,context` |
| всё перед PR | `npm run check:openspec` |

Отчёт агента — что сделано, что не прошло, объём контекста в токенах до и
после, список «(проверить)».

### Язык

Артефакты, контекст, пользовательские строки, комментарии и сообщения
коммитов — на русском; идентификаторы, пути, код — на английском.
