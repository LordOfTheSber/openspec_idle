# Паттерны работы с OpenSpec в этом репозитории

Сводка договорённостей, которые сложились при разработке OpenSpec IDE по
самому OpenSpec: как устроена матрица «модули × домены», где какие файлы
лежат и как в этом процессе работает ИИ-агент. Нормативная часть —
[`openspec/config.yaml`](../openspec/config.yaml),
[`openspec/context/02-conventions.md`](../openspec/context/02-conventions.md) и
разделы README «Контекст модулей» и «Контроль контекста»; здесь — как это
применяется на практике и почему.

## 1. Матричная структура: модули × домены

Проект описывается по двум независимым осям.

| Ось | Что это | Где лежит | Отвечает на вопрос |
| --- | --- | --- | --- |
| **Домен** (capability) | поведение системы — требования и сценарии | `openspec/specs/<домен>/spec.md` | *что* система должна делать |
| **Модуль** | часть кода — пакет, сервис | `openspec/context/modules/<модуль>/` | *где и как* это сделано |

Связь между ними — **многие-ко-многим**: модуль перечисляет домены, поведение
которых реализует его код (`domains` в `index.md`), а у домена видны все
модули, которые его перечислили. Один домен обычно размазан по нескольким
модулям (модель в `core`, маршрут в `server`, экран в `web`), один модуль
обслуживает несколько доменов.

### Модули

Зависимости — по сборке и импортам, а не «с кем общается»:

```
core ──► server ──► vscode
  │         └─────► check
  └────► web
```

| Модуль | `code_paths` | `depends_on` | `max_tokens` |
| --- | --- | --- | --- |
| `core` | `packages/core` | — | 22000 |
| `server` | `packages/server` | `core` | 30000 |
| `web` | `packages/web` | `core` | 25000 |
| `vscode` | `packages/vscode` | `server` | 36000 |
| `check` | `packages/check` | `server` | 30000 |

### Матрица

Текущее состояние основных спеков (`openspec/specs/`):

| Домен ↓ / модуль → | core | server | web | vscode | check | модулей |
| --- | :-: | :-: | :-: | :-: | :-: | :-: |
| `workflow-board` | ✓ | | ✓ | | | 2 |
| `spec-delta-viewer` | ✓ | | ✓ | | | 2 |
| `task-metrics` | ✓ | ✓ | ✓ | | | 3 |
| `workflow-designer` | ✓ | ✓ | ✓ | | | 3 |
| `workspace-explorer` | ✓ | ✓ | | ✓ | | 3 |
| `sdd-conformance` | ✓ | | | | | 1 |
| `ide-runtime` | | ✓ | | | | 1 |
| `artifact-editor` | | ✓ | | ✓ | | 2 |
| `archive-preview` | | ✓ | ✓ | | | 2 |
| `vscode-extension` | | | | ✓ | | 1 |
| `agent-bridge` | | | | | | 0 — удаляется change `focus-context-map` |

Как читать и поддерживать матрицу:

- **Домен без модулей** — сигнал: либо поведение никто не реализует (как
  `agent-bridge` после ADR-006), либо модуль забыл его перечислить. IDE
  показывает это предупреждением.
- **Модуль без доменов** (`check`) допустим, если модуль — инфраструктура
  поверх чужого поведения: `check` запускает те же проверки, что и IDE.
- **В `domains` — только существующие основные спеки.** Capabilities, которые
  пока живут только в дельтах активных changes (`context-map`, `quality-view`,
  `spec-quality`, `spec-consistency`, `change-drift`, `conformance-check`,
  `spec-authoring`, `structure-conformance`, `panel-ui`,
  `change-traceability`), в `domains` не попадают: ссылка на несуществующий
  спек — ошибка. Домен добавляется в `index.md` модулей при архивации change,
  который создаёт спек.
- **Проверяй по коду, а не по названию**: домен в `domains` модуля, только если
  код модуля действительно реализует его требования.
- **ADR — третий слой**: `modules` и `domains` во frontmatter привязывают
  решение к ячейкам матрицы, и ADR попадает в набор контекста этих модулей и
  доменов.
- **Матрица задаёт форму плана.** Пункты `tasks.md` группируются по модулям в
  порядке зависимостей — «1. Модель (`core`) → 2. Сервер → 3. Интерфейс
  (`web`) → 4. VS Code → 5. Документация». Каждая группа самостоятельно
  проверяема и даёт отдельный шаг агенту.

### Набор контекста

Из матрицы IDE собирает набор файлов для задачи: общий контекст +
`context.md` модуля и транзитивно его `depends_on` + спеки их доменов + ADR
(только действующие). Набор отдаётся агенту строками `@путь`. Бюджет набора —
`max_tokens` в `index.md` (текущий объём + ~25 % запаса); превышение — повод
сжать контекст, а не поднимать бюджет.

## 2. Структура файлов

```
openspec/
  config.yaml                 схема spec-driven, контекст проекта для CLI, rules по артефактам
  structure.yaml              разрешённая раскладка папок (проверяется IDE и CI)
  quality.yaml                машинно-проверяемые правила качества, пороги, исключения
  specs/
    <домен>/spec.md           основные спеки — источник истины о поведении
  changes/
    <глагол>-<что>/           активный change
      .openspec.yaml          schema, created
      proposal.md             Why / What Changes / Не входит / Capabilities / Impact
      design.md               Context / Decisions (решение + альтернатива) / замер
      tasks.md                группы по модулям, пункты с проверкой и ↳-ссылками
      specs/<домен>/spec.md   дельта: ADDED / MODIFIED / REMOVED / RENAMED Requirements
    archive/
      YYYY-MM-DD-<имя>/       заархивированные changes
  context/
    01-project.md             общий контекст: продукт, источник истины, устройство, термины
    02-conventions.md         договорённости: язык, процесс, код, проверка
    modules/<модуль>/
      index.md                только frontmatter: module, description, domains,
                              code_paths, depends_on, max_tokens
      context.md              назначение, устройство (таблица «файл — что делает»),
                              контракты, инварианты, как менять, подводные камни
    adr/
      ADR-NNN-<slug>.md       status, date, modules, domains; Контекст / Решение /
                              Рассмотренная альтернатива / Последствия
docs/
  mockups/*.html              HTML-макеты интерфейса до change
  openspec-patterns.md        этот файл
.claude/skills/, .claude/commands/opsx/
                              навыки и команды OpenSpec для Claude Code
.agents/skills/               те же навыки для других агентов (отличаются только
                              именами команд: /openspec-* вместо /opsx:*)
tests/fixtures/<сценарий>/openspec/
                              фикстурные OpenSpec-проекты для тестов и e2e
```

### Именование

- **Change** — kebab-case с глаголом-префиксом по виду изменения: `add-*`
  (новая возможность), `fix-*` (исправление поведения), `rework-*` /
  `redesign-*` (переделка), `validate-*`, `focus-*` (сужение/замена).
- **Архив** — `YYYY-MM-DD-<имя>`; дата — день архивации. Связанные changes
  архивируются пачкой одним коммитом.
- **Домен** — существительное kebab-case, путь может быть вложенным
  (`identity/auth`). Имя в `Capabilities` proposal — точный путь спека.
- **Общий контекст** — `NN-тема.md`: номер задаёт порядок в наборе.
- **ADR** — `ADR-NNN-<slug>.md`, номера не переиспользуются. Отменённое решение
  не переписывается: `status: superseded` + `superseded_by` (как ADR-005 →
  ADR-006).

### Форма артефактов

- **proposal.md** — `## Why` (проблема, ссылка на макет), `## What Changes`
  (жирные заголовки пунктов), явное «Не входит: …», `## Capabilities` с New /
  Modified и точными путями, `## Impact` — код (файлы и функции), API (новые
  маршруты, ревизия `API_REVISION`), файлы проекта.
- **Дельта спека** — `# Spec Delta: <домен>`, требования
  `### Requirement:` с нормативом «ДОЛЖЕН/ДОЛЖНА (SHALL)», у каждого минимум
  один `#### Scenario:` с **WHEN**/**THEN** на конкретных данных фикстур
  («у дельты `data-export` одно предупреждение `vague-wording`»), а не
  абстрактных.
- **design.md** — `## Context` начинается со ссылок: «Мотивация — в
  `proposal.md`, требования — в дельте `specs/<домен>`, макеты — …, строится
  поверх `<change>`». Далее `## Decisions` — `### N. <решение>` с абзацами
  **Решение.** и **Альтернатива — …** (почему отказались). Для эвристик и
  метрик — **«Замер на этом репозитории»**: функцию прогоняют на самом проекте
  и записывают числа.
- **tasks.md** — группы по модулям; пункт формата
  `- [ ] N.M <что сделать>; проверка — <тест/e2e/команда>`, под ним строки
  `↳ <домен> / <сценарий>` для трассировки. Последняя группа —
  «Документация»: README, контекст затронутых модулей, `verify`, `test:e2e`,
  `openspec validate <change> --strict`.

### Что проверяется автоматически

| Правило | Где задано | Чем проверяется |
| --- | --- | --- |
| Раскладка папок | `openspec/structure.yaml` | раздел «Структура», `check:openspec` |
| Связи модулей, доменов, ADR; объём, повторы, пропавшие пути, отставание | `openspec/context/**` | раздел «Контекст», `check:openspec --only context` |
| Решение в design с альтернативой, пункт плана с метрикой приёмки | `rules` в `config.yaml` → `artifacts` в `quality.yaml` | раздел «Качество», «Проблемы», CI |
| Формат дельт и спеков | CLI OpenSpec | `openspec validate --strict` |

Правило из `config.yaml`, которое агент может «прочитать и забыть», переносится
в `quality.yaml` как проверка — так оно перестаёт зависеть от внимательности
агента.

## 3. Паттерны работы с ИИ

### Роли

IDE не вызывает LLM и не запускает агентов (ADR-006): агент работает в
терминале или редакторе, а IDE готовит для него контекст, проверяет
результат и показывает изменения файлов. Человек решает, что делать
(proposal, макет, ревью), агент — пишет артефакты и код по плану, проверки —
ловят расхождения.

### Жизненный цикл change

```
explore ──► mockups ──► propose ──► (update) ──► apply ──► sync/archive
 /opsx:explore  HTML    /opsx:propose  /opsx:update  /opsx:apply  /opsx:archive
```

1. **Explore** (`/opsx:explore`) — обсуждение без кода. Агент может писать
   только артефакты change и только после явного подтверждения объёма.
2. **Макеты** — для любого UI сначала `docs/mockups/<тема>.html`, отдельным
   коммитом `docs(mockups): …`. Proposal и design ссылаются на макет, спека
   описывает поведение, видимое на нём.
3. **Propose** (`/opsx:propose`) — все артефакты за один шаг, отдельным
   коммитом `docs(openspec): change <имя>` **до** кода. Ревью плана — ревью
   этого коммита.
4. **Update** (`/opsx:update`) — новое решение по ходу работы сначала
   вносится в артефакты и согласуется между ними, потом в код. Код при этом не
   трогается.
5. **Apply** (`/opsx:apply`) — по группам `tasks.md`. После каждой группы —
   `npm run verify` (`operations.apply.guidance` в `config.yaml`); пункт
   отмечается `[x]` только когда его проверка прошла. Коммит
   `feat(<scope>): …`, мелкие правки после — `fix(<scope>): …`.
6. **Archive** (`/opsx:archive`) — после `openspec validate --strict`;
   дельты сливаются в основные спеки, затем домены добавляются в `domains`
   модулей. Архивируют пачкой, когда серия changes по одной capability
   закончена.

Один PR — одна фича или серия связанных changes, коммиты в порядке
`docs(mockups)` → `docs(openspec) change` → `feat` → `fix`. Ветка — `claude/<имя>`.

### Серии changes поверх незаархивированных

Крупную возможность режут на серию changes, каждый строится поверх
предыдущего, ещё не заархивированного: `focus-context-map` →
`add-context-selection` → `add-context-control` → `add-context-usefulness` →
`add-context-antipatterns` — все с `ADDED Requirements` в одну capability
`context-map`. В `design.md` это фиксируется строкой «Строится поверх
`<change>`». Риск такой серии — пересечения дельт; их показывает раздел
«Пересечения» (`add-change-drift`), а перед архивацией серию проверяют
целиком.

### Контекст для агента

- **Набор, а не весь репозиторий.** Агенту дают набор модуля (или нескольких
  узлов матрицы) строками `@путь` — из карточки модуля или панели «Набор
  контекста».
- **Контекст пишет и чинит агент по навыку `context-fill`**
  (`.claude/skills/context-fill/SKILL.md`): пять промптов — общий контекст,
  модуль, ADR, обновление после изменений кода, сжатие перегруженного набора.
- **Правила контекста**: только проверяемые пути и точные имена из кода; не
  пересказывать спеки и design — ссылаться; не повторять абзацы между
  файлами; никаких заготовок и `TODO`; неизвестное — «(проверить)» с тем,
  что проверить.
- **Контекст обновляется в том же change**, что и код: последний пункт плана
  — «контекст модулей …». Отставание контекста от кода (коммиты в
  `code_paths` после правки `context.md`) IDE показывает сведением.
- **Архитектурное решение — в ADR**, сжато (200–600 токенов), со ссылкой на
  design.md, где оно принято.
- **Токены считаются**: оценка IDE ≈ (латиница / 4 + прочее / 2,5), бюджет
  `max_tokens`, коэффициент полезности, антипаттерны (большие блоки кода,
  base64, псевдографика, HTML, «вода», капс). Перед тем как поднять бюджет —
  убрать повторы, пересказ и лишние `depends_on`.

### Самопроверка агента

После правки агент запускает проверки сам, а не оставляет их человеку:

| Что менял | Команда |
| --- | --- |
| код | `npm run verify` (typecheck, eslint, Vitest) |
| интерфейс | `npm run test:e2e` |
| артефакты change | `openspec validate <change> --strict` |
| контекст, структуру | `npm run check:openspec -- --only structure,context` |
| всё перед PR | `npm run check:openspec` |

Отчёт агента — что сделано, что не прошло, объём контекста в токенах до и
после, список «(проверить)».

### Честность оценок

- Эвристики подаются со знаком ≈ и с границами точности, а их калибровка —
  «Замер на этом репозитории» в design.md, а не уверенный тон.
- Каждое утверждение в контексте проверяемо по коду; сомнительное помечается,
  а не выдумывается.
- Каждое решение в design — с отвергнутой альтернативой: агенту, который
  придёт следующим, важнее знать, почему не сделали иначе.

### Язык

Артефакты, контекст, пользовательские строки, комментарии и сообщения
коммитов — на русском; идентификаторы, пути, код — на английском. Нормативы
спек — «ДОЛЖЕН (SHALL)», сценарии — **WHEN**/**THEN**.
